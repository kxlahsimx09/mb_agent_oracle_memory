## Honest Feedback (what's friable)

- **Step 7.A assumes single-worktree ownership of the PR branch.** In a multi-worktree fleet where each agent gets its own `.wt-N` and a prior pass's branch is still checked out elsewhere, the prescribed `git checkout "$branch"` *cannot run*. The branch-from-tip + refspec-push pattern I used is the correct workaround and should be added to Step 7.A as the multi-worktree path. Without it, a future agent will hit the checkout error and may wrongly fall back to opening a duplicate PR (7.B) — the exact stacking the amend path forbids. **Proposed:** add a note "if `$branch` is checked out in another worktree (`git worktree list`), branch from `origin/$branch` under a temp name, merge origin/main, push with refspec `temp:$branch`."
- **tester-telegram MCP unregistered for the THIRD consecutive pass.** Passes 26, 27, and now 28 all fell back to `#telegram-failed`. The cadence channel (@ampay_test_alert_bot) has been silent for three runs. This is no longer a transient — it needs brew-ops/human to add the registration to the fleet host's `~/.claude.json`. The fallback works, but the operator-facing "did today's code break coverage?" signal is not reaching its audience.
- **The twenty-eighth note is the only material content; the rest of the header is ~190 lines of verbatim-preserved prior notes (P-001).** The header line for `Validated at:` is now an enormous single paragraph. Not wrong, but it's reaching the point where a human skimming it gets no value past the first note. Candidate for a future structural refactor (collapse old passes into a linked appendix) — but that's a P-001-sensitive change needing user sign-off, not something to do silently in a validate pass.

## Recurring-pattern note (for the workflow's "common pitfalls")

This is the second multi-day amend in a row where the *new* surface was a single wallet-log-adjacent payout commit (#505 last pass, #510 this pass) and the deciding factor was always **which fields the test's `countDocuments` filter actually keys on**. The pattern is stable enough to be a checklist item: *for any wallets_change_logs change, the flip test is "does any test filter on the field that changed?" — entity_id/operation changes are load-bearing; reference_id/reference_type/amount additions are not, unless a test asserts them (only `test-payout-admin-cancel.sh` does, and only on the `/cancel` site).*
