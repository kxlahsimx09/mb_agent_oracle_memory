## What the validation turned up that was worth the effort

The headline commit #551 ("Make deposit finalize flip+credit atomic") was the highest-risk
production-surface change I've seen in a while, and it was genuinely worth slowing down on. On its
face it could have flipped *every deposit-auto-match test* to STALE/WRONG-SETUP: it wraps the
matcher's flip-to-`paid` + client-wallet credit + change-log in a Mongo `WithTransaction`, and
MongoDB transactions require a replica set. If the integration-test Mongo were standalone, every
auto-matched deposit would fail to finalize → deposits stay pending → ~20 deposit tests time out.

Two pieces of evidence closed it cleanly and made the NEUTRAL call solid rather than hand-wavy:
1. **The test Mongo IS a replica set** — `docker-compose.yml` literally runs `mongod --replSet rs0`,
   `mongo-init/init-replica.sh` says "needed for transactions", and `setup-infra.sh:281` calls
   `rs.initiate`. So transactions work in the test env by design.
2. **`WithTransaction` is already pervasive in VALID-tested paths** at the prior baseline —
   `services/withdrawalQueue.go` (×4), `payoutReconciliation.go` (×4), Settlement/Payout/Topup/Deposit
   controllers. Those tests are VALID and pass today, which is *runtime proof* the test replica set
   supports `WithTransaction`. The new deposit transaction is structurally identical usage.

Then I verified the observable end-state is byte-for-byte equivalent to before (status=paid + the same
five fields, wallet `$inc balance/available += finalAmount`, one `deposit_match` log with identical
Before/After, `MatchedCount==0` still the race guard), and that the only *new* code paths (missing
wallet / changelog-insert failure → abort) are structurally unreachable in tests because `create_client`
always provisions the wallet. That's what makes this NEUTRAL and not "probably fine."

The trap I deliberately avoided: the W1 production-surface git-log filter does NOT include `main.go`
or `helpers/`. #547 and #553/#554 touched `main.go`/`helpers/storage.go` and would have been invisible
to the scoped log. I read them anyway. #547 gates the periodic schedulers (incl. the deposit Matcher)
behind `RUN_SCHEDULERS` — that *would* have broken every async-match test if the gate defaulted off,
but it's `!= "false"` (default-ON) and the test env never sets the var. #554's Spaces self-check
"does not block startup". Both NEUTRAL — but only because I looked past the path filter. Worth
remembering: a scheduler-gating or startup-blocking change can hide in `main.go`, which the standard
scoped log misses.
