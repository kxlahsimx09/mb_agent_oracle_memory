the injected receiver `9999999999` equals the *default* `BANK_ACCOUNT`

Reading `services/slipFraudCheck.go::EvaluateSlipDestination` settled it cleanly:
the system-bank-account substring compare is gated on `bankAcc != ""` — i.e. it
only fires when the slip carries a `receiver.account.bank.account`. The Phase 2

`ExtractSlipReceiverBankAccount` returns `""` and that branch is skipped
entirely. The proxy is compared solely to the deposit promptpay last-4
(`9999`≠`1234`) → `SlipDestMismatch` → 400, **regardless of `BANK_ACCOUNT`**.
Point (d) was an over-cautious hypothesis. Keeping `9999999999` is correct. That
was the satisfying moment of the session — the static read both confirmed the
promotion and retired a stale worry that would otherwise keep resurfacing on

## Honest Feedback

- **The "production-surface filter = 0 ⇒ no-op" heuristic is incomplete.** The
  task's no-op skip condition ("zero production-surface commits AND pattern lib
  unchanged → skip Step 7") does not account for *test-side* fixes that land on
  main between passes and flip a matrix status. A STALE→VALID promotion is a
  first-class W1 outcome (the matrix has an explicit "Status promotions" field),
  so treating this as a no-op would have left PR #539 asserting a STALE row that
  is no longer STALE. The workflow's Step-1 diff should explicitly include
  `integration-tests/test-*.sh` changes as a trigger for re-evaluation, not just
  production-surface commits. Worth a small note in the W1 reference: "a test
  file changing in-range can *promote* as well as the code changing can
  *demote*." (Proposing, not applying — not my file to edit unilaterally.)

- **point (d) should have been written as a hypothesis, not a near-assertion.**
  The prior STALE row stated the bank-account-collision concern firmly enough
  ("new EvaluateSlipDestination also matches the system bank account, so …
  may resolve ok→200") that it nearly drove a wrong WRONG-SETUP classification
  this pass. The actual gating (`bankAcc != ""`, proxy-only slips never reach
  it) was one function-read away. Lesson for my own future STALE rows: when a
  proposed fix depends on a code path's branch condition, cite the exact branch
  guard, not just the function name.

## Recurring patterns worth a shared note

- The `BANK_ACCOUNT` default (`9999999999`) doubling as the canonical
  "external/mismatch" sentinel in slip-fraud tests is a latent footgun: any
  future assertion that depends on `9999999999` being *external* is only safe
  while the slip carries a proxy (not a bank-account) receiver. If a future
  slip-fraud test injects a `receiver.account.bank.account`, the same value
  would suddenly substring-match the system account → `SlipDestOK`. A test
  helper that picks the sentinel receiver as `BANK_ACCOUNT`-with-one-digit-
  flipped would remove the coupling. (Coverage/robustness idea, not filed as a
  gap row since no test is broken today.)
