# /system-bank — realtime wiring + UI parity + deploy

## One-line
Drove the admin-portal `/system-bank` page from "live-but-static (fetch-once) + mock live-indicator"
to **genuine realtime (12s visibility-aware polling) + 8 in-scope UI-parity items** vs the
`kokarat/clone_maxpay_frontend` reference, then got it **deployed + bundle-verified live** on
Vercel production — via a 4-role team dispatch under my own slug (brew-ops → next-architect →
next-dev → next-pm), plus a follow-on brew-ops deploy.

## What the owner asked
1. Focus on **wiring `/system-bank` to work with genuine realtime data**.
2. Assess: what needs changing, is the backend ready, can it be done.
3. Compare UI vs the `clone_maxpay_frontend` reference; fill the gap to match.
Operating rules: push to completion, ping only for real decisions/ADR/requirement-change/blocker;
dispatch by role (env/supabase=brew-ops, adr/spec=next-architect, requirement=next-writer,
dev/fixbug=workflow-2 build, done-check=pm); **no reusing other teams' agents** — own slug only;
close idle teammates.

## What we found / decided
- The page was **already live** (reads `v_system_banks`), but **fetched once on mount**; the
  `LiveIndicator` was an explicit **mock**. That was the realtime gap.
- **brew-ops:** Supabase Realtime `postgres_changes` on `bank_account` is **unsafe** — it streams
  base-table rows (not the masked view), leaking `bank_credentials_secret_id` + config, and needs
  re-opening the SV7b zero-grant. ⇒ **client-side polling** is the leak-safe, zero-backend realtime
  path. `settlement` = free alias of `method_payout`; `mdrProfile`/`topup` out-of-scope;
  daily-out/amount/priority need a gateway aggregate (separate ADR).
- **next-architect:** spec with the polling decision, a 25-row parity gap table (8 in-scope:
  BACKED-NOW/PURE-UI; 17 fenced as NEEDS-BACKEND), and a build-brief.
- **next-dev:** PR #71 — controlled indicator, 12s visibility-aware silent polling (stale rows kept
  on poll-error, never blanks), settlement chip, available balance, heartbeat freshness, method+bank
  filters, copy buttons. Poll logic extracted to a hook to hold the 250-line cap. tsc + next build green.
- **next-pm:** independent done-check → **PASS** (re-verified both builds, scope intact, no fabricated data).
- Owner merged #71. **brew-ops (follow-on):** prod was **stale** (CLI deploy predating the merge);
  ran `vercel deploy --prod`, **verified the served bundle** carries the change.

## AI Diary (first-person)
I went in treating this as a classic orchestration: scope just enough to write good contracts, then
dispatch. The recon paid off immediately — discovering the page was *already* live (not mock) reframed
the whole task from "wire data" to "add realtime + parity," which is what I put in the contracts. I
deliberately ran brew-ops and next-architect in parallel because the parity diff is independent of the
backend question, and made the architect consume brew-ops's findings for the realtime call.

The architect loop was the moment I felt real friction. Two captures minutes apart showed the same
spinner/idle oscillation and zero files on disk — that pattern (plus the "Teammate came to rest"
self-pings and the fact it had spawned an Explore sub-agent) read clearly as a wedged session, not slow
progress. I nudged once; it ate the nudge. Killing and re-spawning with a tighter, no-sub-agents,
write-first prompt was the right call and it worked first try. I felt good that I'd pre-loaded every
decision into the re-spawn so it didn't re-investigate — that's what made the fresh turn fast.

The quota warning made me pause. I almost just pushed through, but it was a *shared* fleet account at
97% with other teams running, so I treated it as a genuine resource decision and checkpointed. The owner
both green-lit and cleared it — validating the choice to surface rather than silently burn it.

The deploy follow-on was the most satisfying part. My first read of the GitHub "Production / failure"
could have sent brew-ops chasing the wrong thing; spotting that *every* commit (including known-good
ones) had the same `-docs-` failure let me hand brew-ops a precise "this is a red herring, the app is
CLI-only" lead. brew-ops then found prod was genuinely stale and the owner's instinct to deploy was
exactly right — the merge alone had shipped nothing.

## Honest Feedback (frank)
- **What worked:** memory-first + Step-2.5 HEAD verification kept the contracts accurate (the page was
  already live — a stale brief would have wasted a whole build). Parallel R1, kill-and-respawn the wedged
  architect, checkpoint-on-shared-quota, and the bundle-level deploy verification were all correct.
- **What I'd do better:** (1) My first build-watch Monitor had a real bug — comparing a full git SHA to a
  7-char short SHA produced a false "DEV-COMMITTED" event. Cost a stop+re-arm. I should sanity-check
  Monitor predicates before arming. (2) I spawned the *first* architect with a prompt that didn't forbid
  sub-agents; the Explore agent likely triggered the self-ping loop. The re-spawn fixed it, but I could
  have pre-empted the whole incident by saying "read directly, no sub-agents" in the first contract for a
  big-file diff. (3) I leaned on capture-pane polling more than the doorbell; the doorbell never clearly
  fired for me this session (I drove everything off Monitors + manual captures), which is worth noting —
  either it's not wired for this orchestrator pane or I didn't lean on it enough.
- **Process honesty:** I did the recon reads myself (page, api lib, reference sizes, brew findings, the
  spec, the PR diff) — that's orchestrator premise-verification, not "doing the work," but it's a lot of
  reading. Defensible here because each read directly shaped a contract or a checkpoint, but worth
  watching that it doesn't slide into doing the analysis the architect is for.
