## AI Diary

This one actually made me work, which was a relief after reading the cumulative
header prose where every pass for two weeks was "finance, NEUTRAL, carry
forward verbatim." The moment I saw the commit list I flagged two as
existential threats: #514 (Terms & Conditions) touched `routes/depositRequest.go`
AND `routes/payoutRequest.go`, and #535 added a brand-new middleware to
`routes/settlement.go`. If either gated the create paths unconditionally, this
wouldn't be a "2 flips" pass — it'd be a "~40 tests all newly broken" pass,
because almost every test creates a deposit/payout, and seven create
settlements. So I read those two diffs first, before anything else, because the
whole shape of the report depended on them.

Both turned out to be dormant-by-design, and the *reason* each is dormant is
different and worth remembering. #514's `RequireTermsAccepted` fails OPEN:
`currentTermsVersion()` returns 0 when no T&C row exists, and `0 > 0` is false —
the test env never publishes a T&C, so the gate is a no-op. #535's
`SettlementWindowGuard` is config-gated: `IsSettlementBlocked()` returns false
unless `app_settings.settlement_block_enabled=="true"`, which no test sets — so
it's dormant *regardless of wall-clock*. That second point mattered more than
usual today: it's currently ~00:10 Bangkok, which is INSIDE the default
`22:30-02:00` window. If the feature had defaulted ON, every settlement test
would have become time-dependently FLAKY and I'd have been tempted to mark them
FLAKY — but the default-OFF check short-circuits before the window is even
evaluated, so there's no flakiness to flag. I almost wrote a FLAKY note before
re-reading `IsSettlementBlocked()` and seeing the `!= "true"` early-return.
Good catch by reading the helper, not just the middleware.

The two real flips were both in the slip/deposit cluster, and both are
contract-drift, NOT regressions — the production changes are good (the
external-destination guard got more robust; deferred Thunder is the right
design). The tests just assert the *old* contract. #529 was the cleanest:
it renamed response payload keys (`slip_receiver_last4` → `slip_destination`)
AND the log strings the test greps for, AND made the guard match the system
bank account too — and the test injects receiver `9999999999`, which is the
default `BANK_ACCOUNT`, so the guard might now say "ok" and return 200 where
the test wants 400. Three independent breakages in one commit; the test
hard-asserts all three. That one fails a real run.

#522/upload-slip was the subtle one and I sat with it longest. The test asserts
`status=checking` after slip upload, but #522 makes a *pending* deposit stay
pending. The catch: the test has a 503-CDN-skip branch, and the integration env
has no CDN, so at runtime it takes the skip and exits 0 — the drifted assertion
is never evaluated. So is it STALE or VALID? I went STALE-but-latent, and made
"Newly-broken: 2" honest by annotating that one is a direct fail and one is
masked. P-004 says code is truth: the test's documented claim
("upload → checking") is now false for the dominant case. Marking it VALID
would be smoothing over a contradiction. But I refused to pretend it fails a
regression run today, because it doesn't.

## Honest Feedback

**The "Newly-broken since prior baseline: N" line is overloaded and the
workflow doesn't say what it means.** The header comment says the regression
watcher greps it as a gate. But "newly broken" can mean (a) "flipped to a
non-VALID status since the prior baseline" or (b) "would fail a regression run
today." Those diverged this pass: slip-fraud is both; upload-slip is only (a).
I reported 2 and annotated the distinction inline, but a watcher that does
`grep -oP 'Newly-broken.*: \K\d+'` and alarms on `>0` can't see my annotation.
W1 should define this counter precisely — ideally split it into
"newly-non-VALID" and "newly-fails-regression-run" — so the watcher keys on the
runtime-fail number and humans still see the full drift count. Filing this as a
workflow-refinement candidate, not applying it.

**The env-masking case (STALE-but-passes-in-this-env) has no taxonomy bucket.**
The SKILL's STALE definition ("would fail OR pass-for-wrong-reason if run")
technically covers it, but there's no guidance on how a masked-STALE interacts
with the regression counter or whether it should be excluded from
`regression-suite.txt` the way the same-amount-FIFO KNOWN-WONTFIX tests are.
An explicit "LATENT" sub-tag or an `ON_HOLD`-style annotation column would make
these honest without inflating the runtime-fail count.

**`docs/test-index.md` is becoming unreadable as an artifact.** Line 4 alone is
~80k tokens of cumulative "prior pass follows verbatim" prose — I literally
could not Read it in one call and had to grep for section line numbers and edit
by prefix-matching. The append-verbatim discipline (P-001-flavored) is right
for the vault, but this is a *derived* doc the workflow explicitly says I may
overwrite. We should cap the in-file header history (e.g. keep the last 3
passes inline, move older narrative to a `docs/test-index-history.md`), or the
file will eventually exceed every tool's read limit and become unmaintainable.
The matrix itself is fine; it's the header changelog that's metastasizing.

**Telegram has now failed 8 passes straight** and the fallback (file an
`arra_learn`, move on) works but no one is acting on the accumulating
`#telegram-failed` learnings — the bot `@ampay_test_alert_bot` MCP simply isn't
registered on whatever machine these runs land on. This is a real cadence gap:
the operator gets zero push signal that W1 even runs. Worth a brew-ops handoff
to either register the MCP or retire the Step-7b requirement if the channel is
dead. I didn't escalate this pass (the learning trail is the durable record per
the fallback), but 8 consecutive is past the point of "transient."

**What recurred / what I'd want a helper for:** nothing setup-pattern-wise this
pass (no `working_status: 'ready'` cluster etc.). The recurring *analysis*
pattern was "new middleware on a hot route → check the default/fail-open
behavior in the helper, not just the route wiring." Three of the four
highest-risk commits (#514, #535, #528) were guards that are conditional on
state the test env doesn't set up, so they're inert. That's a reusable triage
heuristic: a new guard only flips a test if the test's data/config actually
trips the guard's *condition*, and most new guards default-off or fail-open.
