1. **The `rejected` payout terminal — writer-flagged, NOT escalated to a thread.** §ADR-9 §Bundle TS2 ratifies a 4th payout terminal `rejected` (a *deliberate* bank refusal: insufficient funds at the system bank / account closed / KYC block) distinct from `failed` (system/technical). But §ADR-9 TS3 names its dedicated lifecycle RPC `mark_rejected` as **"future"**, and §ADR-4a's ratified lifecycle RPCs are `mark_success` / `mark_failed` / `mark_waiting_to_review` only — no `mark_rejected`. The trio task scoped PAYOUT-003 explicitly to `failed`. I authored PAYOUT-003 for the `mark_failed` path and recorded the `rejected` gap as a **PAYOUT-003 Open Question**, *not* an `[AWAITING_THREAD]` anchor and *not* a new Oracle thread. Rationale: the surface is **known-deferred, not silent** — the ADR explicitly says "future". PAYOUT-003 itself is fully ratified for its scope and is not blocked. This matches how PAYOUT-008 handled the maintenance-window bulk-cancel question (Open Question section, no anchor). Flagged prominently for the architect in the PR + arra_learn — it is a real candidate for a §ADR-4a amendment + a future PAYOUT-00X story (the bank-reject outcome currently has no story; deposit's symmetric `rejected` got DEPOSIT-007).
2. **File size — 360 lines, over the 250-line target.** Did NOT split. ## AI Diary

This pass felt like the DEPOSIT-006/007/008 batch — a clean tail-wind run where the sources are ratified and the authoring is mostly transcription discipline. The one genuine thinking moment was the `success`/`completed`/`rejected` terminology tangle. Production ts_payouts says `completed`; §ADR-9 says `success`; and there's a `rejected` terminal with no RPC. I almost reached for an AWAITING_THREAD anchor on the `rejected` gap out of caution, then stepped back: the discipline is to escalate *silent* surfaces, and this one is not silent — §ADR-9 literally writes "future `mark_rejected`". A known-deferred item is an Open Question, not an escalation. PAYOUT-008 set that exact precedent in the same file. The honest move was to author the trio as scoped, flag the gap loudly for the architect, and not pretend a story exists that the substrate can't yet support.

The dpay aggregate that returned uniform totals was a small trap — for a moment the data looked like "every payout has every field populated", which would have been a fabrication risk if I'd trusted it. The `$strLenCP` re-run is the kind of thing that pays for the "verify exhaustively" discipline.

## Honest Feedback

- **The `rejected` gap is a real architecture hole, not just a writer footnote.** Deposit's `rejected` terminal got a whole story (DEPOSIT-007, the fraud BLOCK). Payout's `rejected` — a bank deliberately refusing a transfer — is at least as common a real-world outcome as a technical timeout, and right now it has neither an RPC nor a story. The §ADR-9 §Bundle ratified the *taxonomy* but §ADR-4a was never amended to add the RPC. This is a bundle-amendment leaving a sibling ADR behind. Worth a dedicated architect pass.
- **The 250-line rule keeps getting flagged and never enforced.** epic-deposit blew past it; epic-payout is now at 360. The rule is real but the discipline to *act* on it (split, archive) keeps deferring to "a future W2 pass". At some point the W2 pass has to actually happen or the rule is decorative.
- **House-style drift on inline ADR refs.** SKILL §4 says no ADR ids in the body; the merged payout stories are full of them. Either the SKILL rule should be softened to "ADR refs allowed in ACs/edge-cases, never in user-journey prose" (which is what the file actually does), or a W2 pass should strip them. The ambiguity makes every authoring pass re-decide.
