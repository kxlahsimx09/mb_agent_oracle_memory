## AI Diary

The first twenty minutes were almost entirely orientation, not coding. The
worktree I was spawned into (`wt-32`, branch off `main`) did not contain
`scripts/inbox-watcher.sh` at all — `main` and `feat/all-prs-rebased` are two
divergent lineages, and the entire directed-inbox watcher stack lives only on
the `feat/all-prs-rebased` line. If I had trusted the spawn worktree I would
have created the file from scratch on the wrong branch and produced a PR that
silently forked the watcher. Checking `git worktree list` and the fork's PR
list was what surfaced the real topology: PR #70 = `fix/inbox-watcher-
orchestrator-dedup`, still open, the correct base. I created a fresh worktree
off that branch and worked there.

The watcher itself is a dense 924-line bash daemon. Fix 1 turned out small and
clean once I understood that `wake_key` and the `deferred` dedup are two
separate mechanisms — I only had to touch the former. Fix 2 was the bulk: I
deliberately kept the orphan-worktree prune heavily gated and tested it against
a real throwaway git repo with planted orphan / dirty / referenced worktrees.
That test earned its keep — it caught a real bug: my first reference-check used
an exact full-path `grep`, and macOS `/tmp` vs `/private/tmp` symlink resolution
made it miss, pruning a worktree an active envelope still owned. Switched to a
basename match.

The `.agent.bak` line in the brief was the one judgement call. The brief said
"prune them"; AGENTS.md §3a and P-001 said "leave them". I chose not to code
the deletion and instead surfaced the conflict in the reply. That felt like the
right reading of External Brain / Patterns-Over-Intentions — the brief is an
intention, P-001 is a principle, and the charter says the principle wins.

## Honest Feedback

- **The spawn-worktree base mismatch is a real fleet bug, not just my
  inconvenience.** The inbox-watcher campaign system spawns agent worktrees off
  `main`, but the code those campaigns most often need to edit lives on
  `feat/all-prs-rebased`. Any agent given an inbox-watcher task will hit this.
  Worth a follow-up: either merge the lineages or have the spawner pick a base
  per task. I flagged it here but did not fix it (out of scope for #139).
- **PR #71 is stacked on an unmerged PR #70.** Clean for review but it means
  #71 cannot merge until #70 does. Acceptable, but a reviewer should know.
- **I could not run shellcheck** (not installed). `bash -n` + functional tests
  against isolated `STATE_DIR` are decent coverage, but a lint pass would have
  been cheap insurance on 240 new lines of bash.
- **I did not restart the live watcher.** Correct call — it supervises the
  inbox pipeline including this very session — but it means the fixes are inert
  until an operator does the `stop`/`start`. The deploy step is documented in
  the PR and the reply, not automated.
- The watcher file is now ~1030 lines, well past the repo's 250-line
  convention. Splitting a single bash daemon across files would be worse, so I
  left it; the convention realistically targets the TS source, not these
  ops scripts (w2-watcher.sh etc. are all similarly large).
