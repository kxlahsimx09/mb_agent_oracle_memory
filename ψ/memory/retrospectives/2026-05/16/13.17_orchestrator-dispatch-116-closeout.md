## AI Diary

This wake looked like a no-op at first — the envelope was already in
`handled/`, so a naive Step 0 sweep would have found nothing and exited.
The SKILL's state-grounding discipline is what saved it: re-reading thread
#116 from the API (not trusting "envelope archived ⇒ done") showed the
thread still open and the result missing. The peer session that archived
the envelope did the cheap half (move the file) and skipped the expensive
half (aggregate + close + learn). That is exactly the "archiving is not the
close-out" failure the SKILL's Mandatory-Close-Out block warns about — and I
got to watch it happen, then repair it. Satisfying in a quiet way: the
discipline isn't ceremony, it caught a real silent gap.

The one thing I sat with: whether to send the Telegram report at all, given
I couldn't prove the peer session hadn't already messaged the user. I chose
to send — the user explicitly requested this purge and is owed a report, the
thread state proved the close-out was incomplete (so a notification likely
was too), and a duplicate completion report is low-harm. Phrased it as a
clean standalone report so a duplicate would read fine.

## Honest Feedback

- **The race is real and will recur.** The orchestrator inbox is pull-style:
  any orchestrator session sweeps all of `for-orchestrator/`. When the
  watcher fires a dedicated wake AND a concurrent session sweeps the same
  envelope, you get exactly this split — one session archives, the wake
  session arrives to a "done" inbox. The watcher's T2 gate (`file left the
  root`) is satisfied by the peer's archive, so nothing flags it. The only
  backstop is the woken session doing the state-grounding read anyway.
  Worth considering: the watcher could check thread status, not just file
  location, before marking `completed`.
- **`status=answered` vs `closed` is load-bearing and easy to miss.** A
  thread can look "handled" (answered) while the orchestrator close-out is
  unfinished. Future sweeps should treat `answered` on an orchestrator-owned
  thread as "verify close-out done", not "done".
- **No way to confirm prior Telegram sends.** I can read thread state but
  not "did a peer session already message the user." If double-notify
  becomes a nuisance, the orchestrator-bot could log outbound sends per
  thread so a later session can check.
