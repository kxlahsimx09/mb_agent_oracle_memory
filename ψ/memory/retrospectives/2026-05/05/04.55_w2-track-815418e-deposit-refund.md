## Surprises

- **`enable_deposit_refund` defaults OFF and stays that way until ops flips it.** The feature shipped in production-merged #399 but is invisible to live traffic until an `app_settings` upsert. That's the right kill switch for a money-out endpoint, but it means the doc has to be read carefully — the flow EXISTS in code but a curl will return 503 in every environment until ops opts in.
- **`/refund/resolve` is intentionally NOT flag-gated.** The reason is subtle and load-bearing: if ops disables the flag mid-incident (e.g. during a postmortem where they don't want new refunds firing), they still need to be able to close out `refund_pending_review` rows without flipping the flag back on. The doc captures this but it took a second read of the handler comment to spot the asymmetry.
- **The cancel-hook's prior-status branching (`pending_approval=cancelled / approved=uncertain`) was a pre-merge security review fix, not part of the original design.** The commit message has a section "Refund: pre-merge security hardening" that calls it out as a CRITICAL flagged by independent review. Documented the branching in §3 direct-transfers row + §3.2.6 because the alternative ("approved DT cancel always auto-credits") would re-open a double-spend window if someone re-reviewed without context.
