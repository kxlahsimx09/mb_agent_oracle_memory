**What didn't:**
- **Initial dedup proposal had hidden weakness on SCB ambiguous-pair edge case.** I proposed unique constraint + bank-specific composition + raw_text_hash tie-breaker. The composition design was sound for KTB (balance_after distinguishes) but failed for SCB (description identical for same-source same-minute deposits). - **Initial B3 framing as bot-side circuit-break logic** — over-engineered. Required 30-50 LOC in bank-bot adapter per drift class (fail-loud / circuit-break / auth-classify). User's monitoring reframe is cleaner. **Process improvement:** before specifying mitigation logic in implementer territory, ask "is this drift class a concern unique to this endpoint, or shared across system?" Shared concerns belong to centralized substrate, not per-endpoint code.
- **Did not anticipate `linkCheckingDeposit` dependency until B7 walkthrough.** match_hash V1 fraud detection requires correct `bank_statements.matched_request_id` at slip-approve time, which requires the 3-step matcher cascade. I proposed match_hash port without verifying matcher cascade is in next-system spec (it's in §ADR-4b D2 only as 1-line "match-deposits EF"; cascade detail not specified). User's walkthrough request surfaced this. **Process improvement:** when porting feature X from current, verify all dependencies of X (especially same-file-or-flow features that cooperate with X) are also accounted for in next-system spec.
- **Pass duration 9 hours of dialogue is long even for fast lifecycle.** While single-day single-pass is fast for §ADR-X amendment compared to multi-day baselines, 9 hours of dialogue is more than typical 60-120 min W1 spec. Most of that was good architectural dialogue (no wasted time), but pass-time accounting should reflect this honestly. **Note for next pass:** if dialogue extends beyond ~3 hours, consider splitting into multiple PRs or extracting design doc work to separate session.

**What would make the next pass cheaper:**

- **Cascade dependency map:** before porting X, list all features in current that cooperate with X (read same data, write same table, depend on same field). Verify each in next-system spec.
- **Process documentation: "Pre-Input-5 proactive use" pattern.** User caught 3 architectural gaps proactively. Pattern is durable across 13+ instances. Heuristic for system-architect: treat user "ลองค้นดู / verify in current code first" as Pre-Input-5 trigger; budget code-read time accordingly.
