## Surprises

- **The deposit-refund flow's bot-transparency is genuinely architecturally elegant.** The earlier design (per the commit body) proposed a brand-new `ts_deposit_refunds` collection + `SourceTypeRefund` + parallel branches in `services/withdrawalQueue.go` (~700 lines); the shipped design reuses `direct_transfer` end-to-end (~200 lines). For W9 this means: the existing `withdrawal-queue-dispatch-and-claim.md` and `withdrawal-queue-single-bot-transfer.md` flows already correctly describe how the bot processes the refund DT (it's just a DT). The new flow doc only needs to cover the **deposit-side actor-crossings** (admin issues refund → admin reconciles `refund_pending_review`), not the DT-side bot interactions. That makes the W8 authoring scope smaller than it first appeared.
- **`refund_pending_review` is a bisection state, not a queue state.** It lives on `ts_deposits.status`, not on `withdrawal_queue.status`. The DT itself is in whatever terminal state the bot put it. So the future flow's "wait for admin reconcile" step doesn't talk to the queue — it talks to the deposit row. Capturing this distinction up-front in the W8 authoring will save the author a wrong cycle.
