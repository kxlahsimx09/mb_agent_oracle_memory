## 3. orchestrator-bot smart-default (arra-oracle-v3#45, merged 6a74c3b → all-prs-rebased)

`scripts/orchestrator-bot/bot.sh` (+55, -2):

**New helper** `pick_smart_active_thread()` — when no `/use N` is set:
1. Query `$ORACLE_API/threads?limit=30` for pending threads.
2. Filter to parents (title not starting `[from `).
3. Per candidate, fetch full thread, check `messages[-1].role == claude` AND `messages[-1].created_at >= now - SMART_THREAD_WINDOW_SEC` (default 1800s, env-tunable).
4. If exactly one survives → return its id. Otherwise empty (caller falls through; no auto-attach when ambiguous).

Uses live API not `KNOWN_THREADS_FILE` cache because threads opened by the orchestrator agent itself never enter the cache (cache only tracks user-touched threads via `/use` or `/threads`).

**BSD date subtlety baked into the code as a comment:** `date -j -f "%Y-%m-%dT%H:%M:%S" "..."` without `-u` parses input as local time and misreads UTC API timestamps by the tz offset (verified: GMT+7 box would think a 12:44 UTC msg was 6h+ in the past). Fix: `date -j -u -f "..." "..."`. After parsing, strip fractional seconds (`%%.*`) and trailing `Z` (`%Z`).

**Reply wording fix** — the stale `📨 new request received (orchestrator will open a parent thread)` is replaced with two truthful messages:
- Smart-default hit: `📨 continuation → thread #N (smart-default: only recent pending parent; /new override, /use N switch)`
- No candidate: `📨 dispatched (orchestrator will read context and decide: new thread vs continue)`

No behavior change when `/use N` is set. Active-thread path unchanged.

# What I learned (lessons)

## 1. §11k pull-style needs symmetric guarantees (architect side, NOT just protocol doc)

The protocol was already documented in arra-oracle-v3 `.agent/AGENTS.md` §11 (line 333 — "reply in thread → write reply inbox file → archive"). Architect's session-onboarding loaded §11 by reference but the active SKILL.md had no inbox section — so when the architect was deep in the domain-knowledge reply, it executed the **content** step ("reply in thread") and treated "ready to converge" as the close-out, not the **notification** step. The protocol-doc-only version of the rule didn't have enough cognitive weight at the moment of action.

**Heuristic learned:** when a multi-step protocol fails at one step, codify the rule into the SKILL.md of the role most likely to skip it — not just into the shared protocol doc. SKILL.md is what loads on activation; AGENTS.md §11 is what loads on reflection. The active step needs the rule active.

## 2. Bot UX can lie about agent behavior — fix the UX, don't trust the agent to compensate

The orchestrator agent at wt-22 was smart enough to read context and converge into #66 even though the bot told the user "will open a parent thread." That's a *good* failure mode (agent behavior was correct) but a *bad* trust signal — a future agent that's slightly less context-aware could've actually opened #69 because the bot's instruction was effectively "this is a fresh request, treat it as such." Don't rely on agent judgment to mask UX bugs; tighten the UX so the agent gets less ambiguous input.

## 3. Smart-default ergonomics > "type /use every time"

The smart-default function is ~30 lines + 2 lines at the dispatch site. Marginal cost is small (1 list call + N detail calls per dispatch, all <100ms total in practice). Marginal gain is large (the *most common case* — replying to a recent orchestrator question — now works without ceremony). Bias the bot toward what's plausibly intended, fall through to neutral honesty when uncertain. The 30-min window + parent-only + claude-last-msg filter makes false-positives extremely rare.

## 4. Manual nudge envelopes should never spoof `from:`

When I filed the unstall envelope, the temptation was to write `from: next-architect` so the orchestrator's wake handler would see "architect replied" symmetrically. I resisted and used `from: brew-ops` with an explicit "Manual nudge — architect skipped envelope" header in the body. This kept the §11k violation visible to anyone auditing later. The audit trail is the load-bearing artifact — preserve it even when it's slightly less ergonomic.

## 5. BSD date `-u` is non-obvious; codify the wisdom in the comment

Spent ~5min debugging why all candidates were rejected (turned out tz-offset off-by-7-hours from UTC parse). Easy mistake to repeat. Solution: bake the subtlety into the comment in `pick_smart_active_thread` so the next reader (human or AI) sees the rule + the *why*: `# API timestamps are UTC. BSD date -j -f without -u parses as local time and misreads UTC inputs by tz offset.`

- Bot restart noticed and fixed the duplicate-instance issue immediately (kill + nohup + disown). Single instance verified by `ps -ef` parent-pid check.

**What was sloppy:**

- The first restart of the bot left two instances running. Standard `nohup ... &` doesn't always detach cleanly from the spawning shell. Took a second pass with explicit `disown` to fix. Should have done it right the first time — small, but indicative of corner-cutting on operational discipline.
- I opened a PR for the SKILL.md fix on the vault when memory (`feedback_agent_dir_is_symlink.md`) explicitly says "commit-to-main OK (single-author exception)" for `.agent/` edits. Outcome was identical (merged in 5 min) but I deviated from the established convention. The user said "PR" once verbally and I extrapolated; should have weighed the durable memory rule against the in-conversation phrasing. Soft-rule violation; noted for next time.

**What I'd do differently:**
- Earlier session, when designing the directed-inbox protocol, the §11d archive rule was paired with §11c reply but the binding wasn't strong enough to survive a context-heavy session. The rule needs to be inline in *every* SKILL.md of *every* role that participates in pull-style protocols, not just in the shared AGENTS.md. brew-ops's SKILL.md should get the same `## Inbox protocol (binding)` section even though brew-ops hasn't violated it yet. Pre-empt the failure mode rather than wait for the second incident. Worth opening a follow-up issue.
