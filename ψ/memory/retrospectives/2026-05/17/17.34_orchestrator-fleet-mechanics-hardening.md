## Key learnings

1. **The orchestration loop had structural bugs that only surface under load.** Reply-routing to the wrong session, duplicate worker sessions, loop-closure not enforced, gc blind on two independent counts, deploy drift — none were visible until many dispatches ran concurrently. Running the fleet hard *is* the test.

2. **Verify the PR / state — do not trust the agent's reply envelope.** Agents repeatedly reported conflicting, duplicated, or incomplete results: two brew-ops sessions reached opposite conclusions on #153; §11l escalations were noise from sibling churn; "done" replies arrived for work that still needed checking. Direct verification (`gh pr view`, reading the watcher source, `pgrep`) was load-bearing every single time.

3. **A fix for a meta-level bug gets eaten by that same bug.** The #151 and #153 fix-threads — whose whole purpose was to stop mis-routed / duplicate sessions — themselves fanned out into duplicate sessions and tripped the circuit-breaker. Land meta-fixes in a calm fleet state, or the fix-dispatch is itself corrupted by the bug it fixes.

4. **The §11l circuit-breaker earned its keep.** When a session could not close its loop it escalated a priority-high envelope to the orchestrator rather than hanging silently or dropping work. Every escalation this session turned out to be noise — but noise that *surfaced*, which is the correct failure mode.

5. **Adjudicate conflicts by reading the code, not by re-polling agents.** When two brew-ops sessions disagreed on whether #77 was needed, another dispatch would only have produced a third opinion. Reading the actual watcher diff settled it in one pass: #77 closed a real residual (the §2 fallback dedup was orchestrator-gated).

6. **Concrete:** the Nextra v4 `<Layout>` SSR failure is a genuine upstream bug (Zod 4 + a `children`-required schema vs a destructured prop), fixed with a one-line `patch-package` patch — not a version mismatch. The earlier plain-div workaround was a real, considered response, not laziness.

## AI Diary

I came into this session expecting payment-gateway coordination, and for a while that is what it was — dispatch the audit, route the findings, merge the PRs. The turn came when the user asked a quiet, sharp question: when I dispatch work, how do I actually know it finished? I had been polling. Every "เป็นไงบ้าง" from the user was me running a bash check. There was no mechanism — I *was* the mechanism.

Pulling that thread unravelled a lot. The replies to threads I opened were waking *other* orchestrator sessions, not me. Workers getting a second envelope spawned siblings. Agents finished and never reported back. gc had been silently failing for days on two unrelated bugs. The live watcher was running uncommitted code. None of this was a single dramatic failure — it was a fleet that worked well enough to hide its own seams until someone ran it hard and looked closely.

The middle of the session felt like chasing my own tail, and sometimes literally was: the fix-threads for the routing bugs kept fanning out through the very bug they were meant to fix. brew-ops escalated, escalated again, contradicted itself across two sessions. I learned to stop trusting the envelopes and just go read the PR, the code, the process table. That was slower per-step but it was the only thing that produced a single, true answer — most memorably when I adjudicated #75-vs-#77 by reading the diff instead of asking a third time.

By the end the fleet is genuinely in better shape than it started: loop-closure enforced, routing sticky both ways, gc honest, deploy discipline written down, a real secret store, auto-start that retries. And a new project — p2p-hub — is cleanly kicked off and paused at a sensible checkpoint. It felt less like building features and more like tightening every bolt on a machine while it was running.

## Honest Feedback

**What worked.** Closing threads promptly so gc could retire their worktrees — the discipline the user pushed early paid off all session. Verifying state directly instead of trusting replies. Arming the Monitor as an in-session stopgap the moment the user named the polling problem. Phasing big tasks (audit finding #5, the p2p doc) instead of one mega-dispatch. Recommending the restart-first reframe when the pre-restart goal became self-defeating.

**What didn't.** The session was noisier than it needed to be. Stacking fleet-mechanics fixes (#150/#151/#153) while the fleet was actively churning meant each fix-dispatch hit the churn — I should have recognised earlier that meta-fixes need a quiet fleet, and either serialised them hard or done the restart sooner. I also spent real effort disambiguating §11l escalation noise from genuine failure; a calmer cadence would have produced fewer false alarms to triage. The duplicate-worker bug was visible early (the #151 incident) yet I kept dispatching into the same churn for a while before the dispatch-side fix (#153) landed.

**On the human's instinct.** The user repeatedly saw the structural issue before I articulated it — the polling gap, the wrong-session routing, "it should be one answer." When they said "you handle it — there should be one answer," that was the right correction: I had been content to surface a conflict rather than resolve it. The orchestrator's job is to drive to a single answer, by reading the code if necessary.

**Carry forward.** Run meta-fixes against a calm fleet. Treat agent replies as claims to verify, not facts. Keep the Monitor (or its successor — the #151 routing fix) so completion is pushed, not polled.
