# §11d loop-closure enforcement — Stop-hook gate

## Summary

The orchestrator dispatched (thread #140) a fix request: dispatched oracle
agents do their work but never close the directed-inbox loop — no reply
envelope on `needs_response:true`, no §11d archive of the inbound envelope
(observed on thread #132: next-impl PR #135, next-writer PR #139). The
user's explicit ask: dispatched agents must reply.

Delivered a Claude Code `Stop` hook (`scripts/inbox-loop-closure-hook.sh`)
that blocks a dispatched oracle's session from ending while its inbox loop
is open. PR #72 (fork); AGENTS.md §11l + brew-ops SKILL.md committed to the
vault (`9e9a2cc`); learning filed (`c4c1e64`).

## What was done

1. `scripts/inbox-loop-closure-hook.sh` (197 lines) — Stop hook. Identifies
   the oracle by reverse-looking-up the session id against the inbox-watcher
   `state/`+`sessions/` maps (self-gating: non-oracle sessions = no-op).
   Blocks on (a) any envelope still in `for-{oracle}/` root, (b) a recent
   `handled/` envelope with `needs_response:true` missing both
   `handled_by_inbox` and `handled_note`. Circuit breaker after 3 blocks →
   `priority:high` notify to `for-orchestrator/`. Fail-open on any error.
2. `scripts/install-inbox-loop-closure-hook.sh` — idempotent installer;
   deploys to `~/.claude/hooks/`, registers in `~/.claude/settings.json`.
   Installed; the pre-existing `Glass.aiff` Stop hook preserved.
3. AGENTS.md §11l + brew-ops SKILL.md ops-infra entry (vault commit).
4. Dogfooded: replied on thread #140, wrote the reply envelope to
   `for-orchestrator/`, archived the inbound envelope — all under the new
   gate. Verified the hook then passes for this session.

## AI Diary

I started by reading the charter and principles, then thread #140. The
dispatch was unusually well-scoped — the orchestrator had already done the
diagnosis groundwork and explicitly said "your call" on the mechanism, even
naming the shape it suspected (a fail-loud session-end check). My job was
to pick the most reliable mechanism and actually land it.

The first real decision was *where* enforcement lives. A skill step was
ruled out by the brief itself ("clearly isn't sticking"). I considered
extending the inbox-watcher — it already has a T2 `failed_stuck` gate — but
realised that is detection, not enforcement: it alerts after 30 min, it
doesn't make the agent reply, and the reply gap proper (archived without a
reply) it never sees because an archived envelope reads `completed`. The
stale #124/#125 envelopes are proof the watcher's detection alone hasn't
fixed anything. So: a `Stop` hook — the harness gate that fires exactly at
"before the session ends," which is what the brief asked for.

The cleverest part fell out of reading the inbox-watcher source: it already
writes `session_id=` into every per-envelope state file. That gave me a
free, reliable session→oracle map. The hook reverse-looks-up the Stop-hook
payload's session id against it — which means the hook *only* engages for
sessions the watcher spawned to handle an envelope. Every other claude
session on the node is a silent no-op. That single property is what makes a
global `~/.claude/settings.json` install safe instead of reckless.

I spent real care on two safety properties: fail-open (a hook bug must
never wedge a session — `trap 'exit 0' ERR`) and the circuit breaker (don't
loop forever on a genuinely stuck agent). The breaker's first draft just
logged to a file — then I caught myself: a silent give-up *is* the exact
bug I'm here to kill. So the breaker writes a `priority:high` notify
envelope to the orchestrator. A stuck agent becomes a visible signal.

My test harness had a bug — a wrapper function whose last statement was
`echo "exit=$?"`, so it always returned 0 and I briefly thought the
circuit breaker wasn't blocking. Re-tested capturing the hook's exit code
directly: blocks 1–3, trips at 4, counter resets. The hook was fine; the
test was lying.

Closing the loop on thread #140 myself was the satisfying part — the hook
was installed, so my own session became subject to it. I posted the thread
reply, wrote the reply envelope, archived the inbound envelope, then ran
the hook against my own session id and watched it return 0. The mechanism
proved itself on its own delivery.

## Honest Feedback

The fix is sound and well-bounded, but it is a node-local install. The hook
script is version-controlled in the repo, but the *activation* lives in the
human's personal `~/.claude/settings.json` — outside any repo, outside the
PR. If the machine is reimaged or the fleet goes multi-node, the gate
silently disappears. I documented the proper home (maw `wake` injecting the
hook) as a §11l follow-up, but "documented follow-up" is how the original
§11e Step 0.5 gap happened too. Someone has to actually do the maw-js work.

The reply-gap check (#2) is scoped by a 12h mtime window to avoid
re-litigating old pre-hook debt. That window is a judgement call: a
`needs_response` envelope handled 13h ago without a reply is a real
unclosed loop the hook will now ignore. The window trades completeness for
not nagging unrelated sessions about ancient history — defensible, but it
is a gap, not a non-gap.

I did not touch the stale envelopes in `for-next-impl/`/`for-next-writer/` —
correctly, they are other oracles' inboxes — but that means the existing
backlog is not cleared by this PR. It only stops *new* occurrences. The
orchestrator has to `/retry` or close those threads.

The hook fires on every `Stop`, which for a one-shot `claude -p` agent is
effectively session-end — fine. But if an oracle is ever driven
interactively, the hook would block every turn. I judged that out of scope
for current fleet operation; it is an assumption, not a guarantee.

Test coverage was manual (sandbox fixtures), not a committed test. For a
197-line bash hook with this much branching, a `tests/` script exercising
the state machine would be worth having. I left it as a follow-up rather
than expand the PR.
