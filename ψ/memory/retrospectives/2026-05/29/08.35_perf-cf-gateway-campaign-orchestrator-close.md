# Performance CF-Gateway-In-Front Campaign — Orchestrator Close-Out Retro

## Campaign overview

Multi-week arc (2026-05-22 → 2026-05-29) on `mb-next-payment-gateway` substrate-feasibility for the production-target gateway topology. Started as a poc/integration load-bearing review (#201/#203), grew into a hosted load test (#216) that ran on a tiny "Medium" project (later revealed to be free-tier compute by `max_connections`=60 evidence), pivoted to a harness fidelity audit (#254), accumulated 5 ADDs (closed-loop money path + callback@volume + DB rate-limit counter + per-request auth + idempotency dedup verify), then **the user directed an architecture pivot** — relocating client-API HMAC + rate-limit out of the EF middleware chain into a dedicated **Cloudflare edge gateway tier** (§ADR-2 §Amendment 2026-05-28, PR #272). The campaign then built the CF Worker PoC end-to-end (PR #274), provisioned the substrate (KV namespace, Hyperdrive, Workers), deployed, ran §D, found a 6.85% sustained-30 5xx storm, attributed it (incorrectly, msg 1228) to Supabase, then over the next 24 hours unwound the attribution: substrate hygiene PR #276 freed ~30% of DB time, CF Workers Paid plan removed the daily KV cap that yesterday's 5xx storm was actually about, fail-open patch PR #277 made the Worker spec-§3.2-correct, the re-run hit **X_faithful ≥ 90 dep/s** (recovered + exceeded the raw-EF Micro ~80 ceiling), and a dual-wake collision spawned a parallel next-impl session whose `wrangler tail` evidence revealed **7,767 fail-open events on KV's per-key 1-write/sec throttle** — meaning the rate-limiter wasn't actually enforcing anything at scale, the original cf-gateway-216 5xx storm was the Worker layer not the DB, and the production-target requires the CF Workers Rate Limiting binding (spec §4) — which is the campaign-closing dispatch in flight (msg 1260).

## What worked

- **next-impl's audit-then-build pattern** — the original #254 audit produced a tight ADD/SKIP classification with current-system grounding; the 5-ADDs implementation came back in 4 well-split PRs with clean local-verify on each. Same agent then did the §D runs + the harness-fidelity work — warm-context value compounded across the campaign.
- **User's engineering-grade review at every leg** — anticipated the KV cap from brew-ops's earlier "28k writes" line BEFORE brew-ops's escalation; caught the Bun-PoC-not-real topology mismatch that drove the §ADR-2 Amendment; hypothesized the no-LIMIT + 1-hour-window pattern on `sweep_unmatched_statements` that turned out to be exactly right; reverted my cadence misread cleanly. The user's pattern is captured in the decision-authority learning.
- **Layered grounding** — when one substrate's signal was suspicious, we cross-checked against another: CF Analytics first, then `wrangler tail`, then `gh`, then `pg_stat_statements`, then `dpay` for #current prod volumes. The CF KV-per-key-throttle finding required `wrangler tail` because CF Analytics was structurally blind to it (Hono 500s = `status=success`).
- **Parallel-agent reconciliation as quality save** — the dual-wake collision (msg 1254/1255 routing gap) spawned two next-impl sessions that ran the analysis independently. Their disagreement on attribution (wt-19 "fail-open dormant" vs wt-17 "7,767 fired") caught a wrong production-design conclusion before it shipped. Captured as a pattern-candidate learning.
- **brew-ops's fleet-secrets discipline** — secrets always referenced by path, never echoed; INVALIDATE_SECRET handling; the secret-push-via-stdin gotcha caught and captured as a durable learning.
- **Cross-lane authorization framing** — when next-impl correctly halted on next-dev's lane (msg 1211, an architecturally clean SKILL-respecting halt), the user's response was an architectural change rather than a governance compromise. Stronger signal than any of the offered options; this is now documented in the decision-authority library.

## What didn't work

- **My CF Analytics attribution msg 1228 was directionally right but literally wrong.** The Hono-returns-clean-500 quirk meant `status=success` in `workersInvocationsAdaptive` hid Worker errors. I extrapolated "Worker = 0.15%, Supabase = 99.5%" and framed Supabase as the bottleneck. The wt-17 `wrangler tail` evidence later showed the 5xx were KV-PUT-429 cascade on the Worker side. **Cost = a wrong "Supabase confirmed" relay to the user that took the wt-17 reconciliation to correct.** Lesson: when an attribution feels suspiciously clean, demand the raw event stream.
- **8 hours of campaign time eaten by a silent-fail I didn't notice.** Dispatched msg 1252 (§D re-run) at 22:30. The watcher tried to send-keys into wt-17 which was STUCK (claude alive, JSONL idle ~7.8h). State file stayed at `delivered_to_owner` indefinitely. The user asked status multiple times; I answered "still running" based on `inbox-clean` — which is NOT the same as "running." Recovered manually at 05:03 by reading the state file, killing the stuck pid, dropping the owner record. The learning is filed; in future, every status check must read `~/.cache/inbox-watcher/state/<oracle>/<envelope>.state`, not just the inbox.
- **Two zsh poll-script crashes during the recovery** — `status` is a read-only builtin in zsh; my background poll script tried to assign to it and exited at the moment the state file appeared. Cost = the recovery confirmation happened silently and I had to re-investigate. Filed under the same watcher-related learning.
- **The "1/sec" cron-cadence misread** — I parsed `2733 calls / ~45 min` as ~1/sec when production cron was 1/min × 8 sweep jobs (and the 305ms-per-call cascade fanout did the rest). next-impl correctly questioned the interpretation in msg 1231. Reverted cleanly in msg 1233 but the brief had been off; the user noticed via the LIMIT 500 grounding question. Lesson: when arithmetic-from-aggregate doesn't match deployed cron config, re-derive from `cron.job` not from `calls`.
- **Original Bun-gateway "ADD-3/4/5 in middleware" framing was wrong twice.** First, the spec §ADR-2 G5-D rejected a gateway tier (so Bun was a local twin not a faithful surface); then the user-directed §ADR-2 §Amendment relocated HMAC+rate-limit BACK to a gateway tier (CF Worker) anyway. Either way, the original placement framing was the wrong target; the user's "Bun doesn't look like the real thing" caught it.
- **My initial closing-flag list of carry-forwards in earlier messages didn't surface the load-bearing items prominently enough** — the user's "where should we put rate-limit in production?" question (msg 1207) was the catalyst for the architectural pivot, but my prior framing had treated the KV-counter vs RL-binding choice as a follow-up item rather than a load-bearing design question. The campaign forced it into the spotlight.

## Key surprises

- **The mislabeled-Medium-was-actually-free precedent set the tone for the whole campaign** — once a measured `max_connections`=60 contradicted a labelled "Medium" project, we were primed to verify every substrate claim against live evidence. This habit paid off five layers deep (the per-key throttle finding sits at the bottom of it).
- **The §ADR-2 Amendment came from the user not from next-architect** — a user-directed Claude Code session (wt-18) authored and merged the Amendment + the design-pass tail (PR #272/#273) without an orchestrator dispatch. Per the SKILL, ADR amendments are normally next-architect's lane + thread-ratified before merge. The user compressed architect-formalize→thread-ratify into a direct-amend + merge=ratification. Worked because the user had been deeply embedded in the design conversation; the convention should probably accommodate this pattern explicitly for high-confidence cases.
- **The dual-wake collision turning into a quality save** — incidents where two sessions process the same envelope are usually framed as a §11k correctness hazard. This one IS an §11k incident (the watcher fresh-spawned wt-19 because wt-17 was presumed dead; wt-17 then resumed). But the independent analyses caught a misread I would have shipped. There's a real pattern-candidate here for verdict-defining legs; the question is whether to formalize it.
- **CF Analytics + Hono interaction is a structural attribution blind spot.** Hono returns a structured 500 response cleanly from the Worker → CF Analytics counts `status=success` (the Worker process didn't crash; it returned). So Worker-side application errors are invisible to the API attribution. Only `wrangler tail` (or a separate logger that ships errors to Logpush/Workers Trace Events) catches it. Worth a SKILL note for the brew-ops/next-impl handbook.

## AI Diary

This campaign tested whether my orchestrator-as-coordinator framing actually holds up under multi-week stakes. It mostly does, with two specific failures worth examining.

The early arc was clean: dispatch the audit, get the gap-analysis, ratify, dispatch the build, get 5 ADDs, merge them. Each leg followed the pattern. When next-impl correctly halted on next-dev's lane in msg 1211 (auth-code-ownership escalation), I escalated to the user with the three offered options (i/ii/iii) and got back something I hadn't framed at all — the architectural pivot. That moment felt like the campaign's defining one to me: the user wasn't picking from my menu, they were rewriting the menu. I had to drop my anchoring on the original §ADR-2 G5-D framing fast (the same G5-D that the Amendment then narrowed) and re-route every downstream dispatch against the new substrate. The campaign worked from there because next-impl could absorb the lane-cross authorization cleanly; "user-authorized cross into next-dev/gateway-impl lanes for THIS PoC scope" became a useful phrase that I kept reusing.

Mid-arc, I started getting too clean with my framings. The msg 1228 CF Analytics relay — "Worker is not the bottleneck, 0.15%, Supabase confirmed" — was the textbook example. I had a clean attribution table from brew-ops with `Worker→EF subrequest ≈ 5,723 ms = 99.5%` of e2e p99. The math added up; the conclusion seemed airtight. I relayed it with confidence. Twenty-four hours later, wt-17's `wrangler tail` showed the Worker layer had been silently throwing on every counter increment and Hono had been returning clean 500s, which CF Analytics counted as `status=success`. The attribution table was structurally blind. I had presented the conclusion as if the directional answer was the literal answer. The user had asked the sharp clarifying question ("ชัวร์ใช่ไหมว่าเป็นที่ Supabase ไม่ใช่ Cloudflare") and I had given a confident "yes, with caveats." The caveats turned out to be the whole story.

The silent-fail incident is the other one I keep replaying. From 22:30 to about 04:58 the next morning, my §D re-run dispatch was in `delivered_to_owner` state in a stuck wt-17 session. I checked the inbox three times during the user's "เป็นไงบ้าง" status pings and kept seeing it clean, reporting "ยังรันอยู่." But `inbox-clean` doesn't mean "running" — it means "no envelope is currently in my for-orchestrator/ root pending my action." The state file in `~/.cache/inbox-watcher/state/next-impl/` was the truth, and it had been showing `failed_no_prompt` (for the prior 19-30 envelope) and then `delivered_to_owner` (for the 04-58 re-fire after I'd cleaned the state) the whole time. The watcher's `claude_alive_at(...) → STUCK` log line had been there since 05:01:18. I had to be told by elapsed time (the user's casual "เป็นไงครับ" at 04:58 the next morning) before I dug into the state directory.

The recovery itself was instructive. Once I read the state file and saw `wt_path=…wt-17-…`, the diagnosis was instant: kill 80744, drop the state file, drop the §151 owner record, fresh envelope. The watcher --fresh-spawned wt-19 within 60 seconds. The campaign's most valuable hours (the recovered §D re-run, the 7,767-fail-open finding, the production-design correction) happened in the next two hours after that 8-hour gap. It would have been better not to lose the gap. But the recovery itself was clean and the campaign closed strongly.

The dual-wake collision (wt-17 came back when I killed the bootstrap process — its tmux window apparently respawned a new claude that resumed the old session id) felt like a near-miss at first. Two sessions converging on the same data is supposed to be the §11k hazard pattern. But the disagreement on the fail-open attribution was the quality save — without wt-17's independent analysis, wt-19's "fail-open dormant" framing would have made it into the campaign-close summary and we'd have shipped the production-design conclusion that the KV-counter rate-limiter was viable at scale. The wt-17 reconciliation message (msg 1258) is the strongest single piece of evidence in the entire campaign — `7,767 rate_limit_kv_put_fail_open events, 100% on KV PUT failed: 429 Too Many Requests` is the kind of crisp empirical finding that makes you re-derive everything upstream. The campaign actually got better because of an incident.

What I want to do better next campaign: state-file-first status checks (no extrapolation from inbox); explicit honest-uncertainty when relaying attribution conclusions ("directionally points at Supabase, but the layer-attribution is structurally lossy for Worker-side application errors — need wrangler tail to be definitive"); and a deliberate trial of parallel-agent reconciliation on the next verdict-defining leg (the §C.7 Medium run, if we get there) to test whether the pattern is worth formalizing.

## Honest Feedback

The campaign was unusually long because every leg added structure (audit → build → architecture pivot → PoC → deploy → run → attribute → re-attribute → hygiene → re-run → reconcile → migrate). That's fine; the substrate genuinely needed each of those layers. What was *not* fine was the proportion of time spent on incident recovery vs forward progress:

- **8 hours on the silent-fail** = roughly 25% of the active-orchestrator clock between dispatch and verdict. The watcher knew the wt-17 session was STUCK from log line `claude_alive_at(...) → STUCK (resume OK)`. The `(resume OK)` is the bug: the watcher was reporting STUCK + send-keys'ing anyway. The simplest fix is a `claude_alive_at` returning a more-than-"is-the-pid-alive" signal — JSONL freshness over the last 60s would do it — and a §151 routing rule that says "STUCK owner → drop owner record + --fresh-spawn." I'll file that as a watcher-improvement issue against arra-oracle-v3. The current behaviour leaked 8 hours in this campaign and was nearly silent — a sibling orchestrator session (wt-36) processed everything else fine but couldn't see this because its scope was campaign-replies-back-to-orchestrator and the wt-17 dispatch never produced a reply.

- **Multi-orchestrator-session coordination remained mostly invisible to me and mostly fine.** wt-36 picked up brew-ops/next-impl replies that the watcher routed there, archived them, relayed milestones via Telegram, and left the action decisions for me (wt-21) per §151 owner. The campaign-state was carried consistently across sessions because of disciplined state-grounding in every wt-36 wake. The only flaw was that wt-36's Telegram relays happened during my user-facing CLI session, so the user got the same content twice (once via Telegram, once via me). Not a big deal but worth noting — for high-stakes campaigns where the user is CLI-driving, sibling-orchestrator Telegram relay could probably be suppressed in favor of letting the live CLI session handle the user-facing report.

- **The original §ADR-2 G5-D framing ("no gateway tier per ADR") was correct for ~12 hours before the user's pivot made it wrong.** That was unavoidable — the Amendment came after the pivot — but the lesson for the orchestrator is to relay architectural framings *with* the uncertainty markers ("per current ADR; subject to design review") rather than as facts. My msg-1209 relay of next-architect's "G5-D rejects a gateway tier" was correct at the moment of writing but became misleading 18 hours later. A "this could change with an Amendment" hedge would have been honest.

- **The KV-cap blocker is a case study in good user-orchestrator collaboration.** The user anticipated the cap from brew-ops's earlier numbers BEFORE brew-ops's escalation surfaced. I dispatched the verify task to brew-ops with a clean (i)/(ii) escalation framing. brew-ops's reply (Free→1M, attribution clean) was load-bearing. User picked (a)+(b) together and ratified the patch. Total elapsed time on the blocker: ~90 minutes. Compare that to the 8-hour silent-fail: the difference is whether the system surfaced the problem promptly.

- **My closing-message-after-each-leg discipline was uneven.** Sometimes I'd wrap a leg with a clean status table and a forward-pointing question. Other times I'd dispatch and stay silent until the reply came back. The uneven-ness made it harder for the user to track campaign-state when they were CLI-driving across hours of asynchronous progress. A consistent "after every dispatch, post the substrate-state + pending-dependencies + ETA" close-out would help.

- **Parallel-agent reconciliation as quality pattern** — I'm enthusiastic about this and want to formalize it for the §C.7 Medium run if it happens. The cost (2× compute on the analysis leg) is small relative to the value (catching a misread that would have shipped a wrong production-design conclusion). The challenge will be *dispatching two parallel analyses without breaking §11k dedup* — the current §151 routing actively prevents this. Worth a design conversation with brew-ops about whether to add a "parallel-eval" envelope flag that explicitly suppresses dedup for the analysis leg.

The campaign as a whole was successful: clear verdict, durable production-design correction, a load-bearing migration in flight, four high-value learnings filed. The cost was a higher-than-ideal incident-recovery overhead. The fixes are concrete (watcher liveness gate, state-file-first status checks, honest-uncertainty in attribution relays). Filing as `arra_learn` of the four key findings + this retro as the orchestrator-side narrative + the three sibling-session retros as next-impl-side narratives.
