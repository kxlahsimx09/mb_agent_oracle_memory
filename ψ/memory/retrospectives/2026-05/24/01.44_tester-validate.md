## What was surprising

- **The naming trap that nearly mis-scoped the idempotency commit.** Older W1
  passes (twenty-second and earlier) wrote "no test exercises the client-facing
  API-key endpoints (`/api/v1/deposit-request`, `/api/v1/payout-request`)" — true
  for the *rate-limit* helpers, but the create handlers `DepositRequestController.CreateDeposit`
  / `PayoutRequestController.CreatePayout` are mounted at **`/api/v1/deposit/create`
  + `/api/v1/payout/create`**, which 29+26 test calls DO hit. The controller name
  ("…RequestController") and the route path ("/create") diverge. If I had trusted
  the old "0 hits on deposit-request" note, I'd have called #392 NEUTRAL-by-no-test
  and missed that it gates the entire create surface. The twenty-sixth pass caught
  this correctly; the lesson is to re-derive the route→handler map per pass, not
  inherit a string-grep conclusion.

- **#460 has two upload handlers, only one changed.** `UploadSlipAdmin` (admin,
  `/deposits/:id/upload-slip`) lost its synchronous Thunder verify; the client
  `UploadSlip` (`/deposit/:txnId/upload-slip`) — the one `test-deposit-upload-slip.sh`
  actually calls — was untouched. Easy to mis-classify if you only read the diff's
  function name and not which handler the test exercises.

- **#454 "Floor deposit amount" bundled a large bot-host-locator addition**
  (`botHostLocator.go` new, `botOpsService.go`, `SystemBankController.go`). The PR
  title hid the real surface area. Worth remembering that squash subjects under-sell
  the diff.

- **`b7040eb` #471 is a merge commit** — it adds `ClientRequestLogController.go`
  but is simplified out of `git log <range> -- <paths>`. The pathspec git-log under-counts
  merge-commit-introduced surfaces; I only caught it via the `git log` ALL view +
  `git show --stat` returning empty (the merge-commit tell).

## Recurring patterns / candidate refinements

- **Same-range hardening + test-fix nets to NEUTRAL.** #392 (mandatory header) +
  #473 (test patched to send it) is the cleanest example yet of why a single
  *consolidated* validator pass over the whole merged-baseline span is right, and
  why sibling validate PRs that each advance the shared index collide (thread #220's
  own closing note). Recommend the watcher / process adopt single-validator-pass
  discipline rather than amend-chains — exactly what this pass demonstrates.

- **Workflow-1 has no KNOWN-WONTFIX status in its taxonomy.** #475 introduced it
  (FIFO same-amount tests: VALID-status but excluded from regression, full-dir FAIL
  expected). The matrix currently expresses it as "status=VALID + a `**KNOWN-WONTFIX**`
  marker in the root-cause column." That works but is a slight taxonomy gap — a future
  reader might double-count or mis-bucket. Candidate refinement (not applied): add
  KNOWN-WONTFIX as a first-class status value in the SKILL §"Validation taxonomy" and
  the Summary line, with the explicit "excluded from regression-suite.txt; full-dir
  FAIL is expected" semantics. Flagging, not actioning.
