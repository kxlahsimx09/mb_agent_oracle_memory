## The fraud-confirmation arc (the biggest single yield)

The G3 line bent away from "port a retroactive scan" through five rounds of
data-driven sharpening — the structure became a reusable forensic template:

1. **L1** — cell-level matching-payer heuristic, 47% of 4,584 collision
   cells = ~534K–1.5M THB risk exposure.
2. **L2** — backing-statement check, 20.8% PROBABLE (26/125 sample) =
   ~250–350K THB extrapolated slip-level loss.
3. **L3** — Thunder-OCR `transRef` duplication, 12 deposits across the
   entire 18,141-row slip-paid pool = **definitive slip-reuse**.
4. **L4** — per-deposit forensic on the 12: 6 confirmed unrefunded damage
   cases = **7,749.30 THB confirmed loss** (revised up from per-pair
   conservative 5,590.70).
5. **Code-verify** — confirmed mobiz scan is structurally inert
   (`sus.PaidAt` zero-value bug), Thunder pre-computed flags are pure
   dead-data (grep returns 0 reads in any deposit handler), and the only
   real check (slip-upload transRef-duplicate) has a silent admin-role
   bypass.

That progression — L1→L2→L3→L4 + code-verify — converted "47% likely" into
a defensible "12 PROVEN / 6 confirmed / 7,749 THB" + an actionable redesign
direction (V1.5 transRef-check at admin-approve, preventive, 0 false
positives). The G3 PR #189 (port the retroactive scan) was closed
mid-arc because the data made the port useless: all 6 damage cases happened
pre-statement; retroactive fires after the wallet was already credited.

Five learnings filed: production-zero-mis-tune, forensic-confidence-ladder,
semantic-fraud-signal, drop-broken-source, multi-layer-enforcement-gap.

## Honest Feedback

**What worked.**

- The **forensic confidence ladder** progression — L1 likely heuristic → L2
  probable from data-join → L3 proven via semantic-unique signal → L4
  confirmed unrefunded damage. Each level a different evidence type, each
  removing a different false-positive class. The user pulled the levels out
  of me by asking sharp follow-ups; the orchestrator role merely translated
  each into the right pg-writer query. The template generalises; the
  learning is filed.
- **Verify-before-act** caught real defects multiple times — the mobiz
  matchDepositKTB partial guard (#176 pg-tester), the silent-mis-tune of
  the retroactive scan (G3 deep dive), the mobiz code-level gap where
  Thunder flags are written-but-never-read. Without verify, the orchestrator
  would have ported broken designs faithfully and called it done.
- **Drop-and-redesign over port-and-improve** — when the verify-before-act
  showed PR #189's source mechanism was inert in production, dropping the
  PR and authoring V1.5 from the production data was clearly the right
  move. The retro from the last session had a verify-before-remediate
  discipline; this session extended it: verify-before-port-too.
- **Cross-role campaign rhythm** — pg-writer find → next-architect amend →
  next-writer doc-fix → user merge worked cleanly for G2/G4/G-6 and the
  recovery patterns. The §FA1-precedent (RATIFICATION_PENDING marker, flip
  by next-architect, doc-fix follows) generalised to G4 and G-6 without
  drift.
- **Verify-the-watcher discipline (when applied)** — when I did check the
  watcher log, it surfaced everything I needed. The 14:13 ALERT was visible
  from 14:17 onwards; the ownership transfer was logged at 10:50:10
  explicitly with reason. The harness tells the truth; my job is to read
  the right channels.

**What didn't.**

- **The 14:13 stall report drift.** Already discussed. The lesson is
  explicit in the last retro and I still missed it. Action: when a
  dispatch goes out and the expected reply window passes silently, the
  orchestrator should not be reporting "in flight" to the user without
  having checked the watcher log within that window. "Trust but verify"
  → for delivery, the verification source is the watcher log, not the
  prompt stream.
- **Ownership-transfer blind spot.** I should have noticed my session was
  no longer the routing target for #175 replies as soon as the first reply
  went to handled/ without me getting a prompt. The user noticed by way of
  "ตอนนี้ผมต้องถามคุณถึง progress ตลอดถูกไหม" — and they were correct.
  Action: after any significant gap in receiving replies, poll the watcher
  log + handled/ proactively, even if no Stop hook fires.
- **Hook-format fumbles.** Two iterations to get the reply-envelope
  location right. Acceptable cost (it's an obscure protocol detail and the
  hook fires three times before giving up, giving room to learn) but
  worth flagging — the lesson is now an Oracle learning, future sessions
  shouldn't repeat it.
- **Sibling-session sprawl accepted.** My dispatches kept stamping a dead
  worktree path. Better fix would have been to start a fresh orchestrator
  session via maw-wake and use arra_handoff to forward context. I chose
  context preservation over fleet hygiene; defensible but not free.

**For next time.**

- **Poll the watcher log proactively** on every "expected reply" window.
  Don't wait for the harness to surface the failure mode that exists
  precisely at the harness's wake layer.
- **After ownership transfer is observed, accept and adapt** — don't try
  to migrate ownership back unless there's a clean path. Grep handled/
  becomes the read-path for the affected thread; that's fine.
- **Forensic ladder template** — start any fraud / coverage-gap analysis
  with the L1→L4 frame in mind. Don't claim L3 strength from L1 evidence.
- **When porting from a reference system, verify the reference works** —
  not just "the code exists" but "the code fires in production data." If
  zero hits over a meaningful window + non-trivial suspect population, the
  reference is broken; redesign rather than translate.
- **Multi-layer enforcement audit** — for any deployed check, audit all
  three layers: read+act, bypass path, audit trail. "The check exists in
  code" is not the same as "the check enforces in production."
