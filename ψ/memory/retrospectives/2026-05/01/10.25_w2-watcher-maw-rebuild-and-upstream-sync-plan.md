# Why this happened (root cause chain)

The visible failure was `bash: maw: command not found`. The actual chain has three layers, only one of which was today's regression:

1. **PATH drift (today's regression).** Watcher launched 04-30 13:59 with `maw` on PATH. Sometime after 14:48 (the last successful wake), some shell-init drift dropped maw's directory from PATH. Background processes don't re-read shell rc files, so PATH stayed broken until the process restarted. Hypothesis: nightly `bun update` or a manual `bun add -g` removed the `~/.bun/bin/maw` symlink — upstream issue **#531** documents this exact recurring sweep with no confirmed root cause.
2. **Stale `dist/maw` binary (long-standing, masked).** Built Apr 19 13:19 against a pre-#543 source — `runtimeSdkVersion()` was still using fs-read of `packages/sdk/package.json`, which fails post-bundle because `import.meta.dir` doesn't resolve in a flattened binary. Fallback: `"0.0.0"`. Plugin manifests across the fleet require `^1.0.0`. Every plugin failed the semver gate from the moment plugin manifests bumped to `^1.0.0`, not from today.
3. **Watcher silent-loop discipline.** `pending_wake_ts` (silent-fail Telegram detector) only arms when `maw wake` exits 0. With exit 127 (command not found) every cycle, the detector never armed → no Telegram alert → 17h of "wakes triggering, nothing happening" with no operator visibility. The detector is fundamentally an *output-presence* check, not an *invocation-success* check, and that gap is the next piece worth fixing (flagged as follow-up in PR #31, not in scope).

The PATH fix unmasked the SDK-gate fix. The silent-fail-detector blind spot meant nobody noticed for 17h. **Three bugs, not one — and they all need different fixes.**

## Why this is safer than first scan suggested

First instinct ("merge will delete 62 plugins, breaking everything") is **wrong** for two reasons:

1. **The plugin folders are dead source.** Upstream's lean-core extraction moved plugins from `src/commands/plugins/<name>/` (in-tree source) to external packages, installable via `maw plugin install <name>`. After merge, plugin behavior is restored by `maw plugin install standard` (or other bundles). The 62 deleted folders are unmaintained dead code in our branch — we don't actually want them.
2. **All 3 fork PRs land in `shared`/`core`/`api` — not `plugins/`.** Every file the PRs touch (`src/commands/shared/wake-*.ts`, `src/core/fleet/*.ts`, `src/api/*.ts`, `src/config/command.ts`) **exists in upstream**. So conflicts are line-level inside known files, not modify/delete catastrophes. Tractable.

The scary number (479 files) is mostly automatic — git will delete the 62 plugin folders without conflict because the local side hasn't modified them since divergence.

## Real conflict surface

`git merge-tree` dry-run flags **1 file** with content conflict: `src/api/claude-fleet.ts` (PR #1 added regression-job detection; upstream evolved the same file). Manual resolve.

Realistic conflict candidates beyond that, all small:
- `src/commands/shared/wake-cmd.ts` — PR #3 fix vs upstream's wake refactors. Both touched the same area.
- `src/commands/shared/wake-session.ts` — PR #2's `.agent` symlink mirror code.
- `src/config/command.ts` — PR #3's `--fresh` / `--prompt` flag plumbing.
- `src/core/fleet/claude-sessions.ts` — PR #1's role inference and CLI claude detection.

Estimate: 5 files of manual conflict resolution, ~30-60 min of careful diffing.

## Steps (when we decide to do it)

### Phase 1 — prep (~15 min, low risk)

1. **Backup the working binary.** `cp ~/Code/.../maw-js/dist/maw ~/Code/.../maw-js/dist/maw.pre-merge-2026-05-01`. Today's rebuild is the known-good escape hatch.
2. **Tag the current branch tip.** `git -C ~/Code/.../maw-js tag fork-pre-upstream-sync-2026-05-01 feat/all-prs-rebased`. Cheap rollback if the merge goes sideways.
3. **Inventory which plugins the watcher actually invokes.** Today: just `wake` (used by `maw wake $role …`). Tomorrow: maybe `peek`, `hey`, `ls`. Make a short list now so we know which `maw plugin install <bundle>` calls are needed post-merge.

### Phase 2 — branch + merge (~30-60 min, conflicts expected)

4. **Branch off, don't merge into the existing branch.** `git checkout -b feat/upstream-sync-2026-05 feat/all-prs-rebased`. Keeps `feat/all-prs-rebased` as the rollback target.
5. **Merge upstream.** `git merge origin/main`. Expect ~5 conflicting files (see surface above). Resolve each by reading both sides — the fork side has the *new* behavior we want to keep, the upstream side has the *new structure* we're migrating into. Apply fork behavior on top of upstream structure.
6. **Run the test suite.** `bun test`. Pre-existing baseline failures (~21 tests as of Apr 30 PR #3) are acceptable; new failures need investigation.
7. **Build.** `bun run build`. Confirm `loaded N plugins (N symlink)` shows expected count and `maw wake --help` registers.

### Phase 3 — plugin install reconciliation (~15-30 min)

8. **Install the bundles for plugins we actually use.** Per upstream commit `91958ee6`, install commands include `maw plugin install standard` and tier bundles. Pick whichever covers `wake`, `hey`, `ls`, `peek` at minimum.
9. **Smoke-test via `maw ls` and `maw wake --help`.** Both must return success and show the expected commands.
10. **Verify watcher still finds maw.** `bash scripts/w2-watcher.sh status` from the arra-oracle-v3 main worktree — should print "running" and the role state files. Watcher does not need a restart unless the binary path changed (which it shouldn't — we kept building to `dist/maw`).

### Phase 4 — ship (~15 min)

11. **Push the new branch to fork.** `git push -u fork feat/upstream-sync-2026-05`. Open PR fork→fork (`feat/upstream-sync-2026-05` → `feat/all-prs-rebased`) for self-review of the merge resolution. Per .agent memory: PRs in Soul-Brews-Studio/* target the fork.
12. **Merge the PR.** Now `feat/all-prs-rebased` has the upstream sync. `feat/upstream-sync-2026-05` can be deleted.
13. **Optional: rename the branch.** "all-prs-rebased" stops being accurate after a merge (history isn't rebased anymore). `feat/oracle-fleet-and-wake-fixes` would describe the actual content. Defer unless someone is confused by the name.

## Risks worth re-checking before doing the merge

- **PR #3 may already be upstream by the time we sync.** I haven't checked whether the user opened PR #3 against upstream after merging into the fork. If yes, the wake-silent-fail conflict goes away — pure no-op merge for that file. Worth a `gh pr list --repo Soul-Brews-Studio/maw-js --search "wake silent-fail"` before starting Phase 2.
- **Plugin install requires network.** The registry at `maw.soulbrews.studio/registry.json` must be reachable. Offline = no plugins.
- **Plugins.lock pinning.** Upstream uses `plugins.lock` for sha256 pinning of installed plugin tarballs. Decide whether we want pinning (more secure, more friction on upgrades) or unpinned (smoother). Default: pin the bundles we depend on.
- **`dist/` rebuild discipline.** If post-merge `dist/maw` ends up older than source again (someone forgets to rebuild), we'll repeat today's incident. A pre-commit or pre-push hook that fails if `src/cli.ts mtime > dist/maw mtime` would close that loop. Not in scope for the merge itself.

# Honest Feedback

**What worked.** Two things stand out:

1. The two-stage debug — fix the outer layer (PATH), let it unmask the next layer (SDK gate), fix that — is the right shape for problems that look monolithic from the outside. I almost tried to fix both at once and would have shipped a bigger PR with worse boundaries. Sticking to single-concern PRs (just MAW_BIN resolution in PR #31, defer silent-fail-detector improvement) kept the blast radius small and the fix auditable.
2. Reading code comments before testing is underrated. The `registry-helpers.ts:11-13` comment told me the answer to "why is SDK 0.0.0" before I'd run a single grep. Whoever wrote that comment saved me probably 30 minutes of source spelunking. **Lesson: when something says `// previous approach broke because X — see #N`, that's the answer, not background noise.**

**What didn't.** Three things:

1. **Silent-fail blind spot.** The watcher fired 599 wakes through a ~17h window with zero operator-visible signal. The silent-fail Telegram detector exists *specifically* for this case and didn't fire because `pending_wake_ts` only arms on exit-0. Today's PR didn't fix that — I deferred it to keep PR #31 small. I think that was right, but the gap should not stay open long; it's the difference between "watcher broke last night, fixed it this morning" and "watcher broke last week, only noticed today because someone happened to look".
2. **I didn't ask about today's specific log files until late.** When the user reported the PATH issue, I jumped to scripts and fix logic. Looking at `~/w2-watcher.stdout.log` (where the timestamped log lines actually go) earlier would have shown the trigger pattern + retry timing immediately. Two separate log files (`stdout.log` for `log()` calls, `watcher.log` for maw stderr) was confusing — I should have surfaced that split as a "quick observation, also worth fixing" rather than letting the user discover it themselves.
3. **The retro almost didn't get written.** The user explicitly asked for it. I almost defaulted to inline summary in chat. The reason retros are mandatory in this project's workflow is *exactly* because the upstream-sync analysis is the kind of work that gets re-derived from scratch every time it isn't written down. Documenting Phase 1-4 in this retro is probably worth more than the actual fix it accompanies.
