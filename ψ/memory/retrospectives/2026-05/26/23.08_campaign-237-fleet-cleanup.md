## Honest Feedback
The §151 sticky-ownership + per-(oracle,wake-key) model worked exactly as designed here — it's *why* wt-4 was safely distinguishable from a true orphan. But it also exposed a real gap in the orchestrator's situational awareness: wt-20 genuinely could not see wt-22's campaign in its own owner records, so it nearly ordered the deletion of a sibling's live worktree. The "ADJUDICATE, don't guess" instruction is the only thing that saved it — which means the safety currently rides on the orchestrator remembering to flag ambiguous cases AND the brew-ops handler bothering to check owner records + thread status. That's two human-discipline links in a chain that could be a tooling check. A `maw oracle retire <worktree>` (or an inbox-watcher GC guard) that refuses to retire any worktree referenced by a non-closed thread's `.owner` file would make this class of mistake structurally impossible, the same way `git worktree remove` without `--force` makes dirty-removal impossible. I filed the adjudication rule as a learning, but a learning is a claim; the gate would be truth. Worth proposing to the human.

## Lessons Learned
- **Pattern**: Before retiring any worktree, `grep -rl <worktree-id> ~/.cache/inbox-watcher/sessions/` → `arra_thread_read <owning-thread>` → only `status=closed` is retire-eligible. base-SHA/no-commits is normal for review/ratify/discuss tasks and is NOT orphan evidence.
- **Pattern**: Two concurrent orchestrator sessions can own separate campaigns; absence from ONE orchestrator's owner records ≠ orphan (§151 ownership spans sessions, keyed per oracle+wake-key).
- **Gotcha (tooling)**: this sandbox zsh loses PATH inside `for`/`eval` loops (`git`/`sed`/`basename` → "command not found"); a spurious "FAILED" can mask that the command never ran. Run destructive ops as top-level statements + verify each exit code.
- **Mechanics**: no `maw sleep` verb — use `tmux kill-window`/`maw kill`; target windows by NAME (renumber-windows shifts indices); `git worktree remove` without `--force` IS the dirty-gate; cache eviction is plain `rm` of ephemeral `~/.cache` files (no P-001 concern).
