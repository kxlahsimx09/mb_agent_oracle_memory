## AI Diary

This campaign was a marathon run as ~15 short sessions, and the thing that made it work was the **sequential cadence** the orchestrator and I converged on after the early misstep. My first three PRs (#245/#247/#248) all branched off the same pre-merge main, and they collided in glossary.md + INDEX.md exactly as I'd predicted — I'd flagged it but still opened all three before any merged. Resolving #247 then #248 against the merged main cost two whole sessions of rebase-and-take-both-hunks. The lesson landed hard: from #249 onward, one PR per pass, branch off the *latest merged* main, pause for the user's merge, repeat. Zero conflicts for the next four epics. The orchestrator made it the explicit rule ("prefer sequential"), and it was the right call — the per-pass round-trip latency was far cheaper than compounding N-way append conflicts.

The most satisfying parts were the data-grounded scoping calls. dpay-finder repeatedly caught divergences between the ADR/Bucket-B prose and production reality: the OTP-relay being bot-side (keyed by acct, no user_id) so it does NOT belong in the Auth epic; the `audit_trail` collection being the 6.6M-row HTTP log, not the action audit (`activity_logs`); settlement status being an int with `waiting_to_review`=3. Each time, verifying the shape before scoping kept a wrong assumption out of the docs. The anti-pattern in the SKILL ("don't claim X without verifying the discriminator") generalized to "don't *scope* an epic without verifying the data."

The A1/A4 refreshes at the end were a good closer because they exercised a different muscle — surgical edits to two 120k/195k-line existing epics rather than greenfield authoring. The discipline there was: grep to the exact story anchor, read just that region, patch precisely, append a revision-log entry, never rewrite. PAYOUT-010 was the one judgment call — "give it its own mechanism" could have meant an edit to PAYOUT-008 or a new story; I chose a new story because it's genuinely a distinct always-on mechanism with its own trigger and failure code, and a dedicated id is more discoverable.

The whole campaign also closed a loop on myself: the per-client rate-limit I flagged as unratified-config in AUTH-006 (PR #247) came back ratified via §ADR-11's A3 amendment and I homed it as CLIENT-002 (PR #253) — a flag I raised early, resolved late, by my own later pass.

## Honest Feedback

- **The sequential-off-merged-main rule should be in the W1 workflow doc.** The single biggest efficiency lever this campaign — and the single biggest time sink before I adopted it — is not written anywhere. workflow-1 Step 9 should say: "if authoring multiple epics in a campaign, branch each off the latest *merged* main and prefer one-PR-per-pass; parallel off-main PRs N-way-conflict on glossary/INDEX/README append regions." Brew-ops handoff candidate. This is the third campaign-scale lesson about shared-file append churn and it's now durable.
- **dpay-finder delegation is the right default and earned its keep every single epic.** Not once did the ADR + pg-writer prose fully match production without a nuance worth catching. Keep leaning on it for scoping, not just citation.
- **The 250-line budget remains fiction and that's fine.** My epics ran 130–365 lines; the existing ones are 120k–195k. "Readable in one sitting, split only when a cluster is independent" is the real rule. (Same note as my P0 retro — still unaddressed in the SKILL.)
- **Cross-cutting-NFR epics (admin-audit, client-api) needed explicit anti-duplication discipline.** Admin-audit and client-api both governed surfaces already specified elsewhere (the individual admin actions; the create endpoints). The right shape was "own the shared invariant, cross-reference the owning stories" — I had to consciously resist re-listing. Worth a SKILL note: when an ADR is "intentionally small / cross-cutting," the epic owns the rule and cross-refs the surfaces; it does not re-author them.
- **The MDX brace-check grep is too naive** — its `-v` filter only skips lines *starting* with a backtick, so it false-positives on every fenced-mermaid or mid-line inline-code brace. I had to fall back to a diff-of-added-lines check to be sure. The reliable check is "diff the added lines for braces, then confirm each is fenced or backticked" — the mermaid parser already covers the fenced ones. Worth replacing the grep recipe in the anti-patterns section.
