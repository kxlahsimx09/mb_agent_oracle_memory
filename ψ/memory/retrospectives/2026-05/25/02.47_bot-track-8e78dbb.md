## Honest Feedback

- The merge-commit-vs-code-commit baseline trap is real and I nearly shipped the
  wrong SHA (`29675b4` merge commit instead of `8e78dbb`). The 6.A spec says
  "merge origin/main" then bump baseline but doesn't explicitly warn that
  `git rev-parse HEAD` after the merge is the merge commit, not the tracked main
  commit. A one-line note in 6.A ("baseline = the main code commit being tracked,
  i.e. `git rev-parse origin/main`, NOT the post-merge HEAD") would prevent this.
  Worth a workflow-spec nudge to brew-ops if it recurs.

- §5.3's mixed-hash citation convention (historical `@old` rows keep flat paths,
  new `@8e78dbb` rows use do/aws paths) is *correct* but reads slightly oddly to
  a human skimming — they see both `scripts/create-bot-aws.sh@96bd212` and
  `scripts/aws/create-bot.sh@8e78dbb` for what is the same file. I added an
  explicit sentence in the AWS intro explaining the rename + why the bullets
  cite the old path. That sentence is load-bearing; without it the doc looks
  internally inconsistent. Future restructures of already-documented surfaces
  should budget for a "the citations below predate the rename" disclaimer.

- The cross-repo check was cheap and conclusive here (deployment ops never
  touches the mobiz contract), but I'm glad the 5th Step-2c trigger (grep sibling
  flow docs) exists — it turned "I'm pretty sure there's no signal" into "I
  grepped 12 docs and there's no signal," which is the difference the DoD asks
  for.
