# W2 cleanup - statement matching current-system verify flags

## Scope

Closed the two live verification flags in `docs/requirements/epic-statement-matching.md`:

- `FLAG[G5 / thread #175]` on date-less statement dedup.
- `FLAG[G1 / thread #175]` on Step-1 `target_account_match` semantics.

No next-system semantic was changed. The pass converted provisional flag comments into source-backed prose after verifying current-system mobiz behavior.

## Evidence

- mobiz `controllers/BotConfigController.go:761-803` guards statement dedup with `transaction_date_bkk > 0`; date-less rows bypass current-system dedup and insert.
- dpay MCP count on 2026-05-25 found zero production `bank_statements` rows with missing, null, or zero `transaction_date_bkk`.
- mobiz `services/transactionMatcher.go:150-225` requires KTB full payer account and applies source-bank filtering when the account prefix resolves.
- mobiz `services/transactionMatcher.go:235-337` requires SCB payer last-4, requires source bank code for non-PromptPay transfer rows, and permits PromptPay last4-only when the statement shape does not expose source bank code.
- No amount-only Step-1 fallback remains in the verified current-system matcher.

## Changes

- Replaced the G5 flag with explicit current-system divergence language: next-system NULL-safe dedup is a defensive consistency rule, not volume-driven migration pressure.
- Replaced the G1 flag with bank-specific Step-1 source-identity requirements for KTB, SCB transfer, and SCB PromptPay.
- Updated `old:code` source lines with the exact verified file ranges and production count evidence.

## Retrospective

The important workflow decision was not to open an architect thread first. The flags explicitly asked for code verification, and the ratified ADR already fixed the next-system behavior. Architect escalation is appropriate only if current-system verification contradicts the ratified semantic, exposes ambiguous intent that would change the requirement, or requires revising the next-system contract.
