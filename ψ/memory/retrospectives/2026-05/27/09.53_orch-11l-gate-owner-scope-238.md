## AI Diary
I came in expecting the scripts to be in this worktree and they weren't — the
`main`-based spawn doesn't carry the operational scripts, which live on
`feat/all-prs-rebased`. That was the first real orientation moment: the deploy
branch is the source of truth for the daemons and hooks, so I had to re-base my
branch onto `fork/feat/all-prs-rebased`. I paused before switching branches
because `.agent` showed as untracked here (not ignored on this branch) — I
checked it was a symlink and gitignored on the target before switching, so the
maw-injected symlink wouldn't get disturbed or accidentally staged. That caution
paid off; the switch was clean.

The fix itself was satisfying because the shape was already laid out by §214: the
hook had a clean `in_scope()` seam and an explicit `oracle != "orchestrator"`
guard with a paragraph explaining exactly why the orchestrator was exempt. The
orchestrator's exemption reasoning ("one hub session spans many wake_keys") was
*correct* — it's why I couldn't just reuse wake_key scoping. The insight was that
§151 already records per-session ownership by worktree, so the discriminator that
fits a multi-campaign hub is the owner worktree, not the wake_key. The owner map
was sitting right there in the watcher (`record_owner`), so the fix is "read a
file the watcher already writes" — minimal, no new state, no race surface.

The part I deliberated on was the no-owner-record fallback. Gate or skip? I
chose gate (over-block), matching §214's stated philosophy: over-blocking is
caught by the T2 backstop, but under-blocking silently re-opens the #140
silent-stall class. That asymmetry decided it.

## Honest Feedback
- The fix is small and well-targeted, but I should be honest that I could not
  *runtime-verify* the orchestrator path end-to-end — only the unit tests prove
  it. The real concurrent-orchestrator scenario (wt-20/21/22) isn't reproducible
  in a hermetic test; the tests assert the owner-match logic, not the live
  watcher integration. The `.cwd` payload field for Claude Stop hooks I'm
  *confident* about but did not capture a live payload to confirm — the `$PWD`
  fallback is the safety net (the hook runs with cwd = the session worktree).
  First debug point if it misbehaves in prod: log `my_wt` vs the owner files.
- I left the §11e *sweep* whole-dir for the orchestrator and only scoped the
  gate, because that's exactly what the consult asked and changing sweep behavior
  is an agent-behavior change beyond the hook. But there's a latent question:
  should a concurrent orchestrator session also *sweep* only its owned campaigns?
  §151 routing already wakes it only for its own replies, so in practice it's
  fine — but I flagged "sweep-reads-all, close-out-owns-own" in the docs rather
  than silently leaving the tension. If multi-session orchestration grows, the
  sweep may want the same owner-scoping.
- Two commit targets (fork PR for code, vault main for docs) is correct per the
  charter but easy to get wrong — the code lives in the repo, the charter in the
  symlinked vault. I kept them as separate commits with cross-references, which
  is the right traceability but means a reviewer must look in two places.
