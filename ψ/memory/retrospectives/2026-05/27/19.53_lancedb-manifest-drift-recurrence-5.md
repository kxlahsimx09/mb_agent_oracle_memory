## Honest Feedback
The rebuild worked and was the right immediate action, but I should be clear with myself: it's the **5th band-aid**, and I shipped it knowing a pre-lock writer could re-drift it mid-rebuild (low odds in a quiet evening window, fully reversible — acceptable, but not zero-risk). The real failure here is organizational/operational, not algorithmic: the #115 campaign declared victory on 05-23 when the lock was only *partially* activated, and the "acceptable transitional window" assumption (recurrence rare, 4×/6wk) was falsified in 4 days. That assumption deserved a verification step at deploy time — "are any writers older than the deploy commit still alive?" — which is exactly hardening option (c) I recommended. Also notable: the `:47778` server being down meant Phase 3's loud boot signal never fired, so the loudness we engineered in Phase 1 didn't help; the drift was caught by next-impl's incidental audit, not by our own instrumentation. That's a gap worth naming — our detection still leans on someone happening to run a vector query. I'm confident in the diagnosis and the restore; I'm appropriately uncomfortable that "restored" here still means "until next time."

## Lessons Learned
- **Pattern**: Advisory inter-process locks have a coverage cliff — one un-upgraded long-lived writer silently defeats the lock for everyone. Deploying the lock ≠ activating it. Verify *all* writers run post-deploy code, or make the lock mandatory (single-writer broker).
- **Pattern**: Verify drift is real before rebuilding — `ls` the referenced fragment + run a *fresh-process* query. A long-lived process's cached handle can give a false degraded (#221) or, conversely, the adapter may re-resolve per query and mask a real on-disk problem.
- **Pattern**: Process-age vs deploy-commit-timestamp forensics (`ps -eo pid,ppid,lstart` ↔ `git show -s --format=%ci`) is a fast, decisive way to attribute a mixed-mode regression.
- **Gotcha**: Detection that relies on a server boot-banner is useless when the server is down; recall-degradation needs an always-on probe, not a boot-time one.
