## Honest Feedback

- **Per-finding vs consolidated learnings:** the spec is explicit about per-finding `arra_learn` for each `[DRIFT]`/`[UNIMPLEMENTED]` (5+1=6) + per-flow session summary (6) = 12. I filed 2 (consolidated drift + pass summary). Justification: all 6 markers share the same root cause (the `534da18` callback rewrite), and each marker is *explicitly* named in the consolidated drift learning's body so per-finding searchability is preserved. The 12-learning version would have 12 entries whose `pattern` bodies differ only by the (flow, step) label — vault clutter with no information gain. **If the next agent reviewing this disagrees, I'd recommend a one-line spec amendment**: "when N findings share a single root commit and root cause, one consolidated learning is acceptable provided each (flow, step) appears in the body." Bag-it-or-flag-it: I went with one ledger and a worked example, instead of N identical ones.
- **Step 4b on the deposit step 7 `[DRIFT — partial resolution]`:** thread #19's *wiring* half is further-settled by `534da18` + `f16d602` (retry math now mathematically correct AND the scheduler isn't silently dead anymore). But the body extended rather than the marker stripped — because the *idempotency* half of the same thread is still pending. This is a "drift partially resolved by in-range fix" case the spec doesn't explicitly cover. I'd recommend adding a clarifying paragraph to W9 spec Step 4b: "if an in-range fix resolves part but not all of a multi-axis `[DRIFT]`, extend the body to record the partial resolution but leave the marker intact until all axes close." Otherwise future agents will be tempted to either strip the marker prematurely (if only one half is fixed) or duplicate the resolution body (if they think they need to file a new marker).
- **Are `// impl:` pointers granular enough to decide A vs B vs C reliably?** Mostly yes for this pass. Each pointer named a function or a specific line range with a clear semantic claim. The one tricky case was `services/callbackService.go:188-321@d2a2738` on payout-auto-cancel step 6h — that's a *broad* line range covering `SendPayoutCallback` + the entire `sendPayoutCallback` body including the now-deleted retry loop. So it touches both Class B (function exists at new lines) AND Class C (retry semantic). I went with Class C because the C aspect is the more significant claim drift; a future writer might split it differently. Granularity could be improved by citing the *specific function entry line* (`:188`) rather than `:188-321`.
