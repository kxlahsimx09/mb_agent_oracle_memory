## AI Diary

The single highest-value piece of work in this pass was not any of the four "headline" callback commits (rebrand, exponential backoff, transport, batch limit) — it was the camelCase one-liner (`f16d602`). On the surface it looks like a trivial bugfix; in reality it exposed that the previous baseline's claim "Persistent retry is owned by the new `CallbackRetryScheduler` (§5) which picks up rows..." was *literally true at code* (the scheduler ran) but *operationally false* (it found nothing to retry). That's the worst class of doc drift — true-by-construction but false-by-behavior. The doc passed every static verification a writer could perform; only a production scrape would have caught it. The learning I filed names this pattern explicitly so a future writer recognizes it on sight.

I also spent some thought on whether to mark `[UNVERIFIED]` on any claim. The natural candidate was "Recommended compound index name `idx_callback_retry_scan`" — the file comment names this index, but I have no way from W2 to verify it exists in production Mongo. I decided not to mark it `[UNVERIFIED]` because (a) the source citation is the file comment itself, not a claim about index existence, and (b) the existing pattern across the doc is to describe recommended/intended indexes from `db/indexes.go` or migration scripts without verifying production state. If this convention is wrong, it should be revised globally, not just in this row.
