## AI Diary

The static-analysis pass was clean and quick — all 5 commits live in `services/callbackService.go` + `scheduler/callback_retry.go` + `controllers/DashboardController.go`, and the 49-test suite touches none of those surfaces in any assertion. Greps for `callback_attempts` / `callback_logs` / `MAXPAY-Callback` / `Ampay-Webhook` / `X-Webhook-Source` / `/dashboard` / `retryBatchLimit` / `maxCallbackAttempts` / `ProcessPendingCallbacks` all returned zero hits across the 49 files. Tests that set `callback_url` (37 files) only do so for completeness on deposit/payout creation — none inspect the merchant-side delivery surface.

What was *surprising*: the PR #436 → #437 sequence. #436 deleted the inline retry safety net (3 attempts in 90s) and put the scheduler in charge — but the scheduler filter had been silently broken since before this baseline (used snake_case `created_at` while the bson tag on `ts_deposits`/`ts_payouts` is camelCase `createdAt`). For the entire pre-#436 period, the broken filter returned zero rows from `ProcessPendingCallbacks` every minute, but nobody noticed because the inline loop hid it. The moment #436 landed and the inline loop was gone, callbacks froze at attempts=1 across the fleet — counted live: 1,400 rows in 24h with `callback_sent != true` that the broken filter excluded. #437 had to ship the same day.

That sequence — *delete-the-safety-net-then-discover-the-fix-was-broken-underneath* — is the load-bearing pattern this pass surfaced. It's a recurring tester-relevant signal: when a PR removes a fallback path, the test suite must already have coverage of the now-load-bearing fallback. Here we have zero. The 🟡 callback-retry scheduler tripwire gap I appended is the regression guard that would have caught the broken filter independently of the inline loop. The same shape applies to *any* future PR that consolidates two redundant paths into one — the tester should be checking "is the remaining path itself tested?" before approving the consolidation.

The 5 commits also confirmed that the two ON_HOLD payout tests (`test-payout-confirm-completed.sh`, `test-payout-auto-reconcile.sh`) are still ON_HOLD on a separate axis. The MarkFailed double-callback race (Oracle thread #2, `fact-markfailed-callback-race-still-at-head-ed45b7e` 2026-04-17) is about *single-emission* semantics, not retry *cadence*. #436 changes cadence only. The race stays. ON_HOLD stays.
