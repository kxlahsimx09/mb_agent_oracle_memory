## What the three commits actually did

1. **`909d5a3` (PR #308) — `services/withdrawalQueue.go` `ClaimByBank` type-preservation fix.** The background post-claim update loop was blanket-writing `{status: "processing"}` onto every `SourceCollection` it claimed. Three of four source collections store `status` as a string (`ts_payouts`, `pullout_logs`, `direct_transfers`) — the string write is harmless. The fourth, `settlements`, stores `status` as int (0=pending, 1=completed, 2=failed, 3=cancelled — expanded with `3=waiting_to_review` in `#224` on 2026-04-18). Writing the string `"processing"` into the int field left the document with a type-mismatched status for the duration of the in-flight bot claim window. `cursor.All` into `[]models.Settlement` then raised a decode error — surfaced to admins as a 500 on `GET /api/v1/settlements` that mysteriously cleared when the bot's `MarkSuccess`/`MarkFailed` write put an int back. Fix: skip the status write for `settlements` specifically; the queue item's own `status: "processing"` continues to track the in-flight transition for dispatcher/reconcile.
2. **`e6e8069` — mock-bank break-otp-confirm fixture reliability.** `integration-tests/mock-bank/public/ktb.html` + `scb.html` cached the server-side toggle in a page-scoped `_brkOtpConfirm` variable set once at page-load. The bot reuses a browser context across tests; a fixture flip set by test N only updated the server-side flag, never the page-scoped variable captured at login in test N−1. Observed regression 20260424-151349: `withdrawal_queue` landed on `success` (real mock-ledger debit 1,000,000 → 995,000) instead of expected `waiting_to_review`. Fix re-reads the server flag on every `_brkOtpConfirm`/`_brkScbOtpConfirm` check.
3. **`0853562` — formal tree-add of `test-dispatcher-stale-bot-skip.sh`.** The prior baseline (7557402) committed at 08:19 referenced this test as VALID via in-session runtime-verified add; the commit adding the file to the tree landed 56 minutes later (09:15). No row change, no behavior change.
