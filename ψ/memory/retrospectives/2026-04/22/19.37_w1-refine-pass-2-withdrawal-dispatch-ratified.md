## Load-bearing decisions made this pass

1. **Invariant rationale upgrade: "policy" → "physical constraint"** (user's reframe on thread #41). This is the biggest conceptual win of the pass. Future architects reading §ADR-4a §Context will understand *why* single-batch-per-bank is non-negotiable and what would make it negotiable (trigger (f): bank portal introduces native multi-session-per-credential).

2. **Pool is a first-class entity, shared across methods** (user clarification + confirmed via direct read of `services/bankRotation.go` calling `selectBank()` for both `SelectBankForDeposit` and `SelectBankForPayout`). The next-system data model has `pool_bank_account` (flat membership) + `bank_account_method` (live junction) — splits the two concerns that the current system conflates in an embedded `pool.bank_accounts[].method` array and consequently drift-prone.

3. **Two-mode source-type schema with CHECK constraint** (verified via direct read of `services/withdrawalQueue.go:199-207, 702-724` + four source controllers). The split between pool-broadcast (Payout/Settlement) and direct-address (Pullout/Direct Transfer) is already in the current system — the next system promotes it from a runtime convention to a database invariant.

4. **Defense-in-depth authorization** (user's contribution late in ratification). Realtime filter is Layer 1 performance; RPC is Layer 2 security boundary. The RPC re-derives the bot's pool from `bank_account_id` and the bot's methods from `bank_account_method` live — rather than trusting the caller. Closes the latent multi-tenancy gap flagged in thread #43.

5. **Claim-side batch assembly** (thread #42, user ratified (a)). `batch_id` generated inside the RPC at claim time; `N` (tier cap) computed by an Edge Function wrapper and passed in as a parameter. Policy in TypeScript (Jest-testable); atomic boundary in PL/pgSQL (pgTAP-testable). Consistent with ADR-3.

## Honest Feedback

**What worked.**

- **Ratification-first pass shape.** Pass 2 started with two resolved threads in hand; the structure (rewrite §Context + §Decision → add §Security boundary → expand §Trade-offs → strip markers → append revision log → commit → close threads with citation → learn + supersede) flowed linearly. No thrashing.
- **Single-Edit section replace.** I rewrote the entire §ADR-4a body in one Edit call using unique anchors. Avoided the state-dependency hazard of many small Edits to overlapping text. For a section this size (~200 lines), one-shot is the right shape.
- **Writing SQL in the ADR.** Initially I considered keeping the RPC as a prose description ("the function resolves pool, checks invariant, claims items"). Writing it as actual PL/pgSQL forced me to be concrete about column names, error codes, and ordering — and that concreteness surfaced the Layer-2a/2b separation + the Edge Function N-parameter boundary. The ADR is now implementable as-is.
- **Supersede discipline.** Pass-1 learning now carries `superseded_by` pointer; P-001 respected. Anyone starting at pass-1 via `arra_search` can walk the chain to pass-2.
- **Cross-role handoff via thread, not implicit drift note.** Thread #43 to pg-writer is explicit, has three falsifiable hypotheses, and cites exact file:line. pg-writer's next session will sweep it in Step 0.

**What didn't work.**

- **Revision-log learning-id prediction.** In pass-1 I correctly noted "filled after Step 8"; in pass-2 I pre-emptively wrote a predicted id (`...-ratif`) that turned out wrong — actual id was `...-claim-ra`. Cost: one small backfill commit. Fix: stop predicting ids; always use placeholder "filled after Step 8" and backfill.
- **Revision-log `**Commit:**` order.** I wrote "filled at commit time" in the pass-2 entry, then committed, then had to backfill with the actual sha. Same pattern as above. For both fields, the placeholder → backfill pattern is correct but creates one extra commit per pass.
- **Pass-2 length budget.** W1 says refine pass = 60-120 min. Pass 2's total elapsed was 2h but active work was ~65 min. The gap is conversational time with the user — which is valuable but not billable against the refine budget. Future passes: record "active work" separate from "elapsed time" in metadata.
- **No `arra_trace_link` between pass learnings.** I supersede'd but didn't `arra_trace_link(prevTraceId=<pass-1>, nextTraceId=<pass-2>)`.
