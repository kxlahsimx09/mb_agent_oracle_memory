## AI Diary

This was the first real run of a workflow I helped shape yesterday (well,
"yesterday" in the sense of "the user's prior brew-ops session" — a
different writer session but the same pair of hands on this end). I did
not get to revisit the `references/workflow-10-constraint-harvest.md`
file with a critic's eye before running it — I ran it and tested the
spec by following it. A few friction points surfaced that a pre-run
review might have caught:

1. **"First run" is under-specified.** The workflow assumes a non-empty
   register and a populated cursor. First-run initialization is covered
   (Step 1 says "If both absent: first run. Initialize the register
   skeleton and the cursor file"), but the spec doesn't call out that a
   first run naturally blows past the "healthy 2–5 entries per pass"
   guidance in §Failure modes. I wrote 12. The guidance is correct for
   maintenance runs but silently permits first-run inflation — a later
   author could read 12 as evidence of classifier drift. I mitigated by
   writing a §First-run observations note in the pass learning, but the
   spec itself could benefit from a one-line "first-run typically
   absorbs months of evidence; 8–15 is normal" acknowledgement.

2. **The workflow says "add cross-link to migration-notes.md — add if
   missing, no-op if present".** But if the *file* is missing, the
   instruction is ambiguous. I chose the conservative read: skip the
   cross-link, flag it in the pass learning, document in the PR body,
   and treat it as partial DoD. The alternative — creating a stub
   `migration-notes.md` just to land a footer line — struck me as
   scope creep. A future editor of workflow-10 may want to add: "if
   file absent, flag as follow-up; do NOT create a stub."

3. **Theme coverage math.** Register's `## Theme coverage` section
   conflates "covered this pass" with "covered ever". On a first run
   those are identical, but on run N they diverge: a theme could have
   4 entries accumulated but 0 new in the current pass. I chose to
   write the table as cumulative (which is what a reader wants), but
   the workflow's Step 8 says "Recompute the `## Theme coverage`
   summary" without specifying cumulative vs per-pass. Minor clarity
   gap.

4. **Pass B + C were more load-bearing than I expected.** Pass A
   (memory sweep) surfaced C-001..C-007 cleanly — those are all
   well-indexed learnings. But C-008 (selector drift), C-009
   (future-dated timestamps), C-010 (stale recipients), and C-011
   (description-no-request_id) only surfaced via Pass B (git log
   scan) and Pass C (PR body read). A writer who skimps on B/C to
   stay inside the 25-min maintenance budget would miss these. The
   pass learning's first-run observation #3 notes this.

5. **"Constraint vs reaction" is genuinely subtle.** The
   `waiting_to_review` state is *our* state machine response to C-006
   (SCB post-OTP ambiguity) and C-011 (statement-no-request_id). It
   would have been easy to write a C-N entry titled "payouts need a
   `waiting_to_review` state" — but that is our design choice, not a
   constraint. I kept the classifier discipline: name the external
   fact that *forced* the state, not the state itself. This required
   two separate entries for what feels like one symptom. Right call,
   I think — the implication for target-system designers is cleaner
   ("these are the two external facts you inherit") than a single
   "you'll need this state" entry that smuggles a solution inside
   the constraint statement.

The register itself reads OK. I'm most worried about C-012
(Asia/Bangkok timezone). I classified it as `leaky` because it's
partly ours (we chose to serve Thai merchants) and partly external
(banks publish Bangkok-local without offsets). A reviewer could
reasonably argue it's not a constraint at all — it's just "code
correctly handles your domain". My rationale: the fact that Thai
bank payloads omit the timezone offset is an external encoding
choice that would survive a rewrite. But if the reviewer reads the
4-test and says C-012 fails, I'd supersede it.

## Honest feedback

**What worked well:**

- Spec-following was linear. Each step had clear inputs and outputs.
  I never had to invent procedure — only judgment calls within
  steps (like which themes to cover, which candidates to promote to
  NEW vs drop as NOISE).
- The 4-test classification heuristic was sharp enough to reject
  several candidates silently. "SCB changed the OTP flow and we
  added keep-alive polling" — the keep-alive is ours, the OTP flow
  change is the constraint. Three times I almost wrote a constraint
  entry for our reaction; each time the 4-test caught it.
- Trace-per-entry creates a readable audit trail. Twelve trace IDs
  feels like a lot, but they're cheap and each one becomes a
  searchable per-entry handle for future reviewers.
- The vault and code PRs being separate because `.agent/` is a
  symlink is the right factoring — one PR per mutation-surface.

**What was harder than it should have been:**

- The `TodoWrite` reminder fires aggressively. I restated the same
  todo state several times just to acknowledge that yes, I'm still
  on step N. Not a workflow issue — a harness-level noise issue.
- Theme coverage rotation relies on a human-readable table in
  `constraints.md §Theme coverage`. Parsing it on future runs will
  be fine for small N but fragile at N>30 themes. If the register
  grows past ~50 entries, this should become machine-readable
  YAML frontmatter.
- The Oracle vault has several untracked/modified files from a
  prior session that I deliberately left alone. That's the right
  discipline, but it meant the vault PR had a `Warning: 3
  uncommitted changes` line from `gh`. A cleaner precondition
  check at session-start would catch "you're in a vault repo
  that someone else was mid-committing in" before the first write.

**What I'd change in workflow-10 if I edited it now:**

1. Add a one-line "first-run" note in §Failure modes acknowledging
   that 8–15 new entries on first run is normal.
2. Add to Step 11: "If a referenced cross-link target file does
   not exist, flag in pass learning and do not create a stub."
3. Add a "constraint vs reaction" sidebar to §Classification
   heuristics with a worked example (ideally the waiting_to_review
   one — it's canonical and will come up again).
4. Clarify Step 8's theme coverage as cumulative-across-all-passes,
   not current-pass-only.

**What I'd change in my execution if I ran this again:**

- Run Pass B (git log) in parallel with Pass A (memory sweep)
  instead of sequentially. The two passes are independent and
  I wasted a few tool calls waiting.
- Candidate identification would benefit from a small scratchpad
  (a temp file or a TodoWrite sub-list) listing (theme, source,
  statement, citation) per candidate, so Step 7's classification
  doesn't have to re-read every search result. I kept it all in
  working memory this time; worked for 12 but wouldn't scale.
