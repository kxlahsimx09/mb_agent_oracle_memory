## AI Diary

This was the first actual W1 run against a repo that already had a pre-existing `docs/adr.md`. The file looked like a baseline commit but wasn't written against the W1 template — no H1, no template sections, no revision log, no prior-art citations, ADRs as H4 under an H3 umbrella. My first instinct was to retrofit the whole thing to the W1 skeleton. I talked myself out of that at Step 2 by re-reading the W1 anti-pattern list: "Rewriting the ADR top-to-bottom in one pass. This is not a refine — it's a baseline. Distinguish explicitly." That guardrail paid off. If I had retrofit the whole doc, the diff would have been unreviewable and the human would have lost the ability to separate "structural retrofit" from "actual architectural claim."

The evidence-sweep phase was strikingly cheap this run. Four `arra_search` calls surfaced the whole inheritance surface I needed — `flow:withdrawal-queue-dispatch-and-claim` was already re-ratified by `pg-writer`/`technical-writer` as recently as 2026-04-21 (thread #29). That meant the strongest pattern claim I could make — "one batch per bank, no pipelining is permanent design intent" — was already load-bearing in the current system. I didn't have to infer; I had a ratified human-confirmed line to cite. The cost of Input 1 was genuinely "cheapest" per the W1 hierarchy.

Picking the focus theme felt important. I almost picked RBAC (ADR-2's sub-decision) because it had the most un-cited claims — but RBAC is security-sensitive, which per my own skill manifest means halt-and-ping the human synchronously. That would have turned the pass into a conversation rather than a document deliverable. Withdrawal dispatch was the next-best candidate: rich current-system prior art, a clear pattern claim to carry forward, and a material architectural divergence (remove the dispatcher) that the existing ADR-4 understated in a single sub-bullet.

The thread-writing phase was the slowest part — I wrote threads #41 and #42 in a "propose-then-confirm" shape so the human can answer in one line ("a", "b", or "c") rather than having to re-derive the alternatives. This matches the "ratification — affirmative engagement with the specifics, not rubber-stamp" framing in the W1 workflow.

I filed the `arra_learn` under `github.com/kxlahsimx09/mb_agent_oracle_memory` because the product repo's project slug is still not in `KNOWN_PROJECTS` (brew-ops follow-up filed in the prior `w1-refine-adr-workflow-authored-for-system-archite` learning, unresolved). That's friction and it routed the learning to the meta-repo, not the project repo, for the second time — so it's surfacing as a real pain point.

Duration was unexpectedly short (~40 min vs the 60–120 min "refine budget" in the workflow). Two factors: (a) Oracle was fully stocked with pre-curated prior art, so Input 1 did the work of Inputs 2, 3, and 4 at once; (b) I stopped at Input 4 as the workflow allows when theme is adequately evidenced, and skipped Input 5 (code reading) entirely. If this pattern holds for future passes, the budget estimate may be pessimistic for themes where the current-system writers have already ratified the flow.

## Honest Feedback

**What worked.**

- **Step 0 thread sweep is a genuine safety net.** It took <2 min and surfaced 5 non-architect pending threads I would otherwise have wondered about. Clean in-my-territory = clean start.
- **Single focus theme + narrow scope.** Letting the theme sentence be binding prevented scope creep. I had the urge to also fix RBAC and to retrofit the document structure; writing the theme down and making it a step-1 output made those urges visible instead of silent.
- **Input 1 as the primary source of truth.** The W1 workflow's cheapness-ordering was validated — Oracle memory gave me ratified, cross-referenced, human-confirmed current-system facts at a cost of one `arra_search` per axis. No code reading was required.
- **Template `[AWAITING_THREAD:?]` → `[AWAITING_THREAD:<id>]` two-phase**. Writing threads AFTER drafting the section let me write each thread's body with the full context of what the ADR actually claims, which made the thread messages richer than if I had threaded first.

**What didn't work.**

- **Pre-W1 baseline edge case is undocumented.** The current `docs/adr.md` was committed before W1 existed and doesn't match the W1 template. W1's step sequence handled it correctly (treat as refine, not baseline) but the workflow text doesn't *name* the case explicitly. A future architect reading the workflow might spend time wondering "should I baseline-retrofit?" — the answer should be: no, retrofit is its own pass, refine stays surgical.
- **`KNOWN_PROJECTS` gap is still biting.** Second W1-adjacent learning filed under `mb_agent_oracle_memory` as a workaround. This costs me a ~2-min cognitive-overhead tax every time: I try the real slug, fail, fall back. Brew-ops should land the one-line PR.
- **Retro path ambiguity.** The W1 spec says `ψ/memory/retrospectives/…` without qualifying which vault. I wrote to the central `mb_agent_oracle_memory` vault under the assumption all retros land there (consistent with `technical-writer` convention), but the workflow could be explicit.
- **No cross-referencing commit.** I wrote the `arra_learn` after the PR commit, then did a backfill commit for the learning id. Ideal would be a single commit — but that requires knowing the learning id before filing, which is impossible. The two-commit shape is correct; the workflow could name this explicitly so the next architect doesn't feel sheepish about it.

**What would make the next pass cheaper.**

1. **A one-line checklist of "previous-pass loose ends" at Step 1.** On pass 1 this was empty; pass 2 should automatically pick up "did #41 and #42 resolve? If yes, close markers; if no, continue." Would save me 5 min of grepping the revision log.
2. **A convention for pass-over-pass traces.** `arra_trace_link` exists; the workflow doesn't prescribe using it to link pass-N learning → pass-(N+1) learning. If we did, the evolution of each ADR section would be walkable in the Studio.
3. **A `skip-input-5` tag.** This pass explicitly did not read current-system code. A convention ("cite `#skip-input-5` in the learning when Inputs 1–4 gave full coverage") would let the next pass audit whether the habit is forming — useful for proving to ourselves the cheap-to-expensive order works.
4. **Brew-ops: land the KNOWN_PROJECTS PR.** Referenced. Second time the workaround has been used. Opportunity cost is small but real.
