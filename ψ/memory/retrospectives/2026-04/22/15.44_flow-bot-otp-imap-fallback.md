## Honest Feedback

**Q — Was the flow boundary clear, or did scope creep across into a neighboring flow?**
Unusually clear, because the sibling `bot-otp-relay` pass yesterday already set the scope boundary via "sibling flow territory" markers. The temptation to fold in the caller-side retry wrapper (3x API → IMAP) was present — the IMAP call only makes sense in the context of the wrapper's cascade — but keeping it out preserves the "one helper, one flow" invariant that makes `bot-otp-relay` and `bot-otp-imap-fallback` parseable as a pair. Future W8 authors working on helpers with nested fallback chains should follow this precedent.

**Q — Are numbered sequence steps actually usable for impl pointers, or did a step aggregate too much?**
The 12-step linear + nested-outer-loop + nested-inner-loop + three-way-outer-alt diagram has the most structural density of any bot-side flow so far (larger than ktb-single-transfer-withdrawal's 10 steps + 4 sub-steps). Steps 9a/9b/9c/9d/10 compress a five-stage filter chain into one inner loop — that's close to the aggregation ceiling. If the bank ever adds a sixth filter (e.g., a new header-based test), splitting to 9e/9f would push the diagram beyond comfortable reading size; at that point, extract the filter chain into its own helper and document separately.

**Q — Did the mobiz-side breadcrumb (if any) accurately predict the bot-side step boundaries?**
N/A — no mobiz side for this flow (and, uniquely, no ever expected mobiz side, unlike bot-otp-relay which could still gain one). The sibling's breadcrumb *did* predict this flow's existence by naming the boundary ("sibling flow territory"), and that prediction landed precisely — no scope drift between the sibling's reference and this flow's actual content.
