Mirrors the `deposit-auto-match-from-statement` same-day S4→S2 pattern from 2026-04-19.

**Drift surfaced during ratification (not a thread question — an observation).** Human asked "ทำไมไม่เป็น waiting_to_review" in response to a production-scenario walkthrough I provided for Q(d). The scenario I had drawn (`t=1:00 bot เจอ popup → timeout → เรียก MarkFailed`) was pre-PR-#83 bot behaviour. Under current bot discipline (PR #83 on 2026-04-19 for SCB maker submit-reached; PR #67/#68/#69 on 2026-04-18 for SCB approver post-OTP 3-layer wait; PR #249 on 2026-04-20 for dispatcher stale-sweep triage on `bank_transaction_id`), any uncertainty about whether money moved must land in `waiting_to_review`, not `failed`. The question forced me to re-read bot-side `app.js` and the relevant learnings, and led to a three-category taxonomy (A: confirmed-non-submit / B: bot-side-uncertainty / C: bank-inconsistency) that clarifies *which* `failed` arrivals ever trigger this flow in today's architecture. Only category C — bank responded with explicit failure but processed the transfer anyway — triggers it. Category C has not been observed in production.

**My first attempt at Q(d) was wrong.** I initially framed SCB as "category B" (uncertainty routed to `waiting_to_review`, auto-reconcile obsolete for SCB). Human correctly pushed back: the real use case is category C (bank-lied), which bot-side discipline can never prevent because bot is not uncertain — it correctly translates what the bank says. The flow is a dormant safety net for that specific inversion. Rewrote response to include the 3-category framing and the practical recovery split (KTB category-C auto-reconciles silently because descriptions carry request_id; SCB category-C routes to admin because descriptions lack it).

**Human ratified all four spec questions plus the scenario correction.** Disposition:
- Q(a): drift, PR needed, filed as a new drift learning + W8 child trace. Same shape as the deposit-sibling Q4a drift from 2026-04-19 (different failure mode — session-abort cleanly here vs. partial-state there — but same alert-surface gap).
- Q(b): intentional (matches deposit-sibling #17 Q4b answer from 2026-04-19).
- Q(c): intentional (internal-only, operators observe logs, no future flow doc).
- Q(d): intentional dormant safety net (Option A — no auto-reconcile P2/P3 broadening; `#200`'s false-match risk still applies to any stale-confidence window; admin confirm-completed sufficient given zero observed frequency).

**Cross-repo awareness earned.** The Q(d) deep-dive pulled in five bank-bot-side learnings (PR #83, PR #67/#68/#69, PR #249, `2026-04-19_pattern-scb-maker-escalates...`, `2026-04-18_decision-scb-approver-post-otp-success-detection`) and required re-reading `kokarat/bank-bot/app.js` line-by-line for the `safeMarkFailed` vs `safeMarkWaitingToReview` call sites. ## Honest Feedback

**Did the single-folded-thread pattern hold up?**

Yes, and with a new wrinkle. Thread #37 fold pattern was identical to the five predecessors (slip-upload, payout-request, topup, deposit-auto-match, and now this). One new observation: **the scenario-correction insight was not in any of the four Q(a)-(d) questions**. It emerged mid-thread from a clarifying prompt ("ทำไมไม่เป็น waiting_to_review") that was outside my pre-drafted question set. This is the first time a ratification revealed doc-level drift that wasn't on the question list. The fix was clean (rewrite §Purpose) but it suggests W8 authors should consider including a default "scenario framing verification" ask in every ratification thread — something like "walk through the triggering scenario in your own words and tell me which step feels wrong". Future W8 template improvement, not action this pass.

**What the drift-learning system did right.**

Category Q(a) had rich prior context: the deposit sibling's Q4a (2026-04-19) had ALREADY encountered a wallet-failure-proceeds-anyway pattern on the deposit side, classified drift, filed learning, queued W4. When Q(a) on the payout side came up, the human's disposition (drift, file, queue) was reached in ~2 seconds because the precedent existed. The drift learning I just filed (`2026-04-22_drift-in-payout-auto-reconcile-from-statement-q.md`) explicitly cross-links to the deposit sibling's drift learning. Next time a reviewer audits the W4 queue, both drift learnings will surface together and can potentially be fixed in one PR (same remediation shape: SSE event + Telegram alert). Cross-learning reuse working as designed.

**What went slightly off.**

My first-attempt Q(d) response (framing SCB as category B / obsolete path) was **wrong** and required rewriting. This cost ~5 minutes and one extra chat turn. Root cause: I anchored on the PR #83 + PR #67-#69 "waiting_to_review discipline" principle and generalised too fast from "SCB uncertainty → waiting_to_review" to "SCB reconcile path obsolete". Missed the category C case (bank-lied, bot correct, statement reveals truth). Lesson: **when generalising from a principle, enumerate the cases it does NOT cover before concluding**. Would have caught the gap in the initial reply instead of needing user pushback.

**Lucky artefact of the doc-drift fix.**

The rewritten §Purpose with explicit A/B/C taxonomy is actually a better doc than the original. The original buried the use case ("if the bot actually did submit... the debit row is the evidence") in the middle of a paragraph; the new version foregrounds it as a labelled category. Future readers (and the bot-writer counterpart when W8 adoption reaches that repo) can pattern-match on the A/B/C frame explicitly. Net quality gain from what was initially a user-prompted correction.
