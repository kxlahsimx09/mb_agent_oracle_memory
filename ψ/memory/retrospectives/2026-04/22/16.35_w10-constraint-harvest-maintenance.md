## AI Diary

This was the second run of workflow-10 in the same day, about 90 minutes
after the first-run baseline's PR merged. Going in, the main question was
whether the workflow would feel meaningfully different in maintenance
mode than first-run mode. It did, in useful ways.

**Same-day maintenance has a distinct shape.** The first-run retro worried
that "zero-entry passes are still valuable as re-verification stamps," but
I came in expecting this pass to yield something precisely because the
first run had left 9 themes at zero. It did — 2 NEW from the theme rotation
alone. Pass A (memory sweep) was where both candidates surfaced. Pass B
(git log) yielded zero because `cf1edb3..HEAD` only contained the W10
first-run commit itself; Pass C (merged PRs) had candidates but they all
either re-encoded existing entries or were internal regression candidates;
Pass D (AGENTS.md §9) added nothing because the discipline rules' *reasons*
are already in the register. On a same-day second run the lane ratio
inverts versus what I'd expect from a weekly or quarterly run — the
pending vault learnings from the last month are the yield-source, not
new commits.

**The preconditions-check upstream was valuable.** The user's first
request came while PR #283 was still OPEN. I stopped, explained the fork
(run on main = duplicate, run on branch = mutate pending PR, zero-delta
re-verify has no register on main to stamp), and waited for the merge
confirm. This added ~1 minute to the total session and saved a much-more
painful unwind. The spec doesn't call this out — there's no "if a prior
W10 PR is still open, wait" clause in §When to run — but it's now
instinct: check the cursor's `mobiz-commit-head` against `origin/main`
before branching. Worth adding to Step 1 as a half-line on the next spec edit.

**The two NEW entries felt comfortable but not mechanical.** C-014
(Telegram) is the cleaner of the two — it's squarely a vendor behavior,
the reaction-vs-constraint distinction is crisp (`escapeMD` is clearly the
reaction), and the tier is unambiguous hard. C-013 (Thunder) is softer
ground: is Thunder's availability gap a *constraint* or is it *our choice
to depend on Thunder when we could have built slip-verify in-house*? I
wrote it as `soft` because a future rewrite could renegotiate or replace
Thunder, and I tried to foreground that in the target-system implication
field. A reviewer could reasonably argue C-013 should be rejected as
"that's a vendor choice, not a constraint" — and if they do, I'd
supersede it rather than fight. The *class-constraint* (3rd-party OCR APIs
are flaky) is real; whether Thunder specifically is a constraint is
more debatable.

**The one candidate I worried about dropping.** The callback-resend
idempotency gap (regression-candidate-callback-resend-scheduler learnings
from 2026-04-19 / 2026-04-21) is a real durability problem. I classified
it as NOISE because the external fact behind it ("merchant endpoints may
process duplicate callbacks") is merchant-implementation-dependent —
some merchants are idempotent, others aren't, and the variance is not
externally imposed on us by a single party we can name. It doesn't pass
the §Classification-4-test cleanly. But it was close enough that I want
to flag it for the next reviewer: if a future W10 run discovers a
*specific merchant* whose callback contract is both documented and
idempotency-hostile, that could be a real partner-sla constraint at
`soft` tier. Parked for now.

**Theme-coverage cumulative fix.** The first-run retro flagged that the
`## Theme coverage` table conflates "covered this pass" with "covered
ever." I fixed this in the register by explicitly annotating the header
"Cumulative across all W10 passes (not just this pass). Per-pass deltas
live in each pass learning." This future-proofs the table for pass N — a
reader now knows where to look for delta (the per-pass learning), not the
cumulative table.

## Honest feedback

**What worked well:**

- Same-day turnaround validated the workflow's maintenance shape. 2 NEW
  entries in ~25 minutes of work; within the spec's budget (25 min for
  maintenance) and right in the middle of the 2–5-new-entries-per-pass
  guidance.
- Parallelizing Pass A searches across 4 themes with a single request
  containing 4 `arra_search` calls would have been faster, but I ran them
  sequentially this pass because each subsequent search was informed by
  the prior one's surface (e.g., the "thunder" search was made more
  targeted after the partner-sla query surfaced `UploadSlipAdmin
  hardening`). The first-run retro's "run B+A in parallel" guidance was
  about *independent* passes; within Pass A the theme-by-theme
  sequencing was still the right shape.
- The 4-test caught 2 NOISE drops cleanly (callback-resend gap and
  statement-push dedup). The two survivors are the ones I expect to
  hold under review.
- Trace chaining via `arra_trace_link(first-run-root, this-root)` is
  cheap and gives a future reader a hop-by-hop audit trail of the
  register's evolution. Two hops in, the chain is starting to prove
  itself.

**What was harder than it should have been:**

- The worktree is at `.claude/worktrees/sad-borg-063e5d/` and was
  forked from `cf1edb3` (pre-merge main). The `git fetch origin` +
  `git checkout -b ... 9660d7d` dance to re-base onto post-merge main
  inside this pre-existing worktree felt slightly off-spec — the
  workflow implicitly assumes a fresh branch from `main` in a vanilla
  clone. Worked fine but added one step of cognitive load. Future
  workflow-10 spec could acknowledge worktrees explicitly in Step 1.
- Child trace creation landed the trace cleanly but `arra_trace` doesn't
  actually populate `foundFiles` / `foundLearnings` for me — I'd have
  to pass them explicitly. I didn't, for either child. Not wrong, but
  the traces are skinnier than they could be. Future runs could build
  a small helper that accumulates dig-points during pass A–D and
  passes them in at trace creation.
- The first-run retro recommended a "candidate scratchpad" per pass.
  I deliberately did not use one because 2 candidates is small enough
  to hold in working memory. But I did have to re-search the Thunder
  learning once to grab the exact PR numbers for the evidence field.
  A scratchpad would have saved that re-search. For 5+ candidates it
  would be non-optional.

**What I'd change in workflow-10 if I edited it now (accumulating with
first-run feedback):**

1. (carry-forward) Add a one-line "first-run" note in §Failure modes
   acknowledging 8–15 new entries is normal on first run.
2. (carry-forward) Add to Step 11: "If a referenced cross-link target
   file does not exist, flag in pass learning and do not create a stub."
3. (carry-forward) Add a "constraint vs reaction" sidebar to §Classification
   heuristics with a worked example.
4. (carry-forward, applied this pass) Clarify Step 8's theme coverage as
   cumulative-across-all-passes, not current-pass-only — I applied this
   to the register header text this pass, but the spec still reads
   ambiguously.
5. **NEW** — Add to Step 1 or a Preconditions bullet: "If a prior W10
   PR is still open against `main`, pause. Either wait for merge (if the
   pass bounds are close to the prior PR's write range) or run on top of
   the pending branch (if the user explicitly opts in)." This is the
   specific issue I had to resolve with the user at the top of this
   session.
6. **NEW** — Step 12 commit/PR step should acknowledge the vault PR as
   a first-class artifact, not just "the pass learning lands via
   `arra_learn`". The vault PR is a real artifact that needs a paired
   commit message and a review surface. Spec currently doesn't call it
   out — it was implicit from the first-run, but a future runner
   encountering this workflow cold could miss it.

**What I'd change in my execution if I ran this again:**

- Pre-build the candidate scratchpad at Step 3 start. Even for 2
  candidates, it reduces the chance of re-searching evidence.
- Pass `foundFiles` / `foundLearnings` arrays to each child trace at
  creation so the trace is not just a query string — it's an indexed
  bundle. Easy win.
- Re-check the worktree precondition at Step 1 more rigorously — I
  only realized the forked-from-pre-merge issue when I tried `git
  status` on the wrong commit-head. A quick `git merge-base origin/main
  HEAD` would have surfaced it.
