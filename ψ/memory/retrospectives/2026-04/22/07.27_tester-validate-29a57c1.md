## What the validation turned up

- **Zero new regressions, zero status flips.** 30 commits in range; only 3 touched production Go/helper code (`29a57c1` WQ GetStats `source_type` param, `f2f7e26` redis TLS opt-in, `21cd87f` k8s env companion). All three are backward-compatible.
- **Mock-bank KTB routing (`0fb1c2e`)** was the "interesting" commit of the pass. It could have turned every KTB-using test STALE, but the author kept both `/ktb` and `/ktb/:account` routes alive in `server.js:2428-2438` and updated the 5 test scripts that construct the URL in the same PR. Clean migration. The reason this matters: the hash router at bank-bot's end was appending `/#/login` to `BANK_URL`, and with `?account=7777/#/login` the hash router misparsed — ended up polling with the container-global `BANK_ACCOUNT`. Path segments compose cleanly. Worth remembering if any future test adds a new URL-constructor pattern.
- **3 amended notes that surfaced silent-stale behavior from the prior baseline.** Three tests that were marked VALID at `22451ef` were actually subtly wrong:
  - `test-mixed-flow.sh` — same-amount-per-iteration produced last4+amount collisions → `match_status:"review"` on every statement → the test "passed" only because it didn't assert match_status. `affc581` (2026-04-21 20:25 GMT+7) fixed by switching to `base + idx`.
  - `test-deposit-collision-dual.sh` — `SKIP_INFRA=true` kept `bank_statements` state across runs; same-minute re-runs collided on dedup key. `5670460` added per-test pre-clean; `92baa85` elevated it to shared `setup_test_data` so all 12 statement-touching tests benefit. `1ad0712` separately aligned the assertion with SCB matcher semantics + guarded KTB `resolveKTBBiznextAccount` against cross-bank session leak.
  - `test-deposit-idempotency.sh` — fails deterministically in the test env because `db/redis.go:120-122` hardcoded Redis TLS while `redis:7-alpine` in compose does not. `add6f49` de-tiered from regression suite; `f2f7e26`+`21cd87f` then fixed the root cause (TLS opt-in via `REDIS_TLS` env, k8s sets it true). Test not re-tiered pending runtime confirmation — a modest todo for a future operator.
  
  **Lesson:** VALID classifications should include "did the test actually assert what it claims to assert under current matcher behavior" — not just "does the URL resolve + the body parse". Prior baseline missed three such cases. For the next pass, when a matcher-semantics commit (like `ae27832`) lands, every test that exercises the matched path deserves a re-read of the assertion block, not just the request shape. Candidate refinement for `workflow-1` §2e WRONG-SETUP trap list.
