## Honest Feedback

**Why did this drift go undetected for 2+ days?**

Root cause: **no automated cross-repo code-change → doc-drift detector exists.** Bank-bot fixes landed, bank-bot side filed its own ruled-drift learning (for drift #2), but the mobiz flow doc that referenced those bank-bot code locations was never re-verified. The `workflow-thread-resolve.md` Pass 2 orphan-scan catches *threads* that got answered without the doc being updated, but it doesn't catch *code* that got fixed without the doc being updated. Different drift class, same invisibility.

Two mitigations possible for future sessions:
1. **Cross-repo link-check.** Periodically grep all mobiz flow docs for `bank-bot/<path>:<line>` citations, resolve them against bank-bot HEAD, flag any citation where the surrounding code no longer matches the doc's claim. Would have caught this in ~1 minute.
2. **Routine W9 pass after cross-repo commits.** When bank-bot commits a drift-resolution (we can tell by commit-message prefix `fix:`), trigger a mobiz W9 pass that grep-scans for that drift's symptoms. Infrastructure-level, not per-session work.

**The user's review prompt was high-leverage.**

Asking "is anything stale given what I just learned?" produced 2 drift-fix discoveries + 1 MEDIUM-severity + 1 LOW spot-fix finding in ~25 minutes. That's a better signal-to-noise ratio than scheduled audits because it was anchored to *specific new knowledge* (the 3-category taxonomy + bot-side discipline PRs #83/#67-#69/#249). Observation: post-ratification review is a **load-bearing discipline** — not just for the ratified doc, but for the entire doc corpus that was authored against older assumptions.

**What this pass did right.**

- Did not open a new Oracle thread. Thread-resolve discipline says code evidence + existing ruled-drift learnings are authoritative for W9. Would have been tempting to "get human approval" for the doc change but that's overkill — the drifts are factually resolved in code, the fix commits are explicit, the sibling ruled-drift learning has verification evidence.
- Cited the drift #2 bank-bot-side ruled-drift learning rather than duplicating it on the mobiz side. One authoritative artifact per drift, cross-referenced — not two parallel copies that can diverge.
- Retained the historical drift descriptions per P-001. Operators debugging pre-fix payouts (from before 2026-04-19 / 2026-04-20) can still understand why their `ts_payouts.bank_transaction_id` contains a reference string — via the `dfafa78` #213 mirror rule that copy is permanent.

**What could have gone better.**

- **Initial audit underestimated drift #1.** First audit report called out drift #2 as HIGH but didn't flag drift #1 at the same severity. Only when I read bank-bot code directly did I realise drift #1 was ALSO fixed. Lesson: when auditing a doc that flags multiple drifts, ALWAYS verify each drift individually against current code rather than assuming the first one found is the only one that moved.
- **Attribution-line slip in PR body.** CLAUDE.md explicitly forbids AI attribution. I included it in the initial `gh pr create` body and only caught it after the PR was opened. Fixed via `gh pr edit`, but the slip would have been visible to reviewers during the brief window. One-shot checklist item to add: before `gh pr create --body "..."`, grep the body for "🤖" / "Generated with" / "Co-Authored-By: Claude" and bail if present.
