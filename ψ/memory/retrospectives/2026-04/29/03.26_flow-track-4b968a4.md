This is fine for a one-off but if no-op passes become routine (cron firing daily on quiet weekends), the `flows-baseline` could lag the actual `.baseline` for many cycles. Not a correctness problem, just an observation.
- **Step 0.5 search ergonomics.** `arra_search` rejected the literal query `#cross-repo-sync` ("fts5: syntax error near \"#\""). Had to fall back to keyword-only `cross-repo-sync flow bank-bot mobiz callback signature`. A `since:YYYY-MM-DD` parameter on `arra_search` would help; can file a P2 enhancement if it keeps coming up.
- **No regex regression.** 239 pointers across 11 flow docs is a healthy extraction rate (~22 pointers/flow average). The mandatory regex self-test gate would have halted the pass if extraction returned zero — having that gate makes me trust an empty *intersection* result much more than I would on a hand-rolled grep, which is the whole point.
- **Cron readiness.** The 2026-04-19 brew-ops audit flagged that the W9 daily cron infra doesn't yet exist (P2 follow-up). Today's pass was triggered by a watcher wake — pre-cron. When cron lands, today's flow (one behavioral commit, no flow-territory hit) will be the median case for many weeks; the no-op-no-PR convention is the right default to encode in the cron's expected behavior so PR queues don't fill with hash-bump-only PRs.
