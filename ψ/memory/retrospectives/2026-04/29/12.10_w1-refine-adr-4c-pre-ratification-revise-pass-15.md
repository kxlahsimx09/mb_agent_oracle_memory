## AI Diary

This pass was a textbook case of "user pushback as design force multiplier." Pass-1's C1 architect-rec (bare 1-min sweep parity) was structurally inferior to what the next-system can do, and I had **not** read current code before writing the rec — assumed parity was the right answer because the ratified flow learning described current as 1-min sweep. User's first sentence — *"ถ้า sweep ทุก 1 นาที ยังไง deposit ที่เข้ามา ก็ ไม่มีทาง การันตี expire ตามเวลาที่กำหนดสิ"* — caught the visibility window I had glossed over.

**The recovery sequence was predictable but slow.** I went through:
1. Acknowledge the concern (~2 min)
2. Propose Option A "faster sweep" + Option B "opportunistic on read" without code-read (~3 min) — **mistake; should have run Input 5 first**
3. User asked "ค้นดูก่อนว่า current เป็นยังไง" — explicitly forced Input 5 (~10 min for code read)
4. Discovered current already implements opportunistic across 6 surfaces with a `SECURITY: Atomic expiration check to prevent race condition` comment (~5 min for analysis)
5. Re-proposed Option B (port from current) — but framed as "improvement" until I caught myself; revised to "parity port" mid-thought
6. User: "ไม่ค่อยชอบ opportunistic เพราะมันไม่ clean แต่อยากรู้ทาฃเลือกอื่นๆ" — pushed back on cleanliness
7. Explored 5 options A-E with complexity/infra/precision matrix (~15 min)
8. User picked Option C (view) + accepted Supabase 1-min constraint
9. Wrote Decision #10 + cross-cut amendments + Trade-offs matrix (~30 min)
10. Commit + thread message + arra_learn + arra_supersede + arra_trace + arra_trace_link + revision-log backfill commit (~15 min)

**The mid-flow correction "opportunistic is parity, not improvement"** was the moment I want to remember most. I had typed the start of "we propose adding opportunistic as an improvement over current's 1-min sweep" and was about to send when I realized — *wait, this is the cross-direction-metric / C4 mistake again. I haven't read the current opportunistic surfaces. Maybe current already does this.* Stopping mid-thought, running Input 5 — that was the right move and would have been an even-better move 5 minutes earlier (i.e., before proposing Option B at all).

**The 5-option exploration was unusually productive.** Normally architect-recs converge to 1-2 options after evaluating; this pass had 5 distinct structural alternatives because the design space genuinely has 5 axes (sweep cadence, opportunistic write, scheduled jobs, external worker, computed view). User's "ไม่ clean" objection forced me to articulate cleanliness as an axis I hadn't been weighing — and once articulated, the view pattern emerged as Pareto-optimal (visibility 0 + callback ≤60s + zero infra + cleanest separation).

**The "callback timing as deliberate contract" reframe was the design move I'm proudest of.** Once I accepted that visibility ≠ emission timing, the design got simpler: view solves visibility (load-bearing); sweep solves emission (non-load-bearing); document the ≤60s callback latency as a merchant-facing contract. This decoupling is the kind of insight that's only obvious in retrospect.

**The cross-cut amendments** (§ADR-4b D5 + §ADR-4d D3) were necessary, not nice-to-have — without them, future code paths could bypass the view and credit wallets on effectively-expired deposits. Recognizing this required tracing the view contract through `finalize_deposit` race-guard semantics. The 60s window between "physically `pending`" and "effectively `expired`" is real; defense-in-depth at the RPC race-guard layer closes it for any future caller.
