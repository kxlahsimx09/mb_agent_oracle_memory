## AI Diary

This was a long session. One calendar day blurred into two. Writing this retro from a seat that feels very different from the one I sat in at pass-1 opening.

**What I thought I was doing when I started:** Running W1 refine-adr against `docs/adr.md` §ADR-4a — write a draft, open ratification threads, commit, retro, done. One pass, ~90 minutes, canonical shape.

**What actually happened:** Seven passes. A 15-commit PR. A convention discovery ("ADR vs design-doc") that required a refactor to the document shape. A cross-role handoff that surfaced a fact error in my own analysis. A vendor-tech evaluation that went from surface enthusiasm to deep skepticism in a single deep-research pass. Two ADRs refined where I expected one. A full day's worth of architect thinking.

The thing I did not anticipate — and probably the most important thing I learned — is the pattern of **user peer review driving each subsequent pass**. I did pass 1 on my own, ratified threads #41/#42 in pass 2, and thought I was done. Then the user read pass 2 and said "required_method is redundant with source_type, isn't it?" — pass 4. Then "amount ≤ balance doesn't handle sum, does it?" — pass 5. Then "the ADR is 450 lines, shouldn't it extract?" — pass 6. Each pass was triggered by the user spotting a class-of-bug or class-of-smell that I had integrated into my own draft without flagging. The user is acting as the experienced reviewer that the ADR process assumes will catch these — and I, as the drafter, am systematically missing them during write-time.

This shook my confidence a little. If user hadn't asked those questions, pass 5's per-row over-commit bug would be in `#decision`-tagged code. Pass 6's ADR-vs-design-doc confusion would be propagated into every future architect session as precedent. Pass-3's wrong call site (`AssignBankToItems`) would be cited forever without correction.

But the system mostly worked. Each surface I missed got caught before merge. No code shipped with the bugs. The `#provisional` → `#decision` gate is the exact discipline W1 is supposed to enforce, and it did enforce it — because the user exercised it. The question is whether I can shift some of that catching *inside* my own drafting process, rather than relying on the user's read always.

The cross-role handoff (thread #43) was the best part of the session. I made a specific, verifiable claim ("`AssignBankToItems` has no `pool_id` filter → latent drift"), shipped it as a handoff to pg-writer, and got back a precise correction within a few hours: wrong call site, real path is in the scheduler package, and the actual-latent-gap is the nil-poolBankIDs fallback at `:596-598`. That's exactly how the two-writer mesh is supposed to function. pg-writer then filed a follow-up drift learning with `related:` backlinks to my work, closing the chain. Zero miscommunication, zero drift, zero rework. Different people, different repos, one coherent record. If the rest of the fleet starts working like this, the system scales.

The vendor-evaluation arc (GoLogin → Steel → back to Hetzner) was the most humbling. Three times in the same sub-discussion I had to correct numbers or assessments as more data came in: first when user provided real GoLogin pricing ($49.50 vs my $35 estimate), then when user pointed out the 300-hour cap changed the cost model entirely, then when I did real research on Steel Browser and discovered 10 incidents per quarter on their own infrastructure. Each correction came *after* I had already presented analysis confidently. Fastest way to a wrong ADR decision is presenting speculation as grounded reasoning. Slow path to a right one is saying "I don't know, let me check" — but I didn't do that enough.

The ADR-vs-design-doc convention that emerged in pass 6 is probably the most durable output of the session. ## Honest Feedback

### What worked

- **Thread-first ratification discipline.** Every load-bearing design claim in passes 1-2 was gated by `[AWAITING_THREAD:<id>]` + `[RATIFICATION_PENDING:<ids>]`. User ratified → markers stripped → `#decision`. No silent promotion of provisional work. This is what W1 is designed to enforce, and it worked exactly as spec'd.
- **Cross-role handoff pattern.** Thread #43 → pg-writer → fact correction → pass-3 refactor → pg-writer drift learning with backlinks → closed. A 24-hour cross-repo conversation in Oracle + `arra_learn` mesh, zero drift, preserved forever. Template for how sibling writers should coordinate.
- **Immediate learning filing during passes.** `arra_learn` within 30 minutes of each milestone means prior-art is at Input-1 cost for next session. This saved future-me probably hours of rediscovery.
- **Physical-constraint reframe (thread #41).** User's framing — "1 bank_account = 1 portal credential = 1 browser session, so Alternative E is structurally impossible" — is stronger than thread #29's "permanent design intent" and will survive design-intent politicking that mere policy rejection would not. Worth escalating as a design-reasoning pattern.
- **ADR-vs-design-doc convention emergence.** User-surfaced, but codified and memorialized in commit + learning. Every future architect session in this repo has the pattern to reference.
- **`arra_supersede` with selective application.** Pass 2 superseded pass 1 (decision shape changed). Passes 3, 4, 5, 6 did NOT supersede pass 2 (primary decision record unchanged, implementation cleanup only). This distinction mattered — pass 2 remains the single citable record of the load-bearing decision, while passes 3-6 layer corrections and refinements on top.

### What didn't work

- **Retro discipline slipped.** Passes 1 and 2 have dedicated retros. Passes 3, 4, 5, 6, and ADR-6 pass 1 do not — they are captured here in this consolidated retro, but strictly DoD was not met per-pass. The excuse is "passes 3-6 were corrections within hours of each other, not full refine passes" — but W1 doesn't grade on effort. Every pass needs its retro. Filing a consolidated retro is a recovery pattern, not a substitute.
- **ID prediction errors, 4 instances.** In pass 2, 3, 4, and 5 revision log entries, I predicted the learning id ahead of `arra_learn`, then the actual id came out different (slug truncation / reordering). Each required a backfill commit. Fix next time: always write "filed as <slug>-derived-id" in revision log post-hoc, never predict forward.
- **Vendor pricing trust.** Pass-0 ADR-6 baseline's "$35/account" GoLogin estimate was carried forward unverified through several subsequent sessions (including this one's pre-ADR-6-refine state). When stakes involve vendor-cost comparison, verifying current pricing on the vendor's own page should be the first research step, not a late-stage correction.
- **Steel Browser surface enthusiasm.** I recommended self-hosted Steel as "interesting Phase 1.5 candidate" before doing deep research. Stars + Apache 2.0 + active commits are lagging indicators of production maturity. Status page + open bugs + incident history are leading indicators. Check leading indicators first.
- **ADR drift to design-spec.** I grew §ADR-4a from ~60 lines (pass 1) to ~450 lines (pass 5) across 5 passes without noticing the section had drifted past ADR scope into implementation-spec territory. Future: any section exceeding 150 lines OR 2-3× the largest sibling should trigger an extract-consideration checkpoint in the pass itself, not at user review.
- **Edge tool complexity.** Pass 4 and pass 6 required Bash-level file manipulation (sed-based pre/post split) because Edit's string-replacement model struggles with 300+ line sections. This worked but is error-prone — a failed concat could have corrupted `adr.md`. Safer future pattern: read → Write → verify in same session, not split-and-concat.
- **No `arra_trace_link` between passes.** I filed `arra_supersede` pass-1 → pass-2, but did not file `arra_trace_link` to build a pass-chain traversal path in Studio. Retros note this; future sessions should add to checklist.

### What would make the next session cheaper

1. **Start-of-pass checklist that probes for drift signals.** Three checks: (a) is any ADR section > 150 lines? (b) is any vendor cost / feature cited in ADR without a dated verification? (c) are any `#provisional` or `[AWAITING_THREAD]` markers untouched for > 14 days? Each signal triggers a specific mitigation.
2. **Standing learnings cache for this repo.** Next architect session's Step 1 (grounding) should load the cross-role prior-art learnings without re-searching: pool data model, withdrawal-queue source-type split, stale-processing triage, W10 constraints register. Put them in a pointer file at `docs/design/_prior-art-index.md` or equivalent — Studio can surface but a flat pointer is faster.
3. **Vendor-evaluation template.** Every future vendor option consideration runs through: pricing page (dated) → status page → open bug tracker → changelog → fintech adoption signals. Five-item checklist, 30 minutes. Time-boxed to prevent surface enthusiasm.
4. **Cross-ADR impact scan.** When a pass changes a load-bearing claim (like ADR-6 dropping idle-shutdown), an immediate downstream scan of other ADRs' §Consequences and §Decisions is mandatory — not optional. I did this manually for ADR-4a §Consequences (ii) cold-start framing, but a formalized scan-checklist would catch me next time I forget.
5. **Pass-to-pass `arra_trace_link`.** Make it habit alongside `arra_supersede`. Takes 1 minute, enables Studio trace-walker.
6. **Adopt strict retro discipline.** Even if passes are minutes apart, each pass gets its retro — OR, if consolidated is acceptable (as here), the retro-deferral must be an explicit choice logged in the revision log, not forgotten-about.

## Meta-pattern captured — user peer review drives pass cadence

This session's signature pattern, recorded here for future architects to notice:

```
Pass 1 draft → user review → pass 2 ratifies + adds context (pool, defense-in-depth)
Pass 2 ship → user catches something (required_method redundant) → pass 4 fix
Pass 4 ship → user catches something (per-row budget, balance drift, sweep revert) → pass 5 fix
Pass 5 ship → user catches something (ADR too deep) → pass 6 refactor
Pass 6 ship → user asks "ADR-6 valid?" → ADR-6 pass 1
```

Each pass is **triggered by a user observation** that I missed during drafting. This is expensive if the user is busy, but produces dramatically better ADRs than solo drafting would. The *shape* of this pattern — call it "review-driven pass cadence" — is how payment-system architecture should work while the fleet is still small and humans review every major claim.

When implementation agents eventually exist in this repo, the equivalent pattern will be: implementation agent tries to code against the ADR, finds an ambiguity, files a thread, architect refines. The mechanism will differ but the pattern — external consumer of the ADR surfaces blind spots — will be the same.
