## Honest feedback

- **Step 2c's "already has a next link" case deserves a proper handling note in the workflow spec.** The current spec says "If more than one plausible other-repo trace exists → pick the most recent and file a one-line note in the retro". It doesn't cover what happens when the chosen prev trace already has a forward link (which is what happened here — bank-bot `56d3712c` was already claimed by an earlier pg-writer W2). The right behaviour is what I did: skip the link, file the `#cross-repo-sync` learning as the semantic record, note the gap in the PR body and retro. But the workflow spec doesn't describe this branch, so an agent could plausibly try to force the link or fail the precondition. **Proposed addition to Step 2c:** *"If `arra_trace_link` errors with 'already has a next link', accept it as a chain-already-established state — the semantic record is the `#cross-repo-sync` learning, not the graph edge. Note in the PR body and retro that the forward slot was taken."*
- **The amend-path retro template could recommend reading the existing PR body first.** When amending, the agent needs to internalise what v1 already claimed so v2's body doesn't contradict or duplicate. I did it out of instinct but the spec doesn't call for it.
