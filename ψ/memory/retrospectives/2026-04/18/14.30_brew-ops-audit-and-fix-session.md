## AI Diary

I started this session thinking I was onboarding `arra-oracle-v3` as a third peer in the vault and that the task was mostly mechanical — move `.agent/`, run `setup-symlinks.sh`, done. That was wrong within the first 20 minutes.

The first real surprise was the case-insensitivity trap. macOS treated `soul-brews-studio` and `Soul-Brews-Studio` as the same directory, so `mkdir Soul-Brews-Studio` silently landed in the lowercase one. Git, being case-sensitive, recorded both names differently across branches. I didn't see the problem until I listed with `ls -la` and noticed one name. The two-step `git mv` through a temp name was the only safe way to rename without `-f` (charter forbids force flags). Lesson: on macOS, always verify casing with `ls -la` immediately after a rename, and always use two-step renames for case-only changes.

Then the user asked me to check sync — and I went deep. `arra_search` for `soul-brews-core` came back fine (principles intact), but once I started comparing disk file counts to DB row counts I found the bloat. FTS had 1695 rows for 598 docs. That felt wrong immediately. I almost jumped into writing a fix before realizing I should check git branches first — and lo and behold, `local/all-prs` already had commit `3c8f55b` that literally described the same bug with the same numbers pattern ("1268 FTS rows for 141 unique ids after 9 reindex passes"). The user had figured this out before me and just hadn't merged yet. That was a humbling moment — the "external brain" (P-003) really is external: the answer was in the vault and in git, waiting to be read.

The `bank-bot<` path was a surprise too. I found it while running `SELECT source_file FROM oracle_documents WHERE source_file LIKE '%<%'` on a whim — mostly to check whether my audit queries were sensitive enough. I wasn't expecting a hit. The fact that it existed for >24h without detection is exactly why workflow-5 §4 (path corruption check) needs to exist.

The hardest mental shift was realizing the workflow I was writing had to include a check for its own failure mode. When the user asked "can this workflow measure whether memory is understandable?", my first instinct was "sure, add a §16". But as I drafted it, I noticed I'd been making durable changes all session without writing a single `arra_learn`. I had 40+ tool calls of real work going to waste. §14d (current-session capture check) came out of that realization: the workflow has to protect against the brew-ops agent itself silently eroding P-001.

Vector search being broken in THIS session but provably working via HTTP was frustrating. I spent maybe 20 minutes chasing it before accepting that MCP stdio processes cache their LanceDB handle and there's no way to reload without killing them — and killing "the right one" risks killing this conversation. The honest call was to document it and let new sessions pick up the fix.

On writing `.agent/skills/brew-ops/references/workflow-5-memory-audit.md`: I initially drafted 15 steps then had to renumber to 16 to insert the coherence check. The renumbering was tedious (8 Edit calls) — a sign that the spec should have been more considered upfront. Next time I'll outline all step numbers before drafting.

## Honest Feedback

**What went well:**
- Demo-before-spec approach for §14: I ran the coherence check on 3 real threads first, found the gap in Thread 3 (vault case-rename), and used that finding to ground the §14 spec. The finding itself was compelling enough for the user to say "add §16 + capture today's work" — which was the right instinct. If I'd jumped straight to spec-writing, the §14d safety-net idea probably wouldn't have occurred to me.
- Respecting `local/all-prs` — my first instinct on FTS bloat was "write a PR to fix it", but checking branches first revealed the fix existed. Saved ~1h of duplicate work + a bad PR.
- `git mv` two-step for case-rename — no `-f`, no data loss, git sees the rename properly (`R100` in diff).
- The `arra_supersede` discipline for the superseded ids — P-001 is preserved, search still surfaces old content with warnings, and the old/new relationship is explicit.

**What went poorly:**
- **Session discipline failure**: I did maybe 5 hours of work before writing a single `arra_learn` or retro. If this session had been interrupted mid-way (battery, network, user pivot), the durable knowledge would have been in git commit messages only — fine for git blame, invisible to `arra_search`. The workflow-5 §14d check that I invented is literally an indictment of my own session behavior. **The right pattern**: after every P0 fix, immediately file the gotcha/decision as `arra_learn` before moving on.
- **Initial audit was too exhaustive**: I queried oracle_documents in 6 different ways before realizing the MCP stdio was stale and some of my "findings" were artifacts of the stale handle. Could have saved time by checking process ages + LanceDB mtimes first.
- **Auto-commit ambiguity**: The vault has an auto-commit hook that swept my work into a commit named `updated` without any detail. I flagged it but didn't ask the user whether the hook should have better messages. That's a gap — the commit message itself is now a lossy record.
- **Workflow renumbering (inserting §14 between §13 and §14 old) required 8 manual edits**: poor craftsmanship. I should have drafted the step list before writing prose.
- **Didn't run verify.sh before ending the session** — should have done a final `bash scripts/verify.sh` pass to confirm all symlinks + oracle DB + ψ counts are green post-changes.

**Open questions / handoff items:**
- **P0-2 (duplicate indexing)**: is the current "by design" classification actually what upstream wants, or is there an intent to dedup at search layer? Need input from the human / maw-js architect before a PR.
- **`bank-bot<` root cause**: which session wrote the original bad `project:` tag? Worth checking `bot-writer` retros from Apr 17 to identify if the LLM produced the `<` or a paste introduced it. Prevention depends on knowing which.
- **`.gitignore` for `.agent/`** in `arra-oracle-v3`: user has declined to touch it, but the symlink's absolute path means any future dev on a different machine will silently lose `.agent/` on `git pull`. Either the project needs `.agent` in `.gitignore` (following the `bank-bot` peer pattern) or `setup-symlinks.sh` must be a hard prerequisite documented in the README.
- **Commit-message hygiene**: the auto-commit hook produces `updated` messages. Worth proposing a maw task to generate better summaries (e.g., "N files via soul-sync + Y brew-ops audit changes") or at least tag auto-commits so they're greppable.

**What I'd do differently next time:**
- File `arra_learn` at the end of every P0 fix, not at end of session.
- Start every brew-ops session by opening a draft retro file and appending to it as work progresses (like a journal) — not writing it from scratch at end.
- Check `ps aux | grep bun` + LanceDB mtimes BEFORE running `arra_stats`, so I know which signals are fresh vs stale from the start.
- Outline workflow numbering before writing workflow prose.
