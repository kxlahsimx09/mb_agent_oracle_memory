## AI Diary

Mixed pass: the mechanical shape of the workflow went smoothly, but I tripped on two small things worth naming.

1. **XML parameter-tag syntax.** When I first called `arra_trace` I wrote `<parameter name="foundCommits">` with a stray space after `<parameter` in my head → the harness rejected it silently, so `foundCommits` never made it into the trace. The trace was created with `commit_count=0`. I only noticed because the response summary gave it away. Retried with the correct syntax and got a proper trace with 7 commits. The zero-content trace is left behind. **Lesson for next time:** when `arra_trace` returns `commit_count=0` on a call where I passed commits, immediately inspect before moving on — don't link an empty trace into the chain.

2. **Reading the commit range carefully.** 9791647's commit message says "Revert to full timestamp cursor with day-boundary reset." At first glance that read as "fully revert PRs #62 + eab43bc" — but reading the code I saw the day-boundary reset is *new*, not a restoration of older behavior. The previous doc section (I had just described it in the prior W2 pass!) had claimed "keep every same-day row"; the new code does NOT do that. The framing I landed on — "partial revert that preserves the late-night fix but drops full-scan cost" — took a minute of re-reading both the old and new branches of `isTransactionNew` to get right. If I had trusted the commit message alone I would have written a wrong doc update.

3. **3faa83a's "+5 minutes" is subtle.** The code compares `transactionDateBKK > nowDateBKK + 5` where both are `YYYYMMDDHHMM` ints. Literally +5 only equals +5 minutes when you're not crossing an hour or day boundary. At the minute boundary (e.g., cursor at `...:57`, +5 = `...:62`, which is a malformed timestamp that compares high against `...:58` within the hour but **won't match** the next hour's `...:02`). The code is OK in practice because future-dated SCB rows are typically hours-ahead, not minutes-ahead — but I kept the doc honest by calling it "5-minute clock-drift tolerance" rather than claiming perfect boundary semantics. Filing this as a minor observation; not worth blocking the PR over.
