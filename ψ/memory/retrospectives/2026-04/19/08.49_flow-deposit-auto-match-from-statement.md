**Non-obvious things I had to dig for:**

- The `expires_at` filter at `services/transactionMatcher.go:151-154` is subtle — expired deposits are excluded from pending-match but fall through to `linkPaidDeposit`, where they become the basis for `match_status="pending_review"` on the statement. That's the bridge to the slip-upload-admin-approve flow and I called it out explicitly in §Error paths so readers don't assume expired deposits are lost.
- `finalizeDeposit` orders deposit-update BEFORE wallet-update. A wallet-not-found or wallet-update error logs but **proceeds** to MDR distribution, statement update, transactions insert, SSE, and callback. I called this out as Q4a — it's either intentional (treat missing wallet as credit-lost, don't block partner earnings) or a drift worth a PR. I did not classify it myself because the code comment gives no hint and the commit history around this function is mostly refactors.
- Amount-only fallback was removed at `:124` with a one-line comment (`Amount-only matching removed — too high risk of false matches`). Q4d asks whether `resolveBankCodeFromPrefix`'s 15-entry map is the canonical allowlist of supported banks. The code doesn't say; I raised it because new-bank onboarding currently has no operator-facing path if the statement description lacks the two supported shapes.
- `mdr_shared` row is inserted **only if at least one partner was credited** (`:801-831`). I captured this in §Postconditions as a conditional so future readers don't assume the row is always present.

## Honest Feedback

**Was the flow boundary clear, or did scope creep across into a neighboring flow?**
The boundary was tight. The flow starts at "a `ts_deposits` pending row exists" (precondition, owned by `deposit-qr-request`) and ends at "callback fired" (terminal, same as `deposit-qr-request` Step 8 terminal). The `linkPaidDeposit` branch for expired deposits was the one place where scope could have crept — I kept it in §Error paths as a cross-reference to `deposit-slip-upload-admin-approve.md` rather than drawing a second branching arrow in the diagram, because the diagram's job is the happy path. Right call, I think.

**Are numbered sequence steps actually usable for impl pointers, or did a step aggregate too much?**
Step 7 ("atomic: ts_deposits→paid + wallets + MDR fan-out + mdr_shared + bank_statements→matched + transactions insert") aggregates ~130 lines of code across `finalizeDeposit` and `distributeDepositMDRFees`. Too much for one pointer line. I compensated in §Implementation pointers by giving Step 7 six sub-path bullets with line ranges for each sub-operation. It works, but it's at the edge — if `finalizeDeposit` grows another stage (e.g., fraud-check), Step 7 should split.

**Did Mermaid help or fight the diagram? Any step you wanted to express that Mermaid couldn't?**
Mostly helped. The one thing I wanted but Mermaid struggles with is the **three-trigger convergence** — I'd have liked a single visual that shows BankBot-ingest, 30s-ticker, and admin-re-match all pointing at the same `matchDeposit` entry. Mermaid's `alt` blocks would work but they'd triple the diagram's height for what's ultimately a "same code path, three callers" footnote. I opted for prose in §Purpose instead. The `Note over Payer,Bank` annotation for "upstream transfer (out of scope)" was the one Mermaid feature I did lean on — keeps the Payer visible as an upstream actor without giving them a misleading arrow.

**Should this flow have been split into sub-flows?**
Considered splitting `deposit-auto-match-from-statement` vs `deposit-auto-match-review-queue` (the SCB multi-candidate branch). Decided no — the review branch is 30 lines of code and its resolution path is owned by a different flow (`deposit-slip-upload-admin-approve`); splitting would have created a stub flow with no admin-side ratified counterpart. Kept as §Error paths + Q4c in the ratification thread so the human can ask for a split if they disagree.
