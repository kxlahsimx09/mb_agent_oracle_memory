## AI Diary

Started the session thinking this would be a drive-by W2 — only one substantive commit in the range. The doc update was mechanically straightforward: add a new sub-section, refresh a line, bump the baseline. The surprise was the **superseded claim** on the existing §3 summary line: the prior writer had documented `/:id/status` as a path-to-cancel, and the new code removed that path without updating the doc. Caught it on the re-read-the-post-change-file discipline (workflow §Step 4), not on the diff. That's exactly the failure mode the workflow warns about in §Common pitfalls — "reading the diff instead of the post-change file" would have missed the supersession.

The `telegram_send` 404 was the one moment I had to reach for the fallback protocol, and I'm glad it was written down. The learning-as-breadcrumb pattern for delivery failures is the right call: don't block W2 completion for a non-load-bearing channel, but leave a breadcrumb specific enough that a future session can re-send verbatim.

The non-transactional three-write in `CancelPayout` nagged at me. On one hand, the admin endpoint is synchronous and sub-second — a crash mid-sequence is astronomically rare. On the other hand, the existing `/confirm-completed` endpoint (§3.2.1) *does* run inside a MongoDB session transaction, and it's conceptually the same shape of work (queue + payout + wallet). Why is this one not? I didn't open a thread because I don't want to bikeshed a feature that's already shipped, but I documented the risk in both the learning and §3.2.3 prose. If it ever bites in production, the trail exists.
