## Honest Feedback

**Was the flow boundary clear, or did scope creep?** Clear. The temptation was to extend into `deposit-qr-request`'s bot-side contract (login, OTP, config fetch) — those are upstream bootstrap concerns for this flow, not part of it. Preconditions captured them by reference rather than unpacking. The harder judgment call was at the other end: do I include the `PUT /bot/balance` step, which technically isn't "deposit-auto-match" but ships on every tick in the same orchestrator? Chose YES, with a callout in the ratification thread (Q4). Reason: operationally inseparable — the bot ships statements and balance in the same `scrapeStatementSafe` / `scrapeStatementSafeForTransfer` function, and splitting the doc would fragment what is in code one unit. If human says split, I split.

**Are numbered sequence steps actually usable for impl pointers?** Yes. Loop-wrapped form unpacked step 4 (navigate portal) cleanly into SCB-UI vs KTB-REST-primary vs KTB-UI-fallback at the §Implementation pointers layer without cluttering the diagram. The `alt rows found / else no new rows` block was exactly what the `scb-dual-control-withdrawal` retro's Honest Feedback said was missing from the linear form — it visually separates the non-POST branch that is otherwise invisible. The 10-crossing cap was comfortable: loop container + alt container consume zero crossings, so per-iteration work had 7 crossings of 10 available.

**Did the mobiz-side breadcrumb accurately predict the bot-side step boundaries?** Partially. The breadcrumb named bot territory as "Steps 1 and 2 (portal scrape) and Step 9 (client callback ack)" on the mobiz numbering. Step 9's "client callback ack" was a misdescription — the bot doesn't participate in the mobiz→Client callback at all; that was probably breadcrumb-writer shorthand for "step 3 POST" and got miscounted. Corrected in my bot-side breadcrumb. Otherwise the contract shape (endpoints, JSON fields, dedup keys, KTB-vs-SCB matcher regexes) transferred verbatim and saved 15+ minutes of inference from code alone.

**Did the self-test surface any tag-ranking issues?** Yes — Test 3 exposed a ranking ceiling. The reverse-direction query `<slug> mobiz-payment-gateway` ranks all learnings with both tokens; my breadcrumb's 10+ lexical mentions of both terms could not overcome the noise from 8 other learnings about unrelated mobiz flows that also have both the slug concept in flow:* tags AND the mobiz-payment-gateway repo tag. This is the documented Known Limitation 2026-04-19 retrieval-quality issue — the index tombstone is the reliable escape. What would make future passes faster: either (a) Oracle tightens the phrase-proximity scoring on compound queries, or (b) spec lowers Test 3's acceptance bar to "any bot-side learning with this slug in top 10" (which passes here — `learning_2026-04-19_flow-deposit-auto-match-from-statement-bot-sid` ranks in top 10) rather than insisting on the breadcrumb id specifically. The mechanism still works via the index learning; the acceptance criterion is brittle to noise.

**Loop-wrapped vs linear — rendered comparison to flow #1.** `scb-dual-control-withdrawal` used linear and the retro called out step 3 + step 8 "aggregated too much" for crossing-cap reasons. Loop-wrapped on this flow had zero aggregation pressure — sub-decisions (SCB-UI vs KTB-API-vs-UI fallback) landed naturally in §Implementation pointers rather than squeezing into a single step label. Confirming §Design notes precedent: pick loop-wrapped when (a) cadence is correctness-relevant, (b) empty-case branch exists, (c) init phase differs from iteration, (d) a step would otherwise aggregate 5+ sub-actions. This flow met all four; `scb-dual-control-withdrawal` met (d) in hindsight but was authored before the framework existed.

**Diagram renders only locally so far.** Stage 1 grep CLEAN, Stage 2 `mmdc` produced 30KB SVG, no stderr. The visual GitHub PR preview check is still pending at retro time — noting explicitly so the next writer knows this pass closes that loop only when the PR is opened in a browser, not via API.

**The arra_trace parameter-parsing corruption is a real bug worth fixing upstream.** My first `arra_trace` call sent `foundFiles` as a newline-formatted JSON array inside the `<parameter>` block. The tool concatenated the entire XML fragment into the `project` field literally. This is the same class of path-corruption the Step 9d verify.sh gate was added to catch — but verify.sh doesn't scan the trace table, only learning source_files. Filed as a workflow-bug so the next writer doesn't repeat it AND so brew-ops knows to consider extending verify.sh to trace rows.

**Second-pass calibration of W8.** First pass (`scb-dual-control-withdrawal`) took several revision cycles for mermaid rendering. This pass had zero mermaid revisions — Stage 1 grep + Stage 2 mmdc together caught every issue before push. Authoring time was comparable to the first pass despite the loop-wrapped form's higher structural complexity. The workflow is maturing.
