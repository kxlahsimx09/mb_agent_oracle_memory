**Key non-obvious facts surfaced (and recorded as docstrings + the §Step-9 learning):**

1. **Wallet semantics branch on entry state.** This is *the* load-bearing detail of the flow. The entry-state test is read **before** the CAS flips status, so the branch decision uses the payout's pre-transaction status. For `failed` → re-deduct because `MarkFailed` refunded; for `waiting_to_review` → skip because `MarkWaitingToReview` deliberately never touched the wallet. Documented as the third paragraph of §Purpose — the spec would be incomprehensible without it front-and-center.
2. **Callback count is path-dependent.** `waiting_to_review` entry → 1 callback (this flow's `completed`). `failed` entry → 2 callbacks total (the earlier `failed` + this flow's `completed`). Same double-callback pattern payout-request §Resolved questions (b) flagged. Cross-referenced rather than re-asking.
3. **Fail-closed on insufficient balance** when `previous=failed`. The `balance >= totalDeduct` atomic guard inside the Mongo session transaction means the whole flip rolls back if the client spent the refund. This surprised me — I expected a force-deduct or a graceful admin-facing error path. The current design says "no." Flagged as §Open questions (a) for ratification.
4. **Queue row history rewrite.** Step 7 `$unset failed_at, error_message` on the `withdrawal_queue` row to match the `success` flip. The audit trail survives elsewhere (`ts_payouts.confirm_completed_reason` + `wallets_change_logs` + `mdr_shared`) but not on the queue row itself. Mild P-001 tension since queue dashboards key off the row. Flagged as §Open questions (b).
5. **MDR is inlined, not helper-reused.** The comment at L1907-1909 makes it explicit — `services.distributeMDRFees` is non-transactional and can't participate in the session transaction. Two MDR fan-out code paths now exist (inline here; helper for happy-path success). Same family as `topup-approve-mdr-distribution` §Resolved questions (b). Flagged as §Open questions (c).

**First-pass rule miss (fixed in commit `0543cab`, same-session).** User caught "diagram error" on initial push (commit `48ad761`). Two W8 §Mermaid safety rule violations:
1. **Rule 5 (second `:` in free-text tail).** Step 1 wrote `PUT /api/v1/payouts/:id/confirm-completed` — the `:id` path placeholder introduces a second colon after the arrow's message-delimiter colon. Mermaid sometimes renders these, sometimes crashes silently (same class as `deposit-auto-match-from-statement`'s first-pass failure). Fix: drop the colon, write `/id/` as a bare path segment. The URL is obviously a placeholder; the reader doesn't need the `:` syntax to recognise it as a path param. This rule is easy to miss because `:id` is muscle-memory from Fiber/Express route syntax — **any REST-path step in a mermaid message needs `:id` → `id` conversion**.
2. **Rule 6 (`;` as sentence joiner).** Step 5 wrote `... balance guard plus payout_confirm_completed change-log; if prev=w2r skip deduction`. The `;` crashed the Note parser's `word;<tag>` failure class even though the step isn't a Note. Fix: replace with `,` and read-as-prose ("... change-log, if prev=w2r skip deduction"). Branching in a single-line message is fine with `,`-separated clauses; reserve `;` for never.

**Lesson:** the W8 workflow file has a "safe template" at §Step 4 but doesn't enumerate the ":id muscle-memory trap" or the "branching-message-written-with-semicolon trap" explicitly. Both felt like subtle instances of the named rules rather than separate rules in their own right, so I read past them. Carry forward: when authoring a mermaid message that describes an HTTP PUT/DELETE on a resource-by-id endpoint, or that expresses an "if X then A else B" branch in one line, treat these as scripted failure modes and drop-colon / comma-join *before* the first preview. The fix cost was small (one commit, ~1 min) but the rule was explicit — I should not have needed the user to catch it.
