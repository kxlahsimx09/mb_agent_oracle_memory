Held the line on P-004: `[DRIFT]` is reserved for code-vs-written-spec divergence. There's no written spec to diverge from, so `[DRIFT]` is unavailable. The correct tool is a ratification thread.

## Honest Feedback

### Was the flow boundary clear, or did scope creep across into a neighboring flow?

Boundary held. The tempting creep was into **deposit-expiry** — I originally drafted a §Error paths bullet saying "a `checking` deposit can be auto-expired if `expires_at` passes before admin action" and had to delete it when I verified the scheduler only expires `status == "pending"`. The correct statement is "the scheduler ignores `checking`, so a slip-uploaded deposit parks indefinitely without admin action" — moved to §Related flows as a retention observation rather than an error path, because it's not an *error*, it's just what happens.

The other potential creep was the entire **deposit-qr-request** happy path. Tried twice to explain the matcher context in §Purpose; cut both times. The correct depth is "matcher exists, this flow is what you do when matcher cannot confirm" — one sentence, not a paragraph. Linked to the sibling flow doc for anyone who needs more.

### Are numbered sequence steps actually usable for impl pointers, or did a step aggregate too much?

Mostly yes, with one caveat. **Step 8** (the atomic Mongo session) is one diagram arrow but 5 sub-pointers in §Implementation pointers: CAS, approval fields, wallet $inc, change log, MDR loop, transaction row. The diagram can't show the internal fan-out without blowing past the 10-message cap. Solution in the doc: one bullet per sub-component with its own `@c5270b3` pointer — a reader following the code can still navigate.

If I had to do it again I'd maybe split step 8 into two diagram messages (`8a: deposit CAS + wallet credit` / `8b: MDR distribute + txn record`) but the second "message" is still a self-arrow, so it doesn't actually buy much clarity. Leaving it as a single step with bulleted sub-pointers is fine.

**Step 5** is similarly multi-faceted (duplicate check + persist + SSE publish) but the sub-steps are all "process the Thunder result and land it in the DB" — that's a single logical atom and the bulleting is natural.

### Did Mermaid help or fight the diagram?

Helped. The `Note over Payer,Client:` out-of-band pseudo-step for the Payer→Client UI handoff is exactly the kind of "this is context, not a contract" marker you want at the top of a flow where one actor (Payer) only exists to set up the scene. Without that Mermaid feature I'd have had to either (a) add Payer as a participant and draw a dashed arrow to Client (looks like a real contract), or (b) start at step 1 and leave the reader wondering where the slip came from.

Fought me on one thing: self-messages (`Gateway->>Gateway:`) render as a small loop icon that doesn't convey the size of what's happening inside. Step 2 (CDN upload) and Step 8 (atomic Mongo txn) look equally weighted in the diagram, but Step 8 is five times the code. The prose compensates, and the impl-pointers section makes the asymmetry obvious to anyone reading top-to-bottom.

### Should this flow have been split into sub-flows?

No. I considered splitting slip-upload-and-verify (steps 1–6) from admin-approve (steps 7–10) into two separate flow docs. Rejected because:

- Both halves are meaningless without the other. "Slip upload alone" is a dead-end (deposit parks in `checking` forever), "admin approve alone" is unreachable without a prior `checking` state (the CAS requires `IN [pending, checking]`, but the payer path doesn't produce `checking` — only the matcher's divergence cases and slip upload do).
- The two entry points (Client's `POST /upload-slip` and Admin's `POST /:id/upload-slip`) converge on identical state (`checking` with the same slip fields). Splitting would force the admin path to be documented twice.
- The Alternate entry section handles the ~5% case cleanly without needing a third doc.

One-sentence test held: "When bank-statement match fails or is skipped, the client forwards the slip, the admin confirms, the wallet credits." That fits on one line. One flow.

### What I'd change about W8 itself

- **Stacked-PR case is under-specified.** The W8 workflow (`workflow-8-flow-map.md`) assumes each W8 PR targets `main`. When the flow's `§Related flows` link points to another flow doc that lives in a still-in-flight sibling PR, there's no written guidance. I ad-libbed: branch off the sibling branch, PR `base = sibling-branch`, call out the stacking in the PR body. Worked, but next time I'd want a W8 clause describing it explicitly so the next agent doesn't re-derive the pattern.
- **Two threads instead of one.** W8 Step 7 anticipates a single ratification thread for reverse-engineered flows. This pass produced two (`#6` ratification, `#7` wallet-op operation divergence). The second one is not about ratifying the *flow* — it's about a code-vs-code semantic gap the flow happens to expose. Current W8 doesn't distinguish "flow-intent ratification" from "side-discovery ratification". Noted; not sure it's worth codifying.
