## AI Diary (mandatory)

Three things bit me during this session.

**1. CLAUDE.md is denser but MORE out-of-date than I expected.** The workflow file warns that CLAUDE.md here is ~20 KB and "unusually detailed" and that P-004 still applies. I was still surprised by how many real features the code has accumulated that the doc simply doesn't mention (16 drifts is a lot for a 10 KLOC repo). The most load-bearing gaps — KTB batch transfer, SCB approver API interception with backend cross-check, the two-phase OTP protocol, the direction-aware cursor module — are all changes that clearly landed under time pressure to stop incidents, without docs following. This is the textbook pattern P-004 was written for: code grew, documents didn't. My instinct was to treat CLAUDE.md's detail as trustworthy; the workflow's P-004 reminder saved me from propagating stale claims.

**2. The .env.example secret dilemma was the hardest call.** The file ships with what looks indistinguishable from a real 64-char hex `BOT_SECRET` and a real-looking `API_URL=https://api.dpay.rest`. Per the workflow's Escalation clause, credential ambiguity halts and goes to `security_auditor`. But there is no `security_auditor` role on the bot side yet. I chose to: (a) file a thread with the specific value inline (private), (b) mark it `[UNVERIFIED] U-1` in the public doc, (c) NOT narrate the value in `docs/current-system.md`. This is the least-destructive interpretation of the escalation clause when the target role doesn't exist. If it turns out to be a real leak, I'll have been over-cautious, which is fine. If it turns out to be a rotated placeholder, a one-line confirmation from a human closes it. The downside is that I opened a PR with an unresolved security-tagged thread dangling — I've been explicit about this in the PR body.

**3. The symlinked `.agent/` made git status look dirty in a confusing way.** `?? .agent` shows up in `git status --porcelain` because `.agent/` is a symlink to the central memory repo (per AGENTS.md §11), and there's also an orphaned `.agent.bak-20260417-102822/` from the symlink migration earlier today. Both are untracked but neither is "my work in progress" — they're ambient state from the agent infrastructure. The workflow's precondition "`git status --porcelain` is empty" would have made me stop and restart if I'd taken it literally. I chose to proceed after confirming the untracked paths were the agent substrate, not real bot-code changes. Noted this inline for the next baseline runner.

What I'm most pleased with: §3 per-bank adapters came out readable despite the volume. The trick was to describe each flow as a numbered list of the *real* steps the code takes (with cited line ranges), and treat any variance from CLAUDE.md as a separate `[DRIFT]` row rather than weaving corrections into the narrative. That keeps the doc useful even when CLAUDE.md eventually catches up.

What I'd do differently: I spent too much time reading every line of `banks/scb/approver.js` when a grep-for-structure + sampled reads around the OTP/intercept blocks would have been enough. The workflow's 60-minute target is achievable but only if I trust summary-over-transcription harder.

## Honest Feedback (mandatory)

**What the workflow got right:**
- The pinned-commit discipline saved me once — about halfway through I saw the workflow hint say "if the commit moves mid-workflow, stop and restart" and I went back and verified `HEAD` had not moved. It had not, but the reflex to check is worth embedding.
- The "bulk-file threads instead of hard-halt" change (versus mobiz's workflow) is right for this repo. Bot code is changing fast; hard-halting on the 5% would mean perpetually re-running baselines that never finish.
- The explicit "never narrate credential paths publicly" clause forced me to think about U-1 carefully instead of reflexively dumping the value into the doc.

**What the workflow got wrong:**
- The "DRIFT count" rubric is missing. mobiz's first baseline produced 10 drift markers in a larger codebase; bank-bot produced 16 in a smaller one. That's not a defect — CLAUDE.md + README here are more ambitious in scope, which means more surface area to drift. But the workflow's DoD has no "if DRIFT > X, flag" threshold. Next version should say something like "≥ 10 DRIFT markers on a first baseline → file a `#decision` learning about CLAUDE.md update velocity".
- The template's §3 assumes "~200 lines per bank" as the spin-out trigger. SCB came out around 85 lines, KTB around 120. Fine at this baseline, but when KBANK lands there will be pressure to fit four banks into one §3 and split becomes inevitable. The template's "optional" per-bank doc guidance should include a softer trigger (e.g. "any bank whose flow has more than 3 production-incident callouts in code comments").
- `.env.example`-class secrets are a real category the escalation clause doesn't handle well when no `security_auditor` role exists yet. Fleet should spin up a `security_auditor` for bot side sooner than later — even if it's just another `technical_writer` instance with a security tag for now.

**What I'd tell the next agent running this workflow:**
- Read `workflow/scb-transfer.md` BEFORE you read `banks/scb/approver.js`. It's the insider narrative and it maps the exact sequence of phases — you'll grok `approver.js` in half the time.
- When you see a comment like "// observed on 2026-04-14 on bot 8204104078" in the code, it's an anchor: search the commit history for the date + bot number, and you'll find the PR that added the fix. That gives you the *why* behind the defensive code and it's worth citing in §8 DRIFT rows.
- Do NOT try to read `banks/ktb/statement.js` linearly — it's 936 lines and half of them are the API-first path. Grep for function starts first, then sample only the functions you need to cite.
