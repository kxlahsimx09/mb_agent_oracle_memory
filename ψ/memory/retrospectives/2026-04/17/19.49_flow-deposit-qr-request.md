## Honest Feedback

**Was the flow boundary clear, or did scope creep?**
Mostly clear. The main temptation was to include the admin slip-approval sub-flow (`UploadSlip` → `checking` → admin approves), because it *ends up paying* via the same wallet-credit path. I resisted and filed it as a queue item under §Related flows. Reason: the actors, auth, and terminating action are all different. If I'd merged it, the diagram would have gained an Admin participant and a JWT-auth path that would have doubled the complexity.

**Are numbered sequence steps usable for impl pointers?**
Step 2 is suspiciously heavy (validate sig + rotate bank + gen PromptPay + persist) — it's technically one "actor-crossing boundary" from Merchant's view but four sub-decisions on our side. I listed all four as nested pointers under Step 2, which works but is ugly. If a future W8 pass on this flow revisits, consider whether Step 2 should be split into 2a/2b — but that's a format question, not a content question.

**Did Mermaid help or fight?**
Helped. 8 steps render cleanly. One thing I wanted to express but couldn't: the 30-second retry loop on still-unmatched statements (Step 6→7 retry cycle). Mermaid has no natural "this hop repeats until condition" notation. Worked around it in §Error paths prose.

**Should this flow have been split into sub-flows?**
No. 8 messages is a clean count, and splitting would produce two flows (creation, reconciliation) that only make sense together. The merchant's experience is *one* flow — that's the actor-level truth.

**W8 workflow itself — candidate clarifications.**
1. The example in `workflow-8-flow-map.md` §Step 5 uses `[UNIMPLEMENTED]` for a `BankBot->>Bank: login + submit transfer` line. That's ambiguous — is the step unimplemented because the bank-bot repo doesn't have W8 yet (→ should be a breadcrumb, not unimplemented), or because the bank-bot isn't doing the action (→ genuinely unimplemented)? I introduced `// ext:` to disambiguate. Suggest the workflow pick one:
   - Option A: use `// ext:` for cross-repo external actors where the other side is owned by us but not in this repo.
   - Option B: keep `[UNIMPLEMENTED]` and require the paired learning to specify which of the two meanings.
   Flagged in the doc header as "marker conventions used in this doc" so future readers don't get confused.
2. The `// impl-level` marker on the cross-link line reads like the cross-link itself is impl-level. I think the intent is "this line lives in the impl-level doc" — worth one sentence of clarification in the workflow.
3. No guidance on how long the `[RATIFICATION_PENDING]` header stays. What if the ratification thread is never answered? Is there a decay rule (re-ask, auto-close, file a `#missing-ratification` learning)? I'd default to "re-ask weekly; after 30 days, file `#missing-ratification` and promote the doc to a lower-trust claim" but the workflow is silent.

**The one thing that surprised me.**
`finalizeDeposit` guards on `status: "pending"` (line 594). Slip-uploaded deposits in `status: "checking"` are invisible to the happy-path matcher. That's a *deliberate* guard — admin must approve the checking-state via a different code path. I almost missed it; caught it when cross-referencing `matchDepositKTB` (pending-only) vs `matchDepositSCB` (paid+expired via `linkPaidDeposit`). This kind of status-based fork is hard to express in a flow doc; hence the §Related flows breadcrumb.
