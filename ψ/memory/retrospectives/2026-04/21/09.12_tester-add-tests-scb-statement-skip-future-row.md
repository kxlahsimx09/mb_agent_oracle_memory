# tester session — SCB statement future-date guard test

This session executed `workflow-2-add-new-test-case.md` end-to-end
for one regression tripwire test. The user surfaced the prior-known
SCB future-row bug (Oracle search hit on the 2026-04-18 learning)
and asked for a workflow-2 design. After scope confirmation, the
test was drafted, run, fixed for one mongosh formatting quirk, and
shipped — one PR, no hand-offs.

## Tests added this session

### test-scb-statement-skip-future-row.sh

- **Gap closed:** new row in `docs/test-coverage-gaps.md` —
  "statement / SCB statement future-date guard" (priority 🟢,
  regression tripwire).
- **PR:** #253 (mobiz-payment-gateway) + companion 7337e54 in
  `mb_agent_oracle_memory` for the symlinked workflow doc registration.
- **Setup hazards designed out:**
  - Pre-clean `bank_statements` for the test account (cursor=0 baseline)
  - **Buddhist-year date format** in `/admin/add-statement` calls — the
    bot's parser strips +543 back to Gregorian; emitting Gregorian
    here would land timestamps ~543 years in the past and the row
    would pass the guard trivially (silent test-passes-for-wrong-reason)
  - Mock-bank render sanity check (`GET /api/account/statements`)
    confirms injected rows reach the page the bot scrapes
  - `MAX_WAIT=180s` covers SCB login + `viewerLoop` 30s cadence
  - mongosh `Long('...')` stringification stripped via
    `grep -oE '[0-9]+'` so bash numeric compare works
- **Notable design choices or surprises:**
  - **Cursor lives in MongoDB, not a local file.** The backend's
    `GetLastStatementDate` (`controllers/BotConfigController.go:743-794`)
    is just `MAX(transaction_date_bkk)` per direction over the
    `bank_statements` collection. So the "cursor not poisoned"
    assertion is a single MongoDB query — no need to mount the bot's
    `/data/` volume or parse cursor JSON. Did not expect this until
    Step 2 reading; would have over-engineered the test otherwise.
  - **Mock-bank `/admin/add-statement` had everything needed.** No
    fixture PR dependency, no hand-off to `mock-bank-sync-check`.
    The endpoint accepts custom `date`+`time` with no past/future
    validation. This is the test that would force classifying
    `/admin/add-statement` from FIXTURES.md TODO list — it's a
    **fixture** (simulates production-plausible bank data shape)
    not just an admin utility. Could close one TODO checkbox in
    FIXTURES.md as part of follow-up.
  - **Buddhist year gotcha** is non-obvious — I almost emitted
    Gregorian (`yyyy:04d`) and would have shipped a test that
    passes for the wrong reason. Caught only by carefully reading
    `bank-bot/banks/scb/statement.js:280-283` which does
    `if (year > 2500) year -= 543`. Worth flagging in a
    follow-up arra_learn for future SCB statement tests.

## AI Diary

This session went much more smoothly than the prior SCB post-OTP
session and that contrast is itself the lesson.

The user asked me to design a test off the prior-known SCB
future-row bug. Step 1 (paraphrase scope) was fast — the bug was
already documented, the fix was already merged, the test type
(regression tripwire) was obvious. Step 2 (read source) revealed
two things I hadn't expected: (a) the cursor lives in MongoDB
computed at read-time, not a local file, which simplified the
assertion approach significantly; (b) the parser converts Buddhist
year → Gregorian, which became the key gotcha for the test setup.

Step 3 (mock-bank readiness) returned all-green: `/admin/add-statement`
was already there, accepted custom timestamps without validation,
and the SCB statement page rendered injected rows in the format
the bot's parser expected. That meant **no hand-off, no PR
dependency, no waiting for another agent** — straight to draft.

Drafting was mechanical mirror-copy from the SCB post-OTP test for
infra setup, but the assertions were structurally different —
based on `bank_statements` collection state rather than
`withdrawal_queue` flow. The structure ended up cleaner because
the failure mode is much more local (parser-level guard, single
file).

Runtime: first run failed only on assertion 4 (cursor compare)
because mongosh in this MongoDB version stringifies `Long` as
`Long('202604210857')` instead of plain `202604210857`. Fixed with
a `grep -oE '[0-9]+'` in the eval pipeline. Second run all-green.
Total iteration: 2 runs, ~5 minutes.

The biggest takeaway: **when mock-bank readiness checks pass on
all 3 surfaces, workflow-2 collapses from a multi-PR hand-off
sequence into a single ~30-min PR.** The hand-off discipline from
the SCB post-OTP session paid forward — `/admin/add-statement`
existed because past sessions had built it, and FIXTURES.md
catalogued it well enough that I knew to check rather than assume.

## Honest Feedback

**What worked well:**

1. **Oracle search → learning → workflow-2 pipeline is now
   well-trodden.** The user's prompt "ค้น memory เกี่ยวกับปัญหา
   statement scb แสดงวันที่ในอนาคต" surfaced the exact learning
   in one query (hybrid search ranked the SCB-statement-future
   learning #6 by score, but the FTS results made the topic
   immediately findable). From there to a designed test was ~20
   minutes of reading + presenting. This is the intended use of
   the vault; it actually worked.

2. **Cursor-as-derived-state is testable without mocking** —
   a major property worth highlighting in a future "patterns
   for SCB tests" doc. Backend computes `MAX(transaction_date_bkk)`
   on every `GetLastStatementDate` call, so MongoDB IS the
   ground truth. Tests can manipulate `bank_statements` directly
   AND can verify cursor state with a single query, no separate
   mock or storage.

3. **Buddhist-year gotcha is the kind of thing that would have
   flake-d this test forever.** Catching it during Step 2 reading
   (not at runtime) saved a multi-hour debug cycle. Reading the
   source carefully BEFORE writing the test paid off — the
   `if (year > 2500) year -= 543` line is a one-liner that's easy
   to miss in a glance but central to the test's correctness.

4. **No mock-bank changes meant no cross-repo coordination cost.**
   The retrospective for the SCB post-OTP session called out the
   "symlinked agent files break the one-PR-per-test contract"
   refinement; this session benefited from the post-OTP session
   already having absorbed that lesson — the workflow doc commit
   in oracle repo went straight in without surprise.

**What was harder than expected:**

1. **mongosh `Long('...')` formatting** ate one full test iteration.
   Worth adding to the integration-test-writer SKILL: when querying
   numeric BSON fields via mongosh in a bash subshell, always pipe
   through `grep -oE '[0-9]+'` to strip wrapper syntax. The
   mongosh version on this docker-compose is newer than what most
   existing tests assume — older mongosh would print plain numbers.

2. **Test isolation across runs** — the second run dump showed two
   LEGIT rows (one from the failed first run, one from this run).
   The pre-clean step deletes from `bank_statements` but **does not
   reset mock-bank's in-memory `target.statements` array** (which
   the bot scrapes from). So the bot saw both timestamps and stored
   both. Did not affect the test result (FUTURE row still excluded,
   guard still works) but is a cleanliness gap. Could add a
   `/admin/reset` call at start, OR document this isolation
   limitation. Filing as TODO in my next session.

3. **Almost shipped a wrong-Buddhist-year test.** First instinct
   was to emit `f"{t.year:04d}"` — Gregorian. Caught it during
   self-review but only because I went back to re-read the parser
   source at Step 2. Workflow-2 Step 2 says "read the feature under
   test" but doesn't emphasize reading carefully enough that you
   notice subtle invariants like timezone/year format. A small
   note in Step 2 — "look for any year/timezone/locale conversion
   in the parser" — would help.

**What I would do differently next time:**

- Keep the FIXTURES.md TODO checkbox audit-and-tick part of the
  PR if the test consumes one of the listed candidates. This PR
  uses `/admin/add-statement` and arguably should classify it as
  fixture-vs-utility per thread #28's audit shape. Did NOT do
  that this session — left as follow-up. Bad habit forming if I
  let this slip every time.
- Before drafting, write the date/time computation in Python
  one-liners (with `TZ=Asia/Bangkok`) and `echo` them to verify
  the format matches what the parser expects. Saves a debug cycle
  if the format is wrong.
