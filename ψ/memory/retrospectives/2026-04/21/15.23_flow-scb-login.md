## Honest Feedback

- **Was the flow boundary clear, or did scope creep across into a neighboring flow?** Boundary stayed clean. Scope explicitly stops at `saveStorage` (Step 14) and excludes balance scrape (`app.js:397`) and `reportStatus('online')` emission (`app.js:1132`) — both are caller responsibilities documented in `scb-dual-control-withdrawal §Postconditions` and `bot-bootstrap-and-status-reporting`. Same scope rule as `ktb-login-with-otp` Q3, which kept this pass uncontroversial.

- **Are numbered sequence steps actually usable for impl pointers, or did a step aggregate too much?** All 14 steps map cleanly to single `// impl:` lines. The one judgement call was Step 4 (post-nav `dismissPopups`) — the helper has eleven popup-class branches, but expanding them into the sequence would have ballooned the diagram past readability. Compromise: Step 4 stays as one bracketing step in the diagram; the eleven classes live in §Implementation pointers. Q4 in the ratification thread asks whether this compression was right.

- **Did the mobiz-side breadcrumb (if any) accurately predict the bot-side step boundaries?** N/A — bot-first flow, no mobiz sibling.

- **Did the self-test surface any tag-ranking issues? What would make future passes faster?**

  Yes — same pattern as `ktb-keepalive-session-rotation` (2026-04-21 morning pass): top-10 ranking miss on compound queries because the bot-side flow corpus has grown to 7 docs (now 8 with this pass) and the breadcrumbs all share `cross-repo-sync` / `flow:` / `bank-bot` / `repo:cross` tokens. The unique slug ranks last, not first.

  Three things would make future passes faster:

  1. **A trace-side tool to attach learning IDs post-hoc.** Step 9c Test 4 is the cleanest acceptance test (trace.foundLearnings explicitly contains the breadcrumb), but Oracle's current build does not expose `arra_trace_update_found_learnings`. Adding it would make Test 4 pass deterministically rather than always-fail-by-design.

  2. **Breadcrumb body should lead with the slug + bot-first marker as the first phrase.** My breadcrumb body opens "flow cross-repo breadcrumb (bot side) — scb-login is a bot-first flow with no mobiz-payment-gateway counterpart." That puts `scb-login` at character ~50 — too late for FTS ranking against breadcrumbs that mention `scb` in their title. Future passes should consider starting the body with the slug verbatim ("scb-login: bot-first flow ...") so token-position weighting helps.

  3. **A specific-term verification query in addition to the compound-query top-10 acceptance.** The current spec asks whether the breadcrumb ranks top-10 on compound queries — but that test gets harder every time the bot-side corpus grows. A specific direct-id-or-unique-phrase lookup (like my "scb-login bot-first credentials handshake" rank-1 verification) is a more durable indexed-and-findable proof. Worth proposing as a Step 9c Test 5 in a future W8 spec edit.

- **Was the comparison with `ktb-login-with-otp` useful?** Very. The KTB doc was the template — same actors structure, same `[CROSS-REPO: bot-first]` framing, same scope-stops-at-saveStorage rule, same `// reverse-engineered:` claim line. Authoring time benefited a lot from having a sibling to read — first 30 minutes were template adaptation, not fresh structuring. Empirical evidence that bot-side flow-doc count compounds positively: the 7th doc was easier to write than the 1st (`scb-dual-control-withdrawal` 2026-04-19, took ~3 hours including thread; this one took ~1 hour).

- **Anything surprising about the SCB code itself?** Two things:
  1. The `dismissPopups` helper has more popup-class branches (eleven) than I expected from reading `scb-dual-control-withdrawal`'s impl pointers — that doc references "session-kicked, session-expired, soft-token, MuiDialog catch-all" as if they were the main four. The other seven (Transfer-AddNewRecipientPopup, promotional banners ×6, MuiSnackbar, MuiDrawer, MuiBackdrop, generic ตกลง, generic close-button) all matter and the production-incident annotations (628 false-positive Escape attempts on bot 8204104078, 13 lost payouts) attached to specific branches make clear they each guard against a real failure class. Worth bringing forward into the dual-control doc on a future revision.
  2. The storage-key convention mismatch (`app.js:254` computes `${config.bank_code}-${role}` and `loginIfNeeded` at `:247` recomputes the same string from `role` alone) is fragile. Both functions independently produce `scb-maker` / `scb-approver` / `scb-viewer` and they happen to agree. If `app.js` ever passes a different separator or prefix, session reuse silently breaks (no error — just creates a fresh storage file at the wrong path). Filed as `[DRIFT-scb-storage-key-convention]` and asked in the ratification thread whether this should queue a W4 to introduce a shared constant.

- **Anything to recommend for the next bot-side W8 pass?** Start with the slug + bot-first marker as the first phrase of the cross-repo-sync breadcrumb body (per Honest Feedback bullet 2 above). Otherwise, the workflow is now well-precedented — three login-flow extractions (`ktb-login-with-otp`, `ktb-keepalive-session-rotation`, `scb-login`) all followed the same shape and the spec's Step 9c known retrieval limitation has been confirmed three times running.
