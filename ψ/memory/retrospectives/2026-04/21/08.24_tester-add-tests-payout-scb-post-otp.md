## Tests added this session

### test-payout-scb-post-otp-waiting-to-review.sh

- **Gap closed:** new row in `docs/test-coverage-gaps.md` —
  "withdrawal-queue / SCB post-OTP ambiguity → waiting_to_review
  dispatch" (priority 🟢, regression tripwire).
- **PR:** #252 (mobiz-payment-gateway) + companion 1531dc7 in
  `mb_agent_oracle_memory` for the symlinked workflow doc registration.
- **Setup hazards designed out:**
  - `working_status: 'ready'` set in MongoDB after bank create
  - `method` array `["deposit","payout"]`
  - mock ledger system + client + customer accounts registered
  - `withdrawal_queue` polled via MongoDB direct (not REST — REST lags
    async MDR distribution)
  - timeout path → `TEST_RESULT=1`
  - fixture pre-flight HTTP probe of `/admin/scb/break-otp-confirm`
    fails early if the mock-bank rebuild missed the new endpoint
- **Notable design choices or surprises:**
  - **Container alignment trick** (non-obvious but reusable): the test
    uses `BANK_ACCOUNT=9999999999` — the default DOCKER_MODE bot
    container's account — so the `index.html` fixture probe (which
    fires at page load before `/api/login` sets the session cookie)
    falls back to the matching mock-bank env default. Avoids the need
    to pass `?account=` query param like the KTB test does. Documented
    in the test header + FIXTURES.md gate condition #2.
  - **Expected-green from day 1** (regression tripwire), not
    forward-looking like the KTB analogue. The dispatcher branch at
    `bank-bot/app.js:1645/:1714` and the approver return at
    `bank-bot/banks/scb/approver.js:582-590` were both already
    landed before this test was written — so the test asserts the
    desired-and-current behavior, locking it in for future refactors.
    Reflected in `docs/test-index.md` status `VALID` (not `UNKNOWN` or
    forward-looking).
  - **Runtime: 90s to terminal status.** SCB dual-control (maker
    submit → approver fresh login → fetch OTP → confirm) is
    significantly slower than KTB single-transfer. `MAX_WAIT=600`
    gives plenty of margin. Worth knowing for future SCB-flow tests.

## Honest Feedback

**What worked well:**

1. **Workflow-2 Step 3e (hand off, never inline) was load-bearing.**
   Without it I would have inlined a mock-bank change into this PR.
   Two surface-level harms avoided: (a) `mock-bank-sync-check`
   wouldn't have reviewed the fixture's 3-surface contract, (b) the
   test PR would conflate two responsibilities.

2. **Thread #28 had a verbatim Step 3f restoration template.** Made
   deliverable C in the hand-off mechanical. The next agent didn't
   need to invent a doc edit — just copy from the thread message.

3. **`docker exec -e DOCKER_MODE=true -e TEST_RUNNER_MODE=1` direct
   exec was much faster than the test-runner web UI** for iterating.
   The reference `learning_2026-04-20_when-running-integration-tests-via-direct-docker`
   already in user memory — I knew to add the env vars and saved
   probably 30s per run.

4. **Pre-flight HTTP probe of the new endpoint** (not just a curl
   round-trip in the test header but an actual `[ "$FIX_PROBE" !=
   "200" ] && fail` check at Step 1) is worth keeping as a pattern.
   If a future container rebuild misses the fixture, the test fails
   loud at second 1, not mid-flow at second 90 with a confusing
   "transfer succeeded normally" path.

**What was harder than expected — and the workflow refinement that
would help:**

1. **Symlinked agent files break the "one PR per test" Step 9
   contract.** `.agent/workflows/run-integration-tests.md` lives in a
   different repo (`mb_agent_oracle_memory`), so my registration edit
   went into a separate commit there, not the test PR. Workflow-2
   Step 9 should explicitly call out this split and recommend the
   commit shape (e.g., "commit the agent edit first with a
   'companion to PR #N' message, then create the test PR referencing
   it"). Right now a tester reading workflow-2 in good faith would
   think they're putting everything in one PR and be surprised at
   `git status` showing nothing in `.agent/`.

2. **The container alignment trick** (using `BANK_ACCOUNT=9999999999`
   to align with mock-bank env default rather than passing
   `?account=`) deserves explicit documentation, not just a header
   comment in this one test. Currently FIXTURES.md gate condition #2
   warns about the *failure* mode but not about the *workaround*. A
   short paragraph "When you can use container-default alignment
   instead of `?account=`" would help. Filing as a TODO in my own
   docs/test-coverage-gaps.md follow-up next session — not blocking
   this PR.

3. **First-run-green is suspicious by default.** Workflow-2 Step 5
   Part B has fix-and-retry guidance for failures but not "what to
   verify when it passes first try." For this test the green was
   real (3 assertions all matched expected values, runtime was
   plausible at 90s, fixture toggle was confirmed via curl), but a
   tester could be tempted to ship a test that passed for the wrong
   reason. A small "first-pass sanity checklist" addition to Step 5
   would be worth a refinement thread.

**What I would do differently next time:**

- Run the parse-check and a `grep -c "<unique-marker>" /app/...` post-rebuild
  verification IN THE SAME message as the rebuild itself, not as a
  follow-up. Saves a round-trip.
- For SCB tests specifically, default to `MAX_WAIT=600` from the
  start — I almost picked 300 by KTB analogue and would have hit a
  flaky timeout boundary on slow runs.
