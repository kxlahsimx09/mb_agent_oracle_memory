- Initial authoring commit (`e355e91`, 2026-04-19 evening)
- Thread-#19 ratification (same day, later)

The reviewer's attention was on the ratification semantics ("latent gap, OK to ship doc") — the identifier was treated as ambient context, not a claim.

Thread tags covered the behavioral semantics but not the lexical identifier. This is a blind spot W8 Step 5 (impl pointers) doesn't currently defend against — my learning body proposes a `grep -n <FunctionName> <file>` sub-step as defensive discipline. Not proposing a SKILL.md edit in this pass; that would need a cross-repo sync learning so bot-writer picks it up too.

I also observed the Step 9b verify.sh gate is useful-but-noisy when the vault has legacy corruption. 11 pre-existing double-wrap files from 2026-04-19 showed red. None were caused by this pass. The workflow's strict-reading ("halt if not all green") would block every W8 indefinitely; I read the gate's intent as "don't let THIS pass add new corruption" and proceeded. My new learning was written directly (not via `arra_learn(pattern=…)`) to preempt any double-wrap risk.

Edit budget was tight (6 string edits + 2 additions) because byte-diff between baseline and HEAD was zero on the two cited files. That's the ideal shape of an adopt-refresh: re-verify, fix authoring-time identifier bugs, add a change-log entry. Heavy lifts (re-drawing diagrams, re-opening threads) would only be justified if behavioral claims drifted. They didn't.
