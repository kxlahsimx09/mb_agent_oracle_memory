# AI Diary

I came in cold to this conversation — the user said "I (in a prior session) wrote this design but deleted it" and pasted a long markdown spec for a directed-inbox protocol. The spec was already 80% complete: three flows (consult/escalate/notify), filesystem-as-doorbell + arra_thread as content layer + watcher as wake mechanism, four open questions (cadence, archive, multi-recipient, priority). My job was to take it from "design draft" to "shipped Phase 1."

The first hour went smoothly. I picked up the Soul-Brews context fast (P-001 `Nothing is Deleted`, the symlinked `.agent/` central memory, AGENTS.md §3a single-author exception for `mb_agent_oracle_memory`). I answered the four open questions with concrete recommendations grounded in existing infra: reuse `w2-watcher`'s 5-min poll, `git mv` to `handled/` per P-001, no broadcast in v1 (YAGNI), per-node local path. The user accepted everything and said "ตามที่แนะนำเลย" which is the brew-ops dream — get clear go-ahead for an opinionated plan.

Then the user asked the question I should have asked myself: "When agent A sends to B, is B a fresh session?" That cracked open the wake-semantics layer I had glossed over. My first answer ("default is `--continue`") was honest but incomplete. The user's follow-up — "if it's a multi-turn back-and-forth on same topic, fresh isn't right" — was the kind of question that turns a design from competent to correct. That's where session-per-thread came from. I sketched the storage layout (`~/.cache/w2-watcher/inbox-sessions/<oracle>/thread-<N>.session-id`) and the decision rule, and §11f was born. That's the part of this design I'm most proud of, because it actually scales: A and B can run several threads in parallel, each oracle's JSONL stays bounded to a topic, eviction by thread-close is clean.

The cold test is where I got humbled. I was about to fire `maw wake next-architect` when I caught the role-label-vs-oracle-name routing bug during reconnaissance via `maw oracle ls`. That find was lucky — I only ran it because I wanted to confirm the wake target before firing. If I'd just typed `maw wake system-architect` confidently I'd have gotten "no oracle named ..." and the bug would have stayed in spec. The fix was straightforward (`git mv` + frontmatter edit + supersede the learning + commit `aa05b73`), but it taught me that role labels and oracle names diverge in fleets where one role has multiple oracles (technical-writer → pg-writer + bot-writer). That's a 1:N relationship I had failed to design for.

Then I fired the cold test and hit silent-fail at the very first step. Five minutes after committing the routing fix, I'm staring at `maw peek` output that ends with "No conversation found to continue" and a shell prompt. The architect pane never received the inbox prompt. I knew instantly what it was — the 2026-04-22 learning about `maw wake --fresh` exits 0 + the `||` template fallback that doesn't fire when continue exits 0 (success). I've debugged this exact pattern before in `w2-watcher.sh`. The fix in that watcher (commit `6b3662d`) is a workaround, not a root fix.

The user's response to my Option A/B/C menu was decisive: "B" — root-fix it in maw-js, don't accept the workaround again. That reordered Phase 2 (2b before 2a), which I'd been planning the opposite way around. It also made me realize Phase 2a as I had drafted it was implicitly relying on the workaround being there, which would have meant duplicating it across yet another script. The user caught a layering mistake that I had missed.

Time-wise, the session ran ~2 hours with the actual edit/commit work concentrated in the first 90 minutes. The last 30 was cold test + cleanup + retro. No long stalls. The TaskCreate/TaskUpdate cadence was useful: 16 tasks over the session, all marked completed by the end (one — task #11, the cold test — completed-with-failure as a known finding, not as a passing test). I rewrote task #6's description after the routing-bug catch to record what it actually accomplished rather than what it was originally created to do, which kept the task list honest.

# Honest Feedback

**What worked.**
- The user's incremental question pattern ("ลองเทสดูก่อน", "ตามแนะนำเลย", "B") let us walk through the design surface one layer at a time. I didn't have to guess priorities.
- Catching the routing bug *before* firing the first wake was pure luck wrapped in a habit — running `maw oracle ls` before `maw wake` is something brew-ops should always do, and I should make that an explicit Step 0 anywhere relevant. Will add it to this learning's "How to apply" if I revisit.
- Using `git mv` for the directory rename kept vault history clean (89%/85%/100% similarity preserved). P-001 compliance was effortless because of the discipline.
- The session-per-thread design holds up to scrutiny — A/B parallel threads, eviction by thread-close, fallback to `--fresh` on cache miss, all internally consistent. I'll be surprised if this needs material revision in Phase 2.

**What didn't work.**
- I drafted Phase 2 in the wrong order. Originally I had 2a (watcher in arra-oracle-v3) before 2b (maw-js native flag). The user's "Option B" reordering exposed that I had structured it client-first instead of root-cause-first. The right shape is always: fix the root, then drop the workaround.
- The cold test was over-ambitious for the first session. I should have anticipated the wake silent-fail (it's in oracle, I knew about it 8 days ago) and either checked whether maw-js had a fix landing, or scoped the cold test to *not* require `--fresh`. I burned a worktree spawning a wake that I should have predicted would fail.
- I let the dogfood envelope do double duty as both "first format validation" and "first cross-oracle wake target." When the wake silent-failed, the envelope test was also blocked. Better split: format validation = single-side simulation; cross-oracle wake = separate test once the wake mechanism is verified working.
- The AGENTS.md §11 first draft was too dense in places (the §11g phase status grew long with the silent-fail addendum). I should sweep §11 for length on the next pass — it's currently ~140 lines, larger than I'd want for a charter section.

**What I'd do differently next time.**
- Run the *capability check* (maw wake mechanism works `--fresh`?) before designing automation that depends on it. The 2026-04-22 silent-fail learning was already in oracle; one `arra_search` would have surfaced it before I scoped Phase 2a.
- Treat role label vs oracle name as a first-class distinction in any new fleet-wide protocol from day 1, not as a routing bug discovered during testing. Add a short `maw oracle ls` inspection to the brew-ops Workflow 5 audit checklist.

**What I want the next session to know.**
- Phase 1 baseline is canonical at commit `aa05b73` (with `303ab8e` adding documentation only). Don't re-run the routing fix.
- The wake silent-fail is the sole gate for Phase 2a. Until `maw wake --fresh --task '<prompt>'` reliably lands at a running claude session with the prompt visible, do not implement `scan_inbox()` in `w2-watcher.sh` — you'll just be re-implementing the workaround.
- The dogfood envelope at `ψ/inbox/for-next-architect/2026-04-30_17-18_from-brew-ops_thread-56_reply.md` is still active (unread). When the architect agent eventually picks it up — manually or via Phase 2a — they should `git mv` it to `handled/2026-04/` with `handled_at` filled in, per §11d.
