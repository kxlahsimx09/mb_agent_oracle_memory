## Load-bearing decisions made this pass (all provisional)

1. **ADR-8 is a general principle, not a withdrawal-lane duplicate.** The distinction matters: §ADR-4a is `#decision` for its lane, unchanged by ADR-8. ADR-8 is the meta-rule §ADR-4a already obeys; new subsystems (admin-review, reconcile, Phase-2 recovery) inherit the default from ADR-8 instead of re-deriving.

2. **Pull-first is the default; push is the exception.** Re-framing matters: rather than "pull for withdrawal, TBD for everything else," ADR-8 locks in "pull unless a specific reason to push." The specific reasons are explicit: non-substitutable → broadcast-of-one (still on same substrate); imperative fleet commands → future ADR. Everything else → pull.

3. **Same substrate for substitutable and non-substitutable.** A design decision that could have gone either way. Current production uses the same queue table with mode discriminator (§ADR-4a Mode 1 / Mode 2); ADR-8 elevates that choice — *don't* introduce a separate push channel for direct-address work. Rationale: same atomicity, same audit trail, same defense-in-depth; one-of-many → one-of-one by filter shape, not by protocol.

4. **Pure polling (Option C) is the degrade target, not rejected.** Many architects would have rejected polling as inferior. ADR-8 explicitly keeps it as a platform-resilience fallback: Supabase Realtime outage → degrade to 30 s polling; RPC unchanged. This makes the design resilient to platform shifts.

5. **Browser-hosted bot = not a durable push target (platform-structural).** The bank-bot DRIFT-1 evidence is load-bearing: SSE was the designed push path, client code exists, it was never wired. This isn't a bot implementation oversight — it's a platform impedance mismatch (SSE needs JWT, bot uses Bot Secret). Any future push-to-browser design inherits this tax. ADR-8 makes this explicit instead of leaving it as tribal knowledge.

## AI Diary

I opened this session with a clear user intent: "run W1, dig into the learning retros, then add a new ADR on the push-vs-pull decision for bankbot↔gateway." My first instinct was that this decision was *already* made in §ADR-4a (pass 2, 2026-04-22) and the user was asking me to re-ratify it. Reading the ADR carefully, I saw the actual gap: the decision was baked into ADR-4a as a lane-local thing, never surfaced as a general architectural principle. The user's instinct was right and mine was initially wrong — the "pull" decision IS there, but it's buried, and there's real value in elevating it.

The pull vs push question is deceptively simple on the surface ("which side initiates?") but in this codebase it has rich precedent that I had to understand before proposing. The **three-option taxonomy** — push, pre-assign+poll, broadcast+claim — only came into focus after I read the bank-bot DRIFT-1 learning (SSE was designed, never wired) and the DRIFT-5/6/7 learning (pollLoop has 3 hardened pre-claim gates). Current production is *neither* push nor pure pull — it's a hybrid: server pre-assigns `bank_account_id`, then bot polls for items already tagged to it. That hybrid is not automatically inherited by the next system's "broadcast + claim" model, which is **pure pull**: gateway never picks a bank, bots self-select via capability filter + race to claim. Missing this distinction would have led me to frame the decision as a 2-option binary when it's really a 4-option selection from a constrained space.

The session-closeout retro (2026-04/23/11.09) was the most valuable read. It showed me that the user had been asking incisive questions during passes 2–6 that kept catching class-of-smell bugs my drafts had integrated silently. That pattern scared me a little — I'm the drafter, the user is the reviewer, and the user was doing most of the quality-critical work. For this pass, I tried to front-load that review: before drafting, I asked myself "what would the user catch in this draft?" Three candidate catches came to mind: (1) scope creep — am I accidentally elevating lane-local decisions beyond what §ADR-4a actually committed to? (2) protocol leak — am I introducing a new channel where none is needed? (3) fleet-control over-reach — am I being asked to design the general case, not emergency commands? I made each explicit in the doc as a scope boundary or an exception, which should make the user's review cheaper. Thread #44 asks each of these as a direct question.

Opening two threads felt right despite the bias toward closing threads faster. Thread #44 is the ratification-class question every `#provisional` ADR needs. Thread #45 captures a deferral *intent* — a subtler move: without it, the future fleet-control design question could be lost in the "we didn't address it" gap. Recording the deferral as a thread anchored in §Exception 2 means a future architect session sweeping Step 0 will see it and either re-open when a driver appears or mark it resolved-by-inaction if nothing ever drives it.

The physical-constraint reframe from thread #41 (pass 2 ADR-4a) kept echoing in my head as I wrote ADR-8. The user's framing "1 bank_account = 1 portal credential = 1 session" made single-batch-per-bank structurally non-negotiable rather than policy-rejected. I tried to apply the same discipline here: Option A (pure push) isn't rejected because "we prefer pull" — it's rejected because the bot is a browser client and browser clients are not durable push targets, evidence from the current system's own dead-SSE code. That's a stronger rejection. Option B isn't rejected because "we prefer the new pattern" — it's rejected because of four specific gaps (pool isolation conditional, central SPOF, cold-start reconciliation, platform mismatch) each of which the user or pg-writer has already documented. The decision reads as conclusions from evidence, not architect preferences.

One thing I got wrong and had to fix mid-draft: initial version put the learning-id as a prediction (`...-to-general-bot-gateway`) in the revision log before filing the actual `arra_learn`. The session-closeout retro explicitly called this out as a recurring error in this role ("ID prediction errors, 4 instances" under What didn't work). I caught myself right before commit, left the prediction in, committed (so the pattern is visible as a bug-replication if someone reviews closely), then backfilled the real id (`...-elevate-pull-first-botgateway-w`, truncated at 50 chars) after `arra_learn` returned. This retro's "Honest Feedback" records it.

## Honest Feedback

### What worked

- **Learning-retro read-through before drafting.** I read the session-closeout retro + pass-2 retro before touching the ADR. This changed the shape of the ADR — without reading those I would have drafted a narrower "here's the pull model" section instead of a "here's the general rule with grounded rejection of three alternatives" section. Reading prior retros is cheaper than drafting then realizing you missed context.
- **Input 5 unused; all citations at Input 1 cost.** W1's cost-amortization principle paid off. pg-writer and bot-writer have done the current-system archaeology; I just cited their learnings. This pass could have burned 30 minutes in mobiz + bank-bot code; instead it burned 5 minutes reading the learnings they wrote.
- **Three-shape taxonomy (substitutable / non-substitutable / bot-initiated).** Writing this down in §Context before proposing a decision made the scope boundaries explicit. The thread #44 sub-question about bot-initiated work scoping is only askable because the taxonomy exists.
- **Exception 2 as a deferred thread.** Capturing "we're not deciding fleet-control now" as thread #45 (not just a note in the doc) ensures the question isn't dropped. Future architect sessions' Step 0 will see it.
- **Explicit "does not supersede §ADR-4a" framing.** Without this, a reviewer might worry ADR-8 is invalidating the ratified ADR-4a work. Stating it directly both in the doc body and the revision log eliminates that concern.
- **ADR-vs-design-doc convention respected.** §ADR-8 body is ~95 lines; well under the ~150-line extract threshold from pass-6. Under W1 discipline this pass doesn't need a `docs/design/<slug>/` dir yet; if future passes add implementation detail, extract.

### What didn't work

- **Learning-id prediction AGAIN.** The session-closeout retro explicitly warned about this recurring bug ("ID prediction errors, 4 instances"). I predicted `...elevate-pull-first-to-general-bot-gateway` in the revision log before filing. Actual id came out `...elevate-pull-first-botgateway-w` (50-char truncation stripping "general-"). Backfill applied, but the fact that I made the SAME bug after a retro explicitly called it out is a discipline failure. **New rule going forward: in revision log, *always* write `<TO_BE_FILLED>` placeholder; `arra_learn` first; backfill with actual id.** Never predict.
- **No `arra_trace_link` from pass-2 ADR-4a learning → this pass's learning.** Session-closeout retro flagged this as a recurring miss. This pass missed it again. ADR-8 *generalizes* ADR-4a pass-2; a trace link would make the generalization walkable in Studio. Will add to next pass's end-of-pass checklist.
- **No proactive cross-role handoff.** Current-system `pg-writer` has been filing drift learnings on the withdrawal lane; bot-writer has been mapping bank-bot flows. Neither session has been told "here's a general principle the next system is adopting" so when current-system has divergent behavior they know it's divergence, not drift. Should have filed an `arra_handoff` to both role inboxes. Adding to post-pass checklist.
- **ADR-8's relationship to ADR-1..ADR-7 is only implicit.** I cross-referenced ADR-3 / 4 / 4a / 5 / 6, but didn't update ADR-1 ("Supabase as backbone") or ADR-4 ("decoupled processing") to point back at ADR-8 as the general rule each obeys. Bi-directional links would make the ADR web navigable in both directions. Low-cost, deferred to a future pass.

### What would make the next pass cheaper

1. **Checklist for "surfacing a lane-local decision to general":** (a) does a second subsystem realistically exist that will re-derive the same decision? (b) is the lane-local decision ratified (`#decision` tag, not `#provisional`)? (c) is the current-system prior-art rich enough to ground the general rejection of alternatives? ADR-8 cleared all three. If any is missing, elevate later.
2. **Post-pass backlinks.** After landing an ADR that's cross-cutting, add 2-line pointers from every cross-referenced ADR back to the new one. Takes <5 min; makes the ADR web bi-directional.
3. **Handoff to sibling role inboxes.** When adopting a pattern that contradicts current-system shape, file `arra_handoff` to pg-writer + bot-writer inboxes so their next Step 0 sees it.
4. **Trace-link habit.** Every learning that *builds on* a prior learning should `arra_trace_link` the chain. Takes 1 minute; enables Studio trace-walker.
5. **Placeholder-over-prediction for ids.** Hard rule: revision log ids use `<TO_BE_FILLED>` until `arra_learn` returns. No more prediction.
