  (main test) + [mobiz-payment-gateway#306](https://github.com/kokarat/mobiz-payment-gateway/pull/306) (regression-suite add)
- **Runtime outcome:** VALID — green on attempt 5 in-session at

- **Setup hazards designed out:**
  - Pre-test cleanup drains orphan pending WQ items from prior runs
    (they inflate `OutstandingCountForBank` and keep banks busy-locked)
  - Both banks meet every OTHER `findIdleBanks` filter (status=1,
    working_status=ready, method≠[], bot_status=online,
    available_balance>0, no maintenance, daily-limit) — only
    `bot_last_checked` differs across phases
  - `primitive.DateTime` (not string) for heartbeat timestamps
  - 3-layer assertion per phase (log grep + distribution count +
    Phase 2 inversion for positive control) — no single check is
    load-bearing
  - Pre-test sanity gate (both fresh, 4 payouts) aborts if the
    load-balancer itself is skewed; prevents a 5/0 ratio from
    false-passing if the picker is broken
  - `wait_for_assignment` timeout 60s (≥ one natural 30s tick) with
    active drain + unlock each second
- **Notable design choices or surprises:**
  1. **Gap-row had the wrong field name.** Gap wording said
     `working_at`; the actual filter reads `bot_last_checked` (updated
     by `POST /bank-status/report`). `working_at` is a different
     field used for per-bank dispatcher lock. Test uses the correct
     field; gap row annotated rather than silently overwritten per
     P-001.
  2. **`drain_bank_queue` + `unlock_both_banks` are a reusable
     pattern, not bespoke.** Without them the test self-blocked at
     4/5 because each dispatcher round's `findBestBankForItem` caps
     at `inflight < perBankCap` where `inflight` counts
     pending+processing items on the bank. With no real bot to
     MarkSuccess, items pile up and the cap hits. Future dispatcher
     tests (stale-timeout reconcile PR #249, idle-only PR #239,
     per-bank cap PR #237) will likely need the same pair of
     helpers — filed as arra_learn with a hoist-to-setup-infra
     recommendation for when a 2nd/3rd test needs them.
  3. **Long-running bot-1 container interfered.** `bank-bot-1` runs
     24/7 in the test env and polls for Bank A's account
     (9999999999). It grabbed some items mid-test and moved them to
     `processing` → eventually `waiting_to_review`. This didn't
     break assertions (count_on_bank filters by system_bank_id, not
     status), but it produced noise in mongo inspection. Worth
     noting in the test header as a known environmental quirk.
  4. **Assertion design**: user pushed back hard on "A=5, B=0"
     alone — correctly identified it as insufficient (picker bug
     could false-pass). Added log-grep + pre-test sanity gate +
     Phase 2 inversion. The log-grep was the decisive addition —
     it directly proves the `continue` at `:376-380` fired for the
     specific bank. Distribution count alone is circumstantial.
  5. **`BotLastChecked > 0` guard** — banks whose bot has never
     reported are NOT skipped by this filter. Filed as separate
     arra_learn; not asserted in this test (would require a
     3rd phase with a brand-new bank and could tangle with
     `bot_status: offline` separate protection).

The diagnostic aha came from reading backend docker logs and
finding `"1 items remaining (will assign next round)"` repeatedly
— that told me the dispatcher was ACTIVELY running but choosing
not to assign. The only cap that would do that is the per-bank
`inflight < cap` gate. Once I read `findBestBankForItem` the fix
was obvious.

Three-layer assertion was user-prompted. I initially had just
counts (A=5, B=0). User's "how do you know it doesn't go to B?"
pushback forced me to strengthen it. This is why reviewer feedback
matters on test design — I would have shipped a weaker test
without that nudge.
