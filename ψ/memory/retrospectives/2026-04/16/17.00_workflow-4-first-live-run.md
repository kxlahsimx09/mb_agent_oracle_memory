## AI Diary

Felt unusually methodical on this one. The workflow reference spells out per-item outputs so precisely that the temptation to mass-resolve ("mark all 10 as A and move on") had an obvious tripwire in the pitfalls section — "Skipping triage because the queue is big." I forced myself to re-read both sides of every item against HEAD even when the answer was obvious. That caught **DRIFT-8** (premise already false at 2026-04-15 — deposit model also uses camelCase, which the original drift author missed) and **DRIFT-10** (CLAUDE.md at HEAD doesn't actually mention the hourly report scheduler, so there was no doc to fix). Both would have been silently mis-labelled as (A) "fix the doc" if I'd trusted the drift's premise without re-verification.

The hardest judgment call was **DRIFT-9**. Strict workflow-4 (A) would have meant authoring 10+ new CLAUDE.md feature sections — 6+ hours of work including domain questions to the user. I couldn't fit that into a "cleanup pass" without bloating the PR. I took a pragmatic (C) closure with a non-standard reason `scope-exceeds-reconcile` and filed a `#next-task` handoff. Flagged the deviation in the resolution learning and PR body so the pattern is auditable. This is exactly the kind of judgment the pitfalls section anticipates ("Mass-closing drifts in one learning" / "Reconciling drift during a feature PR") — but turned inside out: the *non-mass* closure of one large drift, without authoring, is arguably a new pitfall that deserves a note in the workflow ref after this run.

**Second hard call**: CLAUDE.md ownership. SKILL.md lists me as owner of `docs/current-system.md` but doesn't name CLAUDE.md as writer territory (it's the project charter file). Workflow 4's (A) outcome says "fix the doc" without restricting to owned docs, and AGENTS.md §8 ownership table says `doc ↔ code | technical_writer | Update doc to match code`. I concluded CLAUDE.md edits are fair but conservative — surgical rather than sweeping. Kept each edit to the minimum lines needed, cited the code path in the edit or in a leading note rather than adding `// verified:` inline comments (which would clash with CLAUDE.md's prose style).

## Honest Feedback

**What worked**:

- Writing the 10 learnings directly as files (per AGENTS.md §7 "How to actually make the write") kept the 3-layer tag schema intact. The MCP `arra_learn` tool's flat `concepts` array can't express `repo:` / system-phase layers cleanly.
- Parallel reads for code-verification (deposits, payouts, settlements, payoutRequest, scheduler) kept the triage fast — ~10 minutes for all 10 items including cross-checks.
- The §9.a "Drift closed in the 2026-04-16 reconcile pass" table is more useful to future readers than simply removing closed rows — it makes the cleanup pass visible and audit-traceable in-place, without forcing readers into git blame.

**What didn't work**:

- **`arra_supersede` couldn't run** — Oracle's indexer had not picked up the new resolution files by commit time. The MCP tool rejects unknown `newId`. I attempted the chunked `_0` form (which works for lookups from `oracle_documents`) but still failed because the new doc wasn't indexed. Tried HTTP endpoints (`/api/reindex`, `/api/scan`, etc.) — all 404. Oracle's `is_stale: false` + `last_indexed: 36 min ago` suggests the scanner runs periodically; 60 s wait + `touch` did not trigger a reindex. **Outcome**: deferred supersede to a follow-up session; documented in PR body. This is the #1 thing to fix for the *second* live run of workflow-4 — the workflow reference should say "run `arra_supersede` only after verifying the new learning is indexed" and include a way to trigger reindex (probably `arra_learn` as a side-effect, or a fleet CLI command).
- **Commit landed on the wrong branch** (`feat/tester-test-payout-expiry` instead of `docs/reconcile-drift-3b7e0f1`). Git `HEAD` had switched between my `git checkout -b` and the `git commit` — probably a concurrent process in the tmux/fleet environment. Recovered cleanly with `git branch -f` + rebase + reset to origin, but the diagnosis cost maybe 2 minutes. Lesson: run `git status -sb` **immediately before** each commit, not just at session start.
- **DRIFT-7 SSE event list** — I updated the `SSE Events: Published to settlements channel on create, approve, reject` line based on route changes, but didn't audit every `controllers.PublishEvent` call in SettlementController. Flagged this as a residual in the resolution learning and PR body. Future Workflow 2 pass should pick it up.

**First-live-run feedback on the workflow reference itself** (to be folded into `workflow-4-reconcile-drift.md` change log):

1. Add a pre-step between Step 7 (write resolutions) and Step 8 (commit): "verify each new resolution learning is indexed in Oracle before calling `arra_supersede`." Include a sqlite3 query (`SELECT COUNT(*) FROM oracle_documents WHERE source_file LIKE '%2026-...-resolution-%'`) and a fallback path if the indexer is behind (e.g., "file `arra_supersede` as a follow-up task via `arra_inbox` instead of blocking on it").
2. Clarify outcome (C): the strict options (`obsolete | duplicate | feature-removed`) do not cover "scope-exceeds-reconcile." Either add that as a fourth reason or explicitly document that (C) may use a freeform reason so long as a `#next-task` handoff is filed.
3. Add "CLAUDE.md is in writer territory even though SKILL.md §What I own doesn't list it, because it is a doc ↔ code file per AGENTS.md §8." Make ownership explicit to avoid the judgment call I had to make on the fly.
4. Pitfall to add: "Trusting the drift's premise without re-verification at HEAD." 2 of my 10 items (DRIFT-8 and DRIFT-10) had premises that were already false on the day the drift was filed or had been addressed by subsequent commits. Without re-verification they would have been silently mis-labelled.
