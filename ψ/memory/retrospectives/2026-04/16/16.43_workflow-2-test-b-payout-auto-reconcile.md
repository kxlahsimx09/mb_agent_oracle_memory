## AI Diary

The reuse story was clean. Test A taught me the structure; Test B
just swapped the trigger. The biggest design call was *what to plant
in `bank_statements`*. Reading the goroutine code carefully showed it
only consumes:

- `matched_queue_id` (lookup key, must point at WQ._id)
- `match_status` (lookup filter, must be `"matched"`)
- `stmt.ID.Hex()` (used as the new `bank_transaction_id` on the payout)
- `stmt.Description` (embedded in the reconcile reason text)

Every other field on the statement is unconsumed. I could have
planted a 4-field minimal row. I chose to fill in realistic-looking
values for amount, direction, dest_account_*, etc. because:

- A future reviewer or test-runner UI looking at post-test state should
  see a recognisable statement, not a half-stub.
- If the auto-reconcile contract ever expands to consult more fields
  (e.g., "verify amount matches the payout"), the test won't suddenly
  start failing for a reason that has nothing to do with the change
  under test.
- The cost is a few lines of mongo insert; cheap insurance.

This is a tradeoff: minimal stub = honest coverage of "what the
tested code currently consumes"; realistic stub = forgiving against
future contract expansion. I went realistic. Logged here so the
rationale is visible at code review.

The branch incident (committing onto stale `docs/reconcile-drift-3b7e0f1`
instead of the freshly-created `feat/tester-test-payout-auto-reconcile`)
was a wake-up call. The repo has 10+ lingering local branches from
prior Claude Code sessions. When my `git checkout -b` ran, *something*
left me on a different branch by the time the commit fired. I never
saw the prompt switch. Recovered with `git checkout feat/... && git
reset --hard <commit>` — safe in this case because the feat branch
was empty and the stale branch had nothing else on it. But the next
agent in this repo should:

- Run `git branch --show-current` between branch creation and commit
  if the workflow involves branch switching.
- Treat any branch named with timestamp/commit-hash in it as suspect
  until proven otherwise.
- Maybe add a guard in workflow-2 Step 9 itself: assert
  `[ "$(git branch --show-current)" = "feat/tester-test-..." ]`
  before `git commit`.

The `arra_handoff` cwd-relative path bug is a real pattern, not a
one-off — both my handoffs this session landed in the wrong place
(repo cwd) instead of the indexed vault. Manually moved both. Future
agents writing handoffs from a project-repo cwd need to either (a)
chdir to the vault before calling, or (b) write the file directly
themselves. Filing as a learning rather than a bug-fix because the
MCP tool isn't in this repo to fix.

## Honest Feedback

What worked:

- The vault learning `setup-hazard-auto-reconcile-blocks-manual-confirm`
  written during Test A was load-bearing here. I didn't have to
  re-discover that the goroutine fires post-commit; I knew exactly
  what conditions made it find/not-find a match. This is the
  pay-it-forward pattern the Oracle is supposed to enable, and it
  worked first try in the same session.

- Splitting Test A and Test B into two PRs (instead of one big "payout
  repair surface" PR) keeps each PR's review scope tight. The
  reviewer for #179 evaluates "is the manual contract right?", the
  reviewer for #180 evaluates "is the auto contract right?". The
  shared service function means a single review of one would be 90%
  useful for the other, but the explicit cross-references in the PR
  bodies do that bridging without coupling the reviews.

- The composite poll signal in Step 9 (status=completed AND
  confirmed_by="system:auto-reconcile") is more reliable than just
  status=completed because if anything else (a hypothetical race
  with the manual path, or a test-pollution leak) flipped the payout,
  the actor field would not say "system:auto-reconcile". Worth using
  this pattern wherever the test needs to confirm WHICH path landed,
  not just that some path landed.

What I'd do differently:

- I would have run `git branch --show-current` immediately after
  `git checkout -b` to catch the stale-branch issue at the source.
  Cost: one bash call. Benefit: avoids a 3-step recovery.

- The test does not exercise the "no matching statement → goroutine
  silently exits" path. That's the negative-path coverage equivalent
  for Test A's setup. Reasonable to skip — Test A IS that test in
  spirit (it *requires* no matching statement to work). But strictly,
  no test asserts that the goroutine doesn't *spuriously* fire when
  there is no statement. Worth mentioning if anyone asks.

- The PR body's "Conflict notice" anticipates a rebase but doesn't
  pre-write the merged numbers (37 / UNKNOWN=2). I could have
  prepared both PRs to assume the other had merged first — but that
  would have coupled them to merge order, which is the wrong shape.
  The current approach (each PR honest about its own state, conflict
  resolved at merge) is right.

What blocked me / nothing did:

- Same as Test A: nothing genuinely blocked. The pattern reuse made
  Test B about half the wall-clock time of Test A despite roughly the
  same line count. The marginal value of well-organised prior-session
  memory continues to be negative cost (Test A's hazard learning
  literally saved me from a debugging detour Test B would have
  otherwise taken).
