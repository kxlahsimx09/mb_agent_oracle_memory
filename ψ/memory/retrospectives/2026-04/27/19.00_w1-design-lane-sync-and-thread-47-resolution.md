## AI Diary

This session opened with what looked like a tight 60-minute scope — sync the withdrawal-lane design docs to the fair-router model. ADR-8 had been ratified three days ago; the docs had drifted; the gap was visible (18 Mode-1 refs across 3 files). I planned a clean drift cleanup, no decisions, ~60 min.

Two unexpected things happened.

**First, during the sync pass itself**, I found a CHECK-constraint imprecision in §ADR-4a's pass-7 update note. The note had said "CHECK constraint unchanged" but that claim was correct only about *intent*, not literal DDL — the existing 2-branch CHECK rejected the post-routing shape. Fair-router's UPDATE would have failed at runtime. I widened the CHECK to 3 branches and called it out in the revision-log + commit message as a "surfaced inconsistency within ratified scope" — not a new decision, just bringing the schema in line with what the ratified decision required.

This is the kind of thing I'm now actively watching for: when an ADR update cites companion-doc behavior, *grep the companion doc before committing*. Pass-7 didn't do that. The sync pass caught it.

**Second, after I shipped the sync pass and reported "done,"** the user asked me to explain ADR-4a Decision #4 in detail, then ADR-8 step 2's tier cap. While answering both, I realized — and the user spotted before I finished — that I had explained `pickTierCap` (fair-router) and `compute-claim-size` (claim-side) as if they were complementary, but they're the same logic ported to two layers. User asked the perfectly sharp question: "มี pick tier cap กับ compute claim size หรอ" ("are there both?").

That moment was uncomfortable. The sync pass I had just shipped *should have caught this*. The whole point of design-doc audits is to surface this class of cross-cutting drift. I had been so focused on the "Mode-1 retirement" angle that I didn't audit other parts of the claim-RPC layer.

The recovery felt clean, though. Owned the miss explicitly ("user สังเกตเจอ redundancy ที่ผมไม่ได้เห็นเองใน sync pass ที่ผ่านมา"), reconstructed the pass-1 → pass-2 history that produced the leftover, surfaced it as a thread #47 with 3 options + architect recommendation. Anchored it in both ADR sections. User ratified Option A within the session — fastest surfacing-to-resolution loop I've done in this repo.

What I want to remember from this is the *shape* of how the leftover survived. ADR-8 pass-2 did the right thing locally (added `pickTierCap` at fair-router as the new tier-cap owner). What it missed was the cross-cutting question: *"now that fair-router owns tier cap, what mechanism in the old design is now dead?"* That's not a question I asked at pass-2 time. It's a question I now have to ask at *every* reframe. Process improvement adopted in the resolution revision-log entry: "After every reframe, audit which old machinery is now redundant."

Three user-surfaced design issues in two weeks (cross-direction-metric on 4-24, body-size drift on 4-24, tier-cap redundancy on 4-27). All three share the same root: I draft inside one model, user reads with broader-system context and catches the legacy mechanism that didn't get retired with the model change. The pattern is real; the checklist item targets it directly.

The surfacing-to-resolution structure — two adjacent revision-log entries within the same session — is new for this repo. I want to flag it because it makes the journey walkable. If a future architect (or me, in two weeks) reads the log, they see *both* the gap and how it closed. Compare to the typical pattern where a thread opens silently in one session and closes silently in another — the log shows only the closed state, missing the texture of why the question existed in the first place.

## Pattern captured — surfacing-to-resolution as a same-session loop

Sequence:

```
1. Architect drafts at narrow scope (sync pass).
2. User reviews with broader context, surfaces cross-cutting question.
3. Architect:
   - Acknowledges the miss explicitly.
   - Reconstructs pass-history to explain how the leftover survived.
   - Opens thread with 3 options + architect recommendation.
   - Anchors `[AWAITING_THREAD]` at every relevant ADR section.
   - Files revision-log entry capturing the OPEN state.
   - Commits + pushes (continues PR).
4. User ratifies (often within minutes if the surfacing was well-shaped).
5. Architect:
   - Updates ADR sections (strips markers, rewrites decision sentences).
   - Updates companion design docs.
   - Files revision-log RESOLUTION entry adjacent to surfacing entry.
   - Posts closing message in thread + arra_thread_update closed.
   - Files arra_learn for the resolution.
   - Backfills learning id + commit sha.
   - Commits + pushes (same PR).
```

**Prerequisites for this loop to be cheap:**
1. User is active and has system-level context.
2. Architect has the discipline to ship the surfacing as its own commit + revision-log entry, not collapse it into the resolution.
3. Both parties accept "open question" as a legitimate state — not pressure to resolve immediately.
4. ADR-vs-design-doc convention is mature enough that "this is in scope" vs "this is a new decision" is a fast determination.

**When this pattern is wrong:**
- Decisions large enough to need a new ADR section, not a sub-question.
- Security-sensitive questions (halt + ping required; not async thread).
- Cross-role coordination needed (cross-repo writers, sibling agents).

**When this pattern is right:**
- Sub-question within already-ratified `#decision` scope.
- Architect has a defensible recommendation ready.
- User available within hours.
- Resolution is implementable in a single small commit.

This session's tier-cap question fit all four "right" criteria. The whole loop closed in under 2 hours of active work.
