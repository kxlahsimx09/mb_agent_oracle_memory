## Trace-link process bug — explicit treatment (user requested)

### The pattern

`arra_trace_link` has been flagged as missing in **8+ consecutive retros** spanning approximately 4 weeks. Pattern is identical every time:

> *"`arra_trace_link` across the chain — missed again; flagged in Honest Feedback as process-bug-class."*

Today's session shipped **6 new learnings** + **1 supersede chain** (§ADR-4b pass-1 baseline → §ADR-4b ratification). Every learning is a candidate `arra_trace_link` opportunity. **Zero `arra_trace_link` calls were made today.** Same as every prior session.

### Why self-flagging at retro time has provably failed

The mechanism is simple:

```
Pass N work → arra_learn (filed) → commit → push → retro → flag "missed arra_trace_link, will do next time"
                                                                                                            ↓
Pass N+1 work begins → forget → arra_learn (filed) → commit → push → retro → flag again
```

The flag at retro time is **outside the loop where the missing call should have happened**. By the time I'm writing the retro, the moment to call `arra_trace_link` is past — the chain context is fading, and the retro is the wrong place to bolt it on after.

Eight iterations of this pattern is *not* "I forgot, will remember next time." It's a structural process bug: **the trigger to call `arra_trace_link` is in the wrong place in my workflow.**

### What `arra_trace_link` should be linking

Concrete examples from today:
- §ADR-4b pass-1 baseline learning ↔ §ADR-4b ratification learning (already linked via `arra_supersede`, but trace would chain it across the lifecycle including thread #52 messages + commits)
- §ADR-4b ratification ↔ §ADR-4d ratification (both ratified in same session; deposit-lane substrate convergence)
- §ADR-4a `claim_withdrawal_items` learning ↔ §ADR-4b `finalize_deposit` learning ↔ §ADR-4d `finalize_deposit` reuse (third atomic-boundary port)
- Tier-cap surfacing learning ↔ tier-cap resolution learning (already partially linked via revision-log narrative + supersede chain)
- §ADR-6 pass-1 baseline ↔ §ADR-6 design-doc extraction (doc-organization refactor)
- Code-duplication drift in `UploadSlip` vs `UploadSlipAdmin` (current) ↔ §ADR-4d Decision #1 (closes drift structurally)
- 5 user-surfaced clarifications across 2 weeks (cross-direction-metric → body-size drift → tier-cap → §ADR-4b Q3 → §ADR-4d C4) → form a meta-pattern that should be traced across passes

Every one of these is a meaningful trace. None were filed.

### Why the habit hasn't formed

Honest reasons:

1. **Trigger is at retro time, not at `arra_learn` time.** Retro is too late to call the link.
2. **Tooling does not enforce.** `arra_learn` returns success without prompting "do you want to trace this to a prior learning?". `arra_supersede` does prompt (it's the explicit P-001 mechanism), so I always remember it. `arra_trace_link` has no such prompt.
3. **Cognitive load mid-session.** During pass execution, I'm focused on the design + commit + thread cycle. Adding "and trace-link" requires explicit mental space.
4. **Retro flagging gives false sense of progress.** "Flagged in Honest Feedback" feels like accountability, but if the cycle repeats 8 times, the flag itself is the evidence the system isn't working.

### Concrete proposed fix — externalization

The pattern that has worked for `arra_supersede` (always remembered) is **explicit prompt at the right moment**. Three options to externalize:

**Option A — Self-imposed checklist as part of W1 Step 8.** Add to the workflow doc: "After every `arra_learn` call, immediately decide: does this learning chain to a prior one? If yes, call `arra_trace_link` in the same response, before committing." Move the trigger point from retro to learning-creation time.

- *Pro:* simple, no new tooling
- *Con:* same self-discipline mechanism that has failed 8 times; depends on me remembering to read the W1 workflow doc

**Option B — `arra_learn` wrapper / hint.** Modify `arra_learn` (or wrap it with a hint script) to return a reminder: "*New learning filed. Did you want to trace-link to a prior learning? Most recent learnings: [list]*". Surfaces the question at the right time.

- *Pro:* prompt is at the moment of action, not after
- *Con:* requires tooling change (likely needs brew-ops involvement)

**Option C — `brew-ops` automation thread.** File a thread to `brew-ops` proposing: "After any `arra_learn` call within a session that already has a learning filed in the last 7 days, the runtime should surface a one-line prompt: 'Trace-link to learning_X (most recent same-role)?'." Brew-ops decides if this fits the fleet automation roadmap.

- *Pro:* delegates to the right role; durable fix
- *Con:* needs brew-ops engagement; may take cycles to land

### Architect commitment from this retro

For the next session (if I'm honest with myself, **only this commitment is binding**):

**Try Option A first** — add explicit "after every arra_learn, immediately decide trace-link" as an actionable Step 8 sub-task in the W1 internal checklist I keep in retros. If it fails again at the next retro, file Option C (brew-ops thread) without waiting for another iteration.
