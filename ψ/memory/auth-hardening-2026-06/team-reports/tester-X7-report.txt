 KEY FINDINGS (architect-relevant)
--------------------------------------------------------------------------------
F1 (X7-v / auth005 AC6) — SOFT-WINDOW MECHANISM IS INEFFECTIVE over the wire.
   On an external (client) lock the EF sets app_user.banned_until = locked_at + soft_window (3s after
   the shrink — the config IS read), BUT it ALSO issues an independent gotrue ban of ~60s
   (gotrue.banned_until ≈ locked_at + 60s) that is NOT derived from auth_lockout_config.soft_window.
   The gotrue ban dominates: after the 3s app_user window the EF re-runs the password check, gotrue
   still rejects (banned) → invalid_credentials → re-lock. Proven decisively: waiting the FULL ~60s+
   with NO intervening attempt DOES auto-clear (is_locked=false, login proceeds). So:
     • Auto-expiry exists and is WALL-CLOCK (no virtual clock) — confirms the auth-005:74 spec text
       ("virtual clock") is wrong and must be replaced with the wall-clock + shrunken-window form.
     • BUT the sanctioned "shrink soft_window" lever does NOT shorten the effective lockout — the
       gotrue-ban duration is the real knob and is hardcoded/independent.
   RECOMMENDATION (→ next-architect / next-dev): tie the external-regime gotrue ban_duration to
   auth_lockout_config.soft_window (or do not gotrue-ban soft/external accounts; gate purely on
   app_user.banned_until). Until then the shrunken-window mechanism cannot be the sanctioned test lever.

F2 (X2 / auth005 AC3) — the gotrue-429 audited tier is UNVERIFIABLE on qnccph. The EF→gotrue sign-in
   is an internal call not subject to the per-IP sign-in rate limit; the limiter never returns 429 at
   any achievable volume (overload → 500). Recommend a brew-ops gotrue sign-in-rate-limit lever for a
   future run, or an EF unit test of the isRateLimited() branch + the one-row-before-429 write.

F3 (X3b on qnccph) — the EF-side validation is LIVE and spoof-CLOSED (X7-iv green; auth005 AC2/AC9
   reds are the spoofable path being correctly refused). But because the CF edge transform rule is
   deferred, the EF resolves NO trusted client IP on the raw origin → every allowlisted account is
   fail-closed (auth005 AC1 ip=null, AC2/AC9 403). The on-list-PROCEEDS leg is only testable once the
   CF transform injects cf-zone-secret + the real CF-Connecting-IP (sinuw/prod). Re-run AC1/AC2/AC9
   there to close the positive legs.

F4 — EF deploy gap on qnccph: admin-users-unlock (AUTH-005 AC7) and admin-deposit-refund (AUTH-007
   gated money-out) are NOT deployed (404). AC7 + auth007 AC1/S4-a cannot be exercised here. (The
   refund EF is X6-acknowledged Phase-2-deferred; the unlock EF should be deployed for AC7 coverage.)

 F3 ADDENDUM — CF-Connecting-IP is owned by Cloudflare (verified)
--------------------------------------------------------------------------------
A client that sets `CF-Connecting-IP` on the raw *.supabase.co origin is rejected by CLOUDFLARE
itself with HTTP 403 "error code: 1000" (server: cloudflare, content-type text/plain, NO
x-served-by: supabase-edge-runtime) — the request never reaches the EF. A PLAIN request (no such
header) reaches the EF (x-served-by: supabase-edge-runtime, JSON {"error":...}). Consequence: there
is NO client-injectable trusted-IP path over the wire — next-dev's "send CF-Connecting-IP + cf-zone-
secret to exercise the on-list leg" is impossible here (CF blocks the header before the EF; and the
EF only trusts cf-connecting-ip, which CF owns). The spoof is thus blocked at TWO layers (CF error-
1000 + EF secret-gated trust). X7-iv proves no-bypass via both CF-Connecting-IP (CF-blocked 403) and
X-Forwarded-For (EF ignores it → 403 ip_blocked). The on-list-PROCEEDS positive leg is only testable
once the real CF transform rule fronts the stack (sinuw/prod).
