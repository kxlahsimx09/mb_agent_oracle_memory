CONFIRMED FINDING (current source, stated as required)
------------------------------------------------------
File _shared/lockout-support.ts, registerFailedAttempt() two-regime trip.
On an EXTERNAL (client/sub-client/merchant/partner) lock the EF set:
  • app_user.banned_until = now + soft_window      (config IS read — correct)
  • gotrue ban_duration   = `${Math.ceil(soft_window_seconds / 60)}m`
The gotrue ban is rounded UP to whole minutes (min "1m" = 60s) and is NOT
derived from soft_window. So with a shrunken soft_window (e.g. 3s) the gotrue
ban is 60s and DOMINATES: after app_user.banned_until passes (3s), the login
pre-check clears but gotrue still rejects (banned) → registerFailedAttempt fires
again → re-lock. Net: the ratified, configurable soft_window did NOT control the
effective lockout; only a full ~70s wall-clock wait recovered (tester x7-v).
=> Auto-expiry was wall-clock all along, but driven by the wrong knob.

FIX — Option A (pinned; tie gotrue ban to soft_window)
------------------------------------------------------
  - ban_duration: internal ? FAR_FUTURE_BAN : `${Math.ceil(cfg.soft_window_seconds / 60)}m`,
  + ban_duration: internal ? FAR_FUTURE_BAN : `${cfg.soft_window_seconds}s`,
Soft/external gotrue ban_duration = soft_window (seconds) = the SAME value already
written to app_user.banned_until → both clear TOGETHER at the window. gotrue stays
the single enforcement substrate (consistent with the hard regime), so Option A
was workable — no architect flag needed (Option B not taken).
Hard/admin regime UNCHANGED: FAR_FUTURE_BAN (permanent until super-admin unlock, LK1).
