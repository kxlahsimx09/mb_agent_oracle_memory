## Pattern catalog (10 patterns; ordered by instance count)

### 1. User-pushback-as-design-force — 8 cumulative instances

**Definition:** User follow-up question during ratification surfaces architectural decision the architect deferred or claimed without sufficient verification. Question often phrased as "current มี/เป็นยังไง" or "ทำไม X" or "จริงๆ ผมมองว่า Y".

**Trigger heuristic:** when user asks structural follow-up after seeing decisions #1-#N, that's a signal architect missed a load-bearing decision OR over-claimed without verification.

**Instances:**
1. §ADR-4c pass 1.5: *"ไม่ clean"* → drove Decision #10 view contract
2. §ADR-9 pass 1.5: *"EF จะถูก call บ่อยไปไหม"* → cost-coalescing primitive added
3. §ADR-9 pass 1.5: *"เก็บ log ยังไง"* → Decision #6 attempts-log table
4. §ADR-12 pass 1.5: *"client create request ด้วยหรอ"* → Settlement caller correction (PR #235 evidence)
5. §ADR-12 pass 1.5: *"admin UI ไม่น่าต้อง idempotent"* → §ADR-11 scope clarification
6. §ADR-12 pass 1.6: *"current มีแผนจะทำ auto trigger settlement ไหม"* → Phase-2 → Option B parity
7. §ADR-13 pass 1.5: *"check current ก่อนว่ส admin แต่ละเส้น"* → 3-layer rule + audit_log discovery
8. §ADR-13 pass 1.6: *"field ใน business row มันดูรก"* → Option D trigger-based denorm

**Pattern qualifies as durable.** Surfaces at every multi-flow / cross-cutting ADR.

### 2. Drift-closure-as-decision — 4 instances

**Definition:** When drift is system-wide AND has known fix in mobiz prior-art AND fix changes data semantics or architectural shape → architecture closes structurally rather than per-RPC implementation fix.

**Trigger heuristic:** known drift + system-wide + has known fix + fix changes data semantics → lift to architectural decision.

**Instances:**
1. §ADR-10 D4: silent-skip MDR drift (mobiz thread #6) → "every MDR-profile partner produces 1 audit row"
2. §ADR-9 D2: callback-resend idempotency (mobiz threads #19+#31) → producer-supplied event_id as Idempotency-Key
3. §ADR-11 D1+D5: HTTP retry → duplicate row at client-API → required Idempotency-Key on all client-facing creates
4. §ADR-12 D3: Pullout 4-path multi-trigger drift (PR #342 acknowledged) → single dispatcher

**Distinguishes from:** "drift to defer to impl pass" — which is fine when drift is per-RPC localized. Architectural closure only when system-wide.

### 3. Coordination-rule-as-architectural-invariant — 4 instances

**Definition:** When rule is cross-RPC/cross-endpoint AND missing-it = incident-class (deadlock, drift, divergence) → lift rule to architectural invariant; every future RPC author inherits from ADR.

**Trigger heuristic:** cross-something rule + missing-it = incident-or-drift class → architecture is the right place.

**Instances:**
1. §ADR-10 D5: canonical wallet.id ASC FOR UPDATE order (cross-RPC + missing = deadlock incident class)
2. §ADR-11 D5: every client-facing payment-API create requires Idempotency-Key (cross-endpoint + missing = duplicate-row drift)
3. §ADR-12 D4: Direct-Transfer sync-validate-all-before-INSERT (cross-endpoint + missing = admin-UI-divergence incident)
4. §ADR-13 D1: Admin write 3-layer invariant generalization (extends §ADR-12 D4 to all admin write endpoints)

**Pattern reflexive at this point** — when architect notices "every X must do Y", evaluate (a) cross-something? (b) missing-Y = incident class? If both yes, architecture.

### 4. Phase-1/Phase-2 staging — 4 instances

**Definition:** When decision has hedged future direction with named driver, structure as Phase-1 (current/parity) + Phase-2 (trigger-driven evolution path).

**Trigger heuristic:** decision has hedged future direction + driver can be named → Phase-1/2 staging. **NOT applied blindly** — requires named driver.

**Instances:**
1. §ADR-2 RBAC: Phase-1 hardcoded roles → Phase-2 configurable DB-driven (driver: admin UI requirement)
2. §ADR-9 D4 retry budget: Phase-1 fixed schedule → Phase-2 per-merchant config (driver: SLA negotiation)
3. §ADR-10 D2/D3 balance/audit: Phase-1 mutation+log → Phase-2 ledger / audit consolidation (drivers: GDPR / read-pattern audit)
4. §ADR-11 D3 TTL: Phase-1 fixed 24h → Phase-2 merchant-configurable (driver: SLA negotiation)

**Anti-instance:** §ADR-12 D2 Settlement scheduling — pass 1.5 framed as Phase-1/Phase-2 with Phase-2 trigger "merchant-pulled scheduled"; user evidence-checked → no driver evidence → reframed to parity-only Phase-1 + future-ADR-placeholder. **Lesson:** Phase-1/Phase-2 staging needs driver evidence; not blindly applied to "future could change" decisions.

### 5. Future-ADR-placeholder-as-deferred-question — 3 instances

**Definition:** When speculative future emerges without driver, name placeholder ADR + driver shape in §Deferred questions; less architectural debt than committing Phase-2 staging without driver.

**Trigger heuristic:** speculative future without driver → defer to placeholder + name driver shape.

**Instances:**
1. §ADR-12 §Deferred: §ADR-13 Settlement Scheduling placeholder (driver: merchant SLA / ops automation)
2. §ADR-13 D2 + §Deferred: separate `admin_actions` table placeholder (driver: regulatory audit / forensic-query)
3. §ADR-13 D4 + §Deferred: §ADR-14 Fleet-Control placeholder (driver: operator-imperative request OR §ADR-6 Phase-2 Smart Disconnect)

**Distinct from Phase-1/Phase-2 staging** — placeholder is "decision deferred entirely; opens new ADR when driver emerges"; staging is "decision made now with future evolution path named".

### 6. Single-straight-ratification — 2 instances + heuristic limitation surfaced

**Definition:** User ratifies all sub-questions in single response without push-back when pass-1 satisfies enabling conditions.

**Original 5 enabling conditions:**
1. Phase-1/Phase-2 staging on hedged decisions (no premature commitment fear)
2. Architect-rec on every sub-question (binary accept/reject)
3. Trade-offs rejected inline at decision-line (rationale visible)
4. Drift-closure-as-decision when applicable
5. Coordination-rule-as-architectural-invariant when applicable

**Instances:**
1. §ADR-10 thread #57: *"เลือกตามที่แนะนำทุกข้อเลยครับ"* — straight ratify in 1 message
2. §ADR-11 thread #59: *"เอาตามแนะนำ"* — straight ratify in 1 message

**Heuristic limitation surfaced (§ADR-12 + §ADR-13):** even with all 5 conditions, multi-flow ADRs (≥3 flows) and cross-cutting ADRs with parity-default-without-architectural-improvement still trigger user-pushback.

**Heuristic update candidates (post-§ADR-13):**
6. **Scope ≤2 flows / cross-cutting** (not multi-flow surface ≥3 flows)
7. **Architecturally-clean-by-construction** (no parity-without-improvement) — where mobiz pattern is functionally correct but architecturally verbose, evaluate Postgres feature for cleaner shape BEFORE committing parity-preserve framing

§ADR-12 had 3 flows + multi-area + Phase-2 over-projection → 3 user-pushback events / 2 revises.
§ADR-13 had cross-cutting + parity-default for D2 (mobiz field-bloat) → 2 user-pushback events / 2 revises.

**Pattern qualifies as conditional-durable** — works when scope is bounded + architecture-clean. Heuristic refinement ongoing.

### 7. Pre-Input-5 checkpoint expanded — 10 cumulative instances

**Definition:** Verify before claiming, regardless of past-state or future-state direction.

**Original direction (instances #1-#7):** past-state behavioral claims ("current does X") — verify via Input 1 prior-learning OR Input 5 code-read.

**Expanded directions (instances #8 + #10):**
- **Future-state speculation** (instance #8 §ADR-12 Phase-2 auto-recurring without driver) — verify driver evidence; if absent, future-ADR-placeholder
- **Absence-claim sub-shape** (instance #10 §ADR-13 audit_log table) — evidence-of-absence ≠ absence-of-evidence; same rigor as presence claims

**Two brew-ops handoffs filed:**
1. `2026-05-02_18-53_pre-input-5-checkpoint-escalation-instance-7-8.md` (instances #7 + #8)
2. `2026-05-03_11-47_pre-input-5-checkpoint-supplement-instances-9-10.md` (instances #9 + #10)

**Pattern frequency:** ~1 instance per ADR baseline pass on average over 9 calendar days. Multi-flow ADRs concentrated 4 instances in 2 days.

### 8. ADR-network-coherence-as-maintenance-pass — 1 instance (NEW pattern)

**Definition:** When ≥3 new ADRs ratify, batch citation cleanup across earlier-ratified ADRs whose deferred-questions / inline references now point to closed surfaces.

**Trigger heuristic:** every N ADR ratifications (suggested N=3), do a maintenance pass to update sibling deferred-questions + cross-cut citations.

**Instance:**
1. 2026-05-02 maintenance pass — 6 surgical edits across §ADR-4a/4b/4c/7 citing newer §ADR-9/10/11/12. P-001 strike-through preserves history; new citations inline.

**Distinct from W1 baseline / refine / ratification modes.** Pattern attributes:
- No architectural decision changes
- No new threads
- No ratification needed
- Strike-through preserve P-001 history
- Smaller cognitive load than per-ADR full revise

**Pattern qualifies as nascent** — 1 instance; needs more to confirm durable. Document as W1 workflow option for future architects.

### 9. Combined-pass shape — 2 instances

**Definition:** When user-pushback drives within-scope revise during ratification AND user immediately ratifies revised body in same dialogue, combine pass commits (not separate commit per pass).

**Trigger heuristic:** revise scope is bounded to user-named architectural concern + user explicitly indicates ratification intent post-revise → single combined commit.

**Instances:**
1. §ADR-9 pass 1.5+2 combined (cost-coalescing + Decision #6 + ratification)
2. §ADR-13 pass 1.6+2 combined (Option D + ratification)

**Pattern qualifies as durable.** Pass shape should match user-pacing shape, not workflow-default shape.

### 10. Deliberate-divergence-from-mobiz-via-Postgres-feature — 2 instances (NEW pattern)

**Definition:** When mobiz pattern is functionally correct but architecturally verbose/messy AND Postgres has a feature (view / trigger / partial index / generated column / etc.) that enables cleaner shape, divergence is justified.

**Trigger heuristic:** mobiz pattern functionally correct + architecturally verbose + Postgres feature available + business semantics preserved → divergence justified.

**Instances:**
1. §ADR-4c D10: Postgres computed view + partial index → real-time visibility 0 lag (vs mobiz Go opportunistic-on-read inline pattern that user called *"ไม่ clean"*)
2. §ADR-13 D2: Postgres `AFTER INSERT` trigger on audit_log → constant 4 typed columns auto-populated (vs mobiz per-transition denormalized fields scaling N×M which user called *"รก"*)

**Pattern qualifies as durable.** Preserves business semantics; only changes data-model shape. Architecture-vs-design discipline note: divergence is at architecture level (Postgres feature commitment); specific implementation form deferred to design pass.

**Suggested W1 workflow doc note:** at evidence sweep, when reading mobiz pattern, ask *"is this architecturally clean OR functionally-correct-but-verbose?"* If verbose, evaluate Postgres feature for cleaner shape **BEFORE** committing parity-preserve framing.

## Heuristic update suggestions for W1 workflow doc

### Update 1 — Single-straight-ratification 6th + 7th conditions

Current 5-condition heuristic (§ADR-9 pass-1 retro projection) needs:

```
6. Scope is cross-cutting (≤2 flows) rather than multi-flow surface (≥3 flows).
7. Architecturally-clean-by-construction — where mobiz pattern is functionally
   correct but architecturally verbose, evaluate Postgres feature for cleaner
   shape BEFORE committing parity-preserve framing.
```

Without #6, multi-flow ADRs over-predict straight ratification (§ADR-12 had 3 flows; predicted straight; got 2 revises).
Without #7, parity-default ADRs over-predict (§ADR-13 D2 was mobiz parity; predicted straight; got 1 revise via "รก" pushback driving Option D).

### Update 2 — Pre-Input-5 sub-shape examples

Step 4 sub-rule should include both directional examples:

```
Past-state claims include both:
- "current does X" (behavioral) — verify via Input 1 prior-learning OR Input 5 code-read
- "current does NOT have Y" (absence) — verify same way; absence requires same
  evidence rigor as presence
- "current uses pattern Z" (architectural) — verify before committing
  parity-preserve framing; evaluate divergence-via-Postgres-feature if Z is
  functionally correct but architecturally verbose

Future-state claims include:
- "Phase-2 will need Y" (speculation) — verify named driver evidence; if absent,
  use future-ADR-placeholder pattern (defer entirely; name placeholder ADR + driver shape)
```

### Update 3 — Maintenance pass mode

Add to §When to run section:

```
After ≥3 ADR ratifications, run a maintenance pass to update earlier ADRs'
deferred-questions + cross-cut citations referencing the now-ratified ADRs.
Pattern: ADR-network-coherence-as-maintenance-pass. No architectural decision
changes; no new threads; no ratification. Smaller cognitive load than per-ADR
full revise.
```

### Update 4 — Combined-pass shape

Add to §Steps section:

```
Combined pass shape — when user-pushback drives within-scope revise during
ratification AND user immediately ratifies revised body in same dialogue,
combine pass commits (single commit covering revise + ratification). Pattern:
match pass shape to user-pacing shape, not workflow-default shape.
```

### Update 5 — Deliberate-divergence-from-mobiz pattern

Add to §Anti-patterns section as a positive pattern (not anti-pattern):

```
Deliberate-divergence-from-mobiz-via-Postgres-feature — when mobiz pattern is
functionally correct but architecturally verbose/messy AND Postgres has a
feature (view / trigger / partial index / generated column) that enables
cleaner shape, divergence is justified. Architecture-vs-design discipline:
divergence preserves business semantics; only changes data-model shape.
```
