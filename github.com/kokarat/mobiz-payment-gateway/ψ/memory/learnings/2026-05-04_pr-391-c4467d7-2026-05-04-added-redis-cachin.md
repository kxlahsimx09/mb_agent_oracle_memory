# PR #391 (`c4467d7`, 2026-05-04) added Redis caching to three dashboard read endp

PR #391 (`c4467d7`, 2026-05-04) added Redis caching to three dashboard read endpoints whose underlying $group aggregations were repeatedly slow on 4 พ.ค. 2026 slow logs. (1) `BankStatementController.GetBankStatementStats` — caches the 11-field `$group` over `bank_statements` (~10–20 K docs/day, up to ~80–100 K for a 7-day window). Cache key `bank_statements:stats:{hex(sha256(filterJSON)[:8])}`, TTL 60 s. Filter equality is the cache key, so distinct `?search` / `direction` / `match_status` / `system_bank_id` / date-range / amount-range combinations land on distinct keys. Pool-ACL `denied=true` short-circuits before the cache. (2) `BankStatementController.GetBankStatementAccounts` — caches the distinct-accounts dropdown (`$group` over the entire ~470 K-doc collection). Only the **admin path** (no pool scoping → empty `matchFilter`) is cached at fixed key `bank_statements:accounts:admin:v1`, TTL 5 min. Pool-filtered callers fall through to the live aggregate because keying on the full `allowedAccounts` list would lose the benefit. (3) `SystemBankController.GetAllDailyStats` — caches today's deposit/withdrawal `count + total` per system bank ($group over `bank_statements` filtered to today's BKK day). Cache key `system_banks:daily_stats:{startBKK}`, TTL 30 s. The per-bank `/:id/daily-stats` is **not** cached (different code path, low call rate). All three TTLs are well within the human dashboard refresh cadence (multi-second polls); same-tab refresh hits cache.
