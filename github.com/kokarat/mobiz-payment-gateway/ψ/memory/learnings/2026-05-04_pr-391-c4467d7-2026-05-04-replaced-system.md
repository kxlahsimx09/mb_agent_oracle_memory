# PR #391 (`c4467d7`, 2026-05-04) replaced `{system_bank_id: {$exists: true, $ne: 

PR #391 (`c4467d7`, 2026-05-04) replaced `{system_bank_id: {$exists: true, $ne: NilObjectID}}` with `{system_bank_id: {$gt: NilObjectID}}` in `WithdrawalQueueController.GetBanks` (the dashboard "pending by bank" pipeline). MongoDB's `$ne` defeats indexes — the planner falls back to COLLSCAN even when a fully-matching compound index exists. `$gt:NilObjectID` is index-eligible (range on the leading field) AND still excludes the orphan rows: production has 708 `withdrawal_queue` docs with `system_bank_id == NilObjectID` at merge time. Dropping the guard altogether (the initial PR commit's approach) would surface those orphans as a bogus `bank_code:""` row aggregating their summed count — pre-merge verification caught this and switched to `$gt`. Verified parity on production: both predicates returned 102,762 rows, both hit `system_bank_id_1_status_1`; the `$gt` form was ~30% faster (155 ms vs 223 ms) because the optimizer doesn't have to apply `$ne` as a post-filter. General lesson: when an existence-or-non-zero guard is needed on an indexed field, prefer `$gt` over `$ne` — same semantic for a single-zero-sentinel field, but only the former is index-eligible.
