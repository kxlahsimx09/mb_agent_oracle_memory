# Pullout DestCap two-layer guard at b23a903 (PR #336, 2026-04-29). After PR #323 

Pullout DestCap two-layer guard at b23a903 (PR #336, 2026-04-29). After PR #323 (5ce4596) shipped the in-flight pending reservation (`SumPendingPulloutAmountsToDest`), dest banks were still landing over the 100k–120k cap band. Observed 2026-04-29 on bank 5665765524: pullouts of 57k and 73k landed within 5 minutes; balance ended at 126k. Root cause: a window between `MarkSuccess` (which removes the item from pending/processing) and the next bot balance scrape (which mirrors the credited amount into `destBank.Balance`). During that window, a sibling pullout reads the still-stale `destBank.Balance`, passes the headroom check, and pushes the dest past cap. Two-layer fix: **Layer 1 — pre-credit dest in MarkSuccess transaction.** New block in `services/withdrawalQueue.go:MarkSuccess` `$inc`s `system_banks.{balance, available_balance}` on the dest bank matched by `bank_code` + `account_number` + `status: 1` for `source_type=pullout`. `balance_updated_at` is **deliberately NOT touched** — that field remains the canonical "last bot scrape" marker, used by layer 2. Best-effort: log on failure but don't abort the transaction; external destinations (no matching system_bank) match zero rows and silently skip. **Layer 2 — `services.SumSettledPulloutAmountsToDest(ctx, destBankCode, destAccountNumber, balanceUpdatedAt)`.** Sums pullout queue items with `status="success"` whose `completed_at > balanceUpdatedAt` (capped to a 15-minute hard floor). When `balanceUpdatedAt.IsZero()`, falls back to a 24-hour lookback so a brand-new bank doesn't appear to have unbounded headroom. Wired into all three write paths alongside existing `SumPendingPulloutAmountsToDest`: `scheduler.executeTask`, `PullOutTaskController.ExecutePullOutTaskNow`, `BotConfigController.UpdateBankBalance`. Effective dest balance now: `destBank.Balance + pending + settled-unsynced`. Layer 1 closes the window proactively; layer 2 is the safety net for the case where a fresh bot scrape lands between layer 1's pre-credit and the next dispatcher tick — the scrape would overwrite the pre-credit, but the settled-unsynced reservation still keeps the headroom honest. Skip / reduce log lines updated to break out the two reserved totals (`pending` vs `settled-unsynced`) so operators can tell which path triggered. Manual execute-now path's response body now exposes `inbound_pending` and `inbound_settled_unsynced` separately. Effective destination invariant the doc cites: `destBank.Balance + SumPendingPulloutAmountsToDest + SumSettledPulloutAmountsToDest <= cap`.
