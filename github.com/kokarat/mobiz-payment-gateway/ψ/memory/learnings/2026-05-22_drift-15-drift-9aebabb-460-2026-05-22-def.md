# DRIFT-15 (#drift, `9aebabb` #460, 2026-05-22): deferring Thunder slip verificati

DRIFT-15 (#drift, `9aebabb` #460, 2026-05-22): deferring Thunder slip verification to escalation-only removes the Thunder-derived fraud signals from the deposit matcher happy path. Before #460, UploadSlipAdmin called Thunder at upload, so slip_verify_result was populated and the approve-time receiver-mismatch check (services/slipFraudCheck.go) plus the V1 hash-collision check (services/slipMatchHash.go) had data to evaluate when an admin moved the deposit to paid. After #460, a slip-bearing deposit that the statement matcher auto-confirms (linkCheckingDeposit / matchDepositKTB / matchDepositSCB) is never Thunder-verified — slip_verify_result stays empty — so those two approve-time fraud checks have nothing to read on the happy path; they fire only after the slip-review timeout escalates the deposit to admin review (processSlipEscalation/processSlipVerify) or after admin POST /deposits/:id/reverify-slip. The matcher's own duplicate-credit guards (linkCheckingDeposit, checkRetroactiveSlipFraud in services/transactionMatcher.go) remain the happy-path defense. This relates to the prior finding that Thunder isDuplicate / V2 amount-match flags were detected in slip_verify_result but not enforced/blocking at admin approve — #460 narrows the window in which slip_verify_result even exists. Financial/fraud-adjacent; flagged for code_reviewer / security_auditor; queued for W4. Documented in current-system.md §9 DRIFT-15 + inline §3.2 deferred-verification paragraph.
