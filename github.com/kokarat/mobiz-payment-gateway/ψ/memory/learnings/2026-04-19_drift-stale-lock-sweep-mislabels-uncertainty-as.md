# drift — stale-lock sweep mislabels uncertainty as `failed` (Path 2, mobiz siblin

drift — stale-lock sweep mislabels uncertainty as `failed` (Path 2, mobiz sibling of bot-side thread #16). `scheduler/withdrawal_dispatcher.go:788` at HEAD `0d968fa` calls `services.MarkFailed(item.ID, "Processing timeout (10 min) — bot may have crashed. Check bank statement before retrying.")` for every `withdrawal_queue` item stuck in `processing > 10 min`. The error message string itself encodes uncertainty explicitly (*"bot may have crashed. Check bank statement before retrying"*) — meaning code already knows it doesn't know the transfer status — yet the mechanism is `MarkFailed` which: (1) refunds client wallet `amount + fee`, (2) fires `failed` callback, (3) triggers `tryReconcileAfterMarkFailed` goroutine as the safety net. When the bot actually did submit the transfer before crashing (case 2/3 of the three possible states: never-submitted / submitted-not-parsed / parsed-not-reported), the money is already out of the bank but the gateway ledger thinks it was refunded — producing double-transfer risk if client retries on the `failed` callback. Violates the payout state invariant ratified 2026-04-19 (`failed` = proof-negative-only; uncertainty → `waiting_to_review`). 1-line fix: `services.MarkFailed(...)` → `services.MarkWaitingToReview(...)`. Consequences: wallet stays debited (correct — bank may have moved money), no callback fired (no double-transfer risk), item enters admin review queue where operator checks bank statement and resolves via `/:id/confirm-completed` (existing, PR #231) or a future `/:id/confirm-failed` endpoint (payout-request §Resolved questions (c), not yet built). All lifecycle updates (`ts_payouts` flip, bank unlock via `UnlockBankIfDone`, queue cascade) are preserved — `MarkWaitingToReview` does all the same updates as `MarkFailed` minus the wallet refund and callback. The 2026-04-12 "orphan-item" concern documented in the comment at L762-775 (motivating the per-item `MarkFailed` over bulk UpdateMany) does not regress under the fix because `MarkWaitingToReview` still updates ts_payouts + unlocks bank. Scope note: Path 2 is the mobiz-territory sibling of bot-writer's Drift II (thread #16 `bank-bot/app.js:1640-1648`). The two together represent the full invariant-violation landscape in the automated paths; admin-discretion paths (`PUT /withdrawal-queue/:id/failed`, `PUT /payouts/:id/status status=failed`, `PUT /payouts/:id/override target=failed`) are separate class requiring evidence-guard design, not 1-line fixes.
