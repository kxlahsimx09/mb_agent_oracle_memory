## What went well

- **§ADR-11 4-case conflict matrix maps cleanly to 4 tests.** D4 specifies (new key / replay / 409 conflict / expired) — 4 tests cover each case with one outcome assertion + state-after assertions. Reading ADR → writing tests was almost transcription.
- **State machine 'pending' → 'completed' parallels §ADR-9 D6 callback_attempts** + §ADR-4d D9 slip_verify_attempts. Same shape: race-guarded transition with append/update sequencing. Pattern compounding visible at PoC #6.
- **Composite-key UNIQUE constraint test (test 5) is concrete + load-bearing.** Tests 3 cases (different clients / different endpoints / same composite-key replay-pending) in one file. ADR §Out of scope explicitly defers this to impl-pass — PoC validates the architectural intent.
- **bun test running pgTAP-only without Bun.SQL was clean.** No HTTP layer, no mock client. 1.5h end-to-end matches 4d (also pgTAP-only).

## What didn't go to plan — RUNNER BUG (load-bearing)

### The bug

Mutation harness initially reported **M-B + M-E as escapees**. Manually running mutations confirmed: tests DO fail when mutation applied. Why did the runner say PASS?

**Root cause:** `run-tests.sh` counted PASS as:
```bash
if [ "$n_notok" -eq 0 ] && [ "$n_total" -gt 0 ]; then PASS
```

This works when tests fail via pgTAP `not ok`. But when a test aborts mid-flight via SQL ERROR (e.g. `duplicate key value violates unique constraint`), pgTAP doesn't get a chance to emit `not ok` — psql errors out, transaction aborts, subsequent assertions get "current transaction is aborted, commands ignored". Output shows: 1 ok + ERROR + nothing else.

Runner saw: `n_ok=1, n_notok=0, n_total=1 > 0` → marked PASS (wrong!).

### The fix

Extract `1..N` plan declared by `SELECT plan(N)` at top of file. Compare `n_total` to `N`. If `n_total < plan_N` → file FAILS with "aborted mid-flight" indicator:

```bash
plan_n=$(echo "$out" | grep -oE '^1\.\.[0-9]+' | head -1 | sed 's/^1\.\.//')
is_pass=0
if [ "$n_notok" -eq 0 ] && [ "$n_total" -gt 0 ] && \
   [ -n "$plan_n" ] && [ "$n_total" -eq "$plan_n" ]; then
    is_pass=1
fi
```

After fix: M-B + M-E correctly red (test 5 + tests 1/2/3/4/7 respectively). 5/5 mutations OK.

### Backport implication

**This bug exists in run-tests.sh of poc/4a, poc/4b, poc/4c, poc/4d, poc/9.** None of those PoCs reported escapees historically — but the bug means: if any of their mutations caused a mid-flight abort (vs pgTAP not_ok), the harness would have reported PASS silently, hiding a real escape.

Recommendation: file a **maintenance commit** that backports the runner fix to poc/4a/4b/4c/4d/9. ~5-line diff per file. Outside §ADR-11 scope but quality-affecting.

### Honest feedback on the bug

Three lessons:

1. **I copy-pasted run-tests.sh from poc/4d to poc/11 without reviewing.** Pattern-compounding works for code SHAPE but doesn't catch BUGS that are baked in. The runner bug existed since poc/4b's first version — propagated 5 times before discovery. **Mitigation:** when copy-pasting infrastructure, audit the load-bearing logic at copy-time, not just at first-write.

2. **Mutation testing exercises edge cases the original tests don't.** Manual test-suite green didn't catch this — only when M-B/M-E *expected* a specific test to fail did the harness reveal that the runner was misclassifying. **Pattern: mutation testing is also a tool for harness validation, not just spec-test validation.**

3. **plan(N) declaration is load-bearing for runner correctness.** Every test file declares `SELECT plan(N)` upfront. The runner ignored it. New runner uses it as the source of truth. **Lesson: pgTAP's plan() exists for this reason; runners must respect it.**

## AI Diary

### The bug discovery felt like a near-miss

When mutation harness reported M-B + M-E as escapees, my first instinct was "these mutations don't actually break the test logic". I almost moved on, marking them as inherent-redundancy escapes. But the surface area of M-B (UNIQUE constraint change) is so direct + load-bearing that it MUST affect test 5 — if it didn't, my test was structurally wrong.

I ran M-B manually and saw the duplicate-key ERROR + transaction abort. Then traced: pgTAP didn't emit not_ok because the abort happened before the assertion line. Runner saw 1 ok + ERROR text → counted as PASS. Bug located.

If I'd accepted the "escape" without investigation, I'd have shipped a PoC + retro that quietly hid the bug. **Worse: future PoCs would inherit the same broken runner.**

This is the value of mutation testing as a quality gate. It's not just about spec tests pinning claims; it's about validating that the HARNESS interprets results correctly.

### The §ADR-11 D5 architectural-invariant pattern is durable

Reading ADR D5: "every client-facing payment-API create requires Idempotency-Key via shared middleware; endpoint authors cannot opt out". This is the same shape as §ADR-10 D5 canonical lock-order: structural enforcement at the substrate boundary, not per-endpoint discipline.

Future ADRs that want to encode "every X must Y" should follow this pattern. PoC tests can verify the substrate enforces; they can't verify endpoint authors didn't opt-out (impl-pass concern). But the substrate-level guarantee is what makes the rule durable.

### The composite-key UNIQUE design has subtle implications

Test 5 verifies UNIQUE is `(client_id, endpoint, key)` not just `(key)`. This means:
- Different clients can use same Idempotency-Key (no information leak across clients)
- Different endpoints can use same key per client (impl-pass scoping)

If a malicious actor could observe another client's keys, they couldn't replay-attack because (their_client_id, endpoint, K1) is a different composite. This is structural privacy.

D5 §Out of scope explicitly defers "cross-endpoint key-collision policy" — the (composite key) decision IS the policy. Test 5 validates the architectural choice.
