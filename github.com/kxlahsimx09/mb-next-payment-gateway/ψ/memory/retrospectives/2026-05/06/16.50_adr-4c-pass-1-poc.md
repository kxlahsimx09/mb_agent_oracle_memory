## What didn't go to plan

- **First M-C mutation chose wrong direction operator.** I wrote `AND expires_at > now()` thinking "add ANY filter on expires_at to break asymmetry." For fresh pending (expires_at in future), `> now()` is TRUE so the RPC still flipped → admin-maintenance-cancel still worked → test 04 stayed green. Refined to `AND expires_at <= now()` (opposite-asymmetry — only allows expire on already-overdue rows, blocks admin cancel) → test 04 correctly red. Cost: ~3 min. Lesson: **when mutating asymmetric guards, write the opposite-asymmetry, not just any filter that uses the same column**.
- **Nothing else.** This is the cleanest pass yet.

## AI Diary

### Approach

Going into this pass I expected it to be easier than 4a/4b, and it was. The ADR text for §ADR-4c is exceptionally clean — Decisions are short, the design doc literally contains the RPC body verbatim, and the view contract has a beautiful 5×3 alternatives matrix. I was essentially **transcribing** rather than designing. That's good — it means the architect role did its job and the PoC is mostly verifying transcription fidelity, not exploring design space.

### The view contract is the highlight

D10's `v_deposits.effective_status` is the most architecturally interesting decision in §ADR-4c. The tension is: real-time visibility for users vs sweep-bound callback emission for merchants. The view solves it by making "effective" a read-side concept and "physical" a write-side concept; reads can see expiration immediately while writes still serialize through the sweep + RPC. Test 5 + 6 demonstrate both sides — test 5 shows the view computes 'expired' for an unflipped row; test 6 shows that for non-pending or non-overdue rows, the view returns physical status unchanged.

This is the kind of decision that benefits from a runnable PoC because the tradeoff is subtle. Reading the ADR you go "oh, computed view, makes sense"; running test 5 makes you actually *see* the row at `status='pending'` while `effective_status='expired'` — and that's when the architectural elegance lands.

### The drift signal is real

I mined 3 expired samples. ALL THREE had `updatedAt = createdAt` despite physical status='expired'. That's not coincidence — it's a systematic gap in current's expire path. Current likely uses `db.collection.updateOne({...}, {$set: {status: 'expired'}})` directly (raw Mongo, no Mongoose middleware) somewhere. The audit timestamp lies.

Next-system's PoC schema closes this two ways:
1. Explicit `expired_at` column — RPC sets it deterministically; downstream consumers can trust
2. `updated_at` auto-bump trigger on UPDATE — works regardless of caller pattern

Cleanest version: D3's RPC body sets `expired_at = now()`, and the trigger handles `updated_at`. Both timestamps land correctly without either depending on caller discipline.

### Mutation M-C iteration

I expected M-C to red on first try. Stared at the diff and realized: my mutation `AND expires_at > now()` doesn't actually flip *the asymmetry's intent*. The asymmetry says "expire RPC ignores expires_at"; flipping it means the mutation should do "expire RPC honors expires_at *AND uses the wrong-direction filter*". `<=` is the right direction (only-already-overdue) — `>` is just a redundant filter that fresh rows pass anyway.

Took 30 seconds to think through, 30 seconds to code, 30 seconds to verify. The honest takeaway: **mutations against asymmetric/decoupling guards need the opposite-asymmetry mutation, not any-extra-filter mutation**. Captured in retro for next time.
