## What went well

- **Postgres-only-floor was the right cheapness floor.** No EF, no bot simulator, no callback dispatcher needed for the 10 claims. SKILL.md §6 single-criterion test ("does the claim name EF runtime as load-bearing?") cleanly held — atomicity + cascade-ordering both live in PL/pgSQL. Pass took hours not days.
- **Production data mining via dpay MCP was high-density per byte.** 5 `describe_collection` + 6 `find`/`aggregate`/`count` calls gave: schema shape for 5 collections, scale (351,991 paid deposits), match_status distribution, retry pattern, MDR fan-out shape. Convinced me the §ADR-4b mental model was production-faithful and that Q4a was a real risk class (no log-and-continue victims found via the absent-wallets_change_logs filter, but the `transactions` row pattern shows the matcher path is hot).
- **Mutation harness in Bun caught a real test-quality issue.** Without it I'd have shipped a green suite where M-A's regex hit the `now()` *comment* rather than the actual code — same kind of false-positive that mutation testing exists to catch in normal production code.
- **The poison-via-GUC framework scales.** One trigger per step (iii/iv/vi/vii/viii) + `SET LOCAL poc4b.poison='<step>'` lets every test inject failure exactly where needed without polluting other tests. Reusable for later §ADR-4 sibling PoCs.

## What didn't go to plan

- **`max(uuid)` doesn't exist in Postgres.** Initial cascade RPC used `SELECT count(*), max(id)` — caused test 6 to fail with "function max(uuid) does not exist". Restructured to two separate queries (count first, fetch row when count=1). Loss: ~10 minutes. Lesson: pgTAP doesn't help you discover SQL semantics — running real seed data does.
- **`PERFORM` outside `DO` block.** Wrote `PERFORM poc4b.finalize_deposit(...)` at SQL top-level; that's pl/pgSQL syntax, not standalone SQL. Cost: ~5 minutes for tests 5 + 10. Lesson: the test runner needs to surface the actual SQL error, not just "0 ok".
- **`ALTER DATABASE postgres SET poc4b.poison TO ''`** failed with permission denied — Supabase local's `postgres` user isn't granted GUC-registration privilege. Removed the ALTER; PostgreSQL accepts custom dotted-name GUCs without prior registration. Cost: ~5 minutes.
- **String.replace without `/g` flag.** Mutations M-A through M-D failed silently because the regex matched the doc-comment occurrence ahead of the code occurrence. The harness reported "0 actually red" with no clue why. Fixing two of them (M-A, M-B, M-D) by adding `/g` instantly turned 4 escapees into 3 OKs. Lesson: when a mutation harness reports "no reds", first audit the patch on disk before suspecting the spec test.
- **Originally-broad poison trigger broke M-C.** `_poison_step_iii` fired on *any* wallet UPDATE (client + partner). Mutation M-C wraps step (iii) client UPDATE in EXCEPTION — partner UPDATEs in step (v) still raised, function failed naturally, rollback. Test 02 path (iii) didn't see Q4a forbidden quadrant. Refined trigger to fire only on `OLD.owner_type='client'` — faithful to mobiz Q4a (which only swallowed the client failure). Now M-C correctly creates the forbidden quadrant. Cost: ~15 minutes of debug to understand why an "obvious mutation" didn't red.

With a tighter budget I'd cut the README to a punch list and grow it as the test suite materialized; the README is descriptive, not generative — if I need to update it after every SQL fix that's a sign I over-specified.

## AI Diary

### Approach evolution

I started with the assumption that Group A (atomicity) was the **only** load-bearing scope and Group B (cascade) was nice-to-have. Reading the §ADR-4b D2 amendment (ratified 2026-05-06 — yesterday) changed my mind: D2 is also `#decision`, equally load-bearing, and has its own `[POC_GAP:cascade-multi-candidate]` shape that PoC-time mining helped me dimension. Including all 10 tests in Pass-1 was the right call; if I'd split into Pass-1=A and Pass-2=B+C, I'd have re-paid the bootstrap cost (supabase init, schema scaffolding, helpers).

### The wallets_change_logs absence drift

This was the moment I most doubted my plan. The drift learning text said current production "treats missing or failing wallet update as a log-and-continue step" — implying a wallet *update* is attempted with audit. But mining showed `wallets_change_logs.reference_type='deposit'` returns refunds only, never credits. Initial reaction: maybe my filter is wrong; maybe the audit goes to the singular `wallet_change_logs` table. Mined that too — also empty for `reference_type='deposit'`. Then I noticed `transactions` rows have `entity_type='client'` and the deposit `mdr_distributions[]` array carries partner-MDR snapshots inline. Conclusion: **current production tracks credit via `transactions` row + array — no separate audit row exists**. §ADR-4b D5 step (iv) is *adding* an audit row. Tightening, not regression.

This matters because if I'd written a spec test asserting "after credit, exactly one wallets_change_logs row exists with operation='deposit_credit'" without flagging the `#current` absence, an architect retroactive sweep might classify it as missing-precedent → false drift signal. The `[POC_GAP:wallets_change_logs-current-absence]` flag is the breadcrumb for that future architect pass.

### The "deposit.completed" vs "deposit.paid" wording

ADR text consistently says `deposit.completed`. Production callback_logs.event distribution shows zero `deposit.completed` and 412k `deposit.paid`. PoC follows production wording (`deposit.paid`) for fidelity. Could be flagged for architect's W2, but it's wording-only — not load-bearing. Filed in evidence summary.

### Mutation iteration as the strongest signal

Tests 01-10 turning green felt good but didn't prove much — they could all be implementation-grounded. Mutation testing made the difference: M-F drops the `wallets_change_logs` INSERT and reds test 02 + test 03 (the latter via side-effect: test 03 expected exactly 1 audit row after first finalize, mutation drops to 0). That side-effect was unintended on my part — I'd predicted only test 02 would catch M-F. Discovering test 03 also catches it tells me the test suite is more interconnected than my mental model. Good signal that the suite has redundancy where it matters (any wallet-credit-related claim catches an audit-row mutation).
