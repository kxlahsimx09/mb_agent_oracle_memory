# §ADR-9 Pass-1 PoC — retrospective

**Fourth PoC** of `mb-next-payment-gateway`. **First PoC needing real HTTP layer** — Bun-based dispatcher + in-process mock merchant. Closes the consumer side of the outbox contract that 4a/4b/4c established as producers.

7 tests via `bun:test`; 37 expect calls; 105ms; 6/6 mutations all flip expected red, 0 escapees.

## What went well

- **Scope decision held.** Skipped D1 substrate (pg_notify + pg_cron + advisory-lock cost-coalescing) because it's load-bearing for cost/throughput, not delivery semantics. Tests invoke `processQueue()` directly. Right call — this kept PoC small while still pinning the load-bearing claims.
- **Mock merchant abstraction worked.** Programmable-behavior pattern (`MerchantBehavior` discriminated union: `always_200` / `always_500` / `fail_n_then_succeed` / `timeout_always`) made each test self-explanatory. Per-event-id signature/body recording let assertions check round-trip HMAC integrity AND merchant dedup primitive (X-Event-Id stable) AND secret rotation detection — three different invariants on the same mock.
- **`bun:test` was the right choice over pgTAP for this PoC.** HTTP timing + multi-step state assertions don't fit pgTAP's plan/finish model cleanly. `bun:test` handles async + describe/test naturally; ~170 LoC of test code does what would have been 300+ LoC across multiple .spec.sql files.
- **Cross-test redundancy emerged again.** Mutation M-A (drop denorm UPDATE) reds 3 tests because `attempt_count` is consumed by both retry-budget logic + at-least-once verification. M-C reds tests 1+2+3. Same shape as observed in 4a/4b/4c — shared primitive → multiple test guards. By PoC #4 this is durable.
- **Trace chain established.** `603fb3d5…` is a child of `bde8b561…` (4c) via `arra_trace` `parentTraceId`. First cross-PoC chain link. Future PoCs in the deposit/callback area can navigate the chain backward.

## What didn't go to plan

- **Initial test run hung.** `bun test` ran for >2 minutes at 99% CPU. Cause: `await expect(sql\`UPDATE ...\`).rejects.toThrow(...)` pattern leaves Bun.SQL pool in dirty state when the rejected query throws; subsequent queries hang waiting for connection recovery. **Workaround**: use try/catch directly:
  ```ts
  let err: any = null;
  try { await sql`UPDATE callback_attempts SET ...`; } catch (e) { err = e; }
  expect(err).not.toBeNull();
  expect(String(err.message)).toMatch(/append-only/i);
  ```
  Cost: ~10 min to diagnose + fix. **Lesson encoded for future PoCs**: when testing PG-level error paths via `bun:test`, prefer try/catch over `expect.rejects.toThrow` against Bun.SQL.
- **HMAC test compared against pre-computed signature.** First version: `expect(sigsAtt1[0]).toBe(hmacHex(SECRET_V1, body))` where `body = JSON.stringify(payload)`. Failed because the dispatcher signs `JSON.stringify(row.payload)` where `row.payload` is the JSONB value as parsed by Bun.SQL — key order may differ from the original literal. **Fix**: use the body the merchant actually received as the comparison input — `hmacHex(SECRET_V1, bodies1[0])`. This is a proper round-trip check; doesn't depend on Bun.SQL's JSON normalization. Cost: ~5 min.
- **Forgot to write `schema.sql` initially.** Wrote `rpcs.sql` first, hit psql "No such file" when applying. Trivial fix. Lesson: when scaffolding, write schema first (RPCs depend on tables).

## Honest feedback

1. **The "first PoC needing X" tax is real.** PoC 4c took ~1h; PoC 9 took ~3h. The delta is mostly: writing the dispatcher + mock merchant abstractions + figuring out Bun.SQL gotchas. Future PoCs that reuse this layer (e.g., re-test §ADR-9 with different merchants, or test §ADR-11 idempotency middleware) should be much faster. **Calibration for next PoC**: §ADR-3 with EF runtime will be similar — first-time EF setup will eat ~2h before any tests can run.
2. **Trace chain is set up but I still didn't use it during the pass.** Same gap as §ADR-4c retro flagged. I opened the trace, set parentTraceId, but didn't `arra_trace_get` to navigate the chain when I needed context (e.g., when designing the `record_attempt` RPC, I should have walked back to `expire_deposit` for shape consistency). Need to make trace-navigation part of the workflow, not just an attached anchor.
3. **Mock merchant does double-duty (dispatcher target + assertion oracle).** It's neat but couples the two responsibilities. If the merchant + assertions ever diverge (e.g., real-merchant test fixture), this would need refactoring. Acceptable for PoC; flag for production-ready handoff.
4. **The `processQueue` function is sweep-shaped, not notify-shaped.** D1 is hybrid push-pull (pg_notify + pg_cron). PoC tests only the pull side. A real production deployment would need Bun-side or EF-side notify listener — that integration not exercised. Acceptable since D1 is out of scope per README, but a reader could miss this.

## AI Diary

### Approach evolution

Going in I expected this to be the most complex PoC of the series — first HTTP layer, first non-pgTAP test framework, first mock-merchant pattern. It was, but only ~2× the time of the easier ones. Most of the design effort went into:

- Making the dispatcher pure (pure function `processQueue(sql, opts)` rather than long-running daemon) — testable via direct invocation, no scheduling concerns
- Programmable mock merchant — encoding test scenarios as `MerchantBehavior` discriminated union rather than per-test ad-hoc fakes

Both choices paid off at test-writing time — tests read clearly because the moving parts are limited.

### The HMAC test was the most architecturally interesting

Test 3 (`dispatch-time-hmac-uses-current-secret`) demonstrates D3's load-bearing claim: HMAC is signed at dispatch time, using the current merchant secret value. The test:

1. Seeds row + merchant with secret v1
2. First sweep tick — merchant 500s; signature is `hmacHex(v1, body)`
3. Rotates merchant secret v1 → v2
4. Second sweep tick — merchant 200s; signature is `hmacHex(v2, body)`
5. Asserts: signatures differ across rotation, both round-trip-verifiable

What this proves architecturally: rotating the merchant secret automatically re-signs in-flight retries without any DB rewrite. If the signature were stored at write-time on the queue row (Trade-off C in the ADR), rotation would require backfilling all pending rows. The PoC makes the design choice tangible.

### The append-only forensic log is parallel to §ADR-4d D9 (slip_verify_attempts)

D6 explicitly cites §ADR-4d D9 as precedent. Same shape: append-only attempts table + denormalized counter on parent row. Two domains, same pattern. Substrate convergence in the small.

When §ADR-4d slip-integration PoC happens, the schema/test pattern from this PoC transfers directly. That's an estimated 30-40% time savings for §ADR-4d's forensic-log claims.

### The "5 events" insight from §ADR-9 §Context

The ADR opens by enumerating exactly 5 producer flows that feed `callback_queue`:
- `deposit.completed` (auto-match §ADR-4b)
- `deposit.expired` (auto-expire §ADR-4c)
- `deposit.failed` (slip admin-reject §ADR-4d future)
- `payout.completed` / `failed` / `waiting_to_review` (withdrawal lifecycle §ADR-4a)

This PoC consumes events from any producer. The producer-side schema differences (queue row column shape varies a tiny bit across 4a/4b/4c) are abstracted away — dispatcher only needs `(id, merchant_id, payload, status, attempt_count, last_attempt_at, last_response_code, last_attempt_id)` columns + `merchant_config(callback_url, secret)`. So in a unified production schema, the columns from each PoC merge into ONE `callback_queue` table. The PoC's `merchant_id` column makes the multi-merchant story explicit.
