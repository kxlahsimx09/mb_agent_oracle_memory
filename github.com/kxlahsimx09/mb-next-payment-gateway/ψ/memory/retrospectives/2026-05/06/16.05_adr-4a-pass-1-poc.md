## What went well

- **Pattern reuse compounded fast.** Schema + claim_RPC + tests + mutation harness re-purposed the §ADR-4b template. Time per spec test dropped ~40% vs §ADR-4b (estimated). The `_seed_*` helper function pattern + GUC-poison framework + 2-line evidence cite block + Bun mutation harness all transferred without redesign. Each PoC after the first amortizes the boilerplate cost.
- **Mining gave concrete fixtures.** Production sample shapes (`waiting_to_review` rows with OTP-clicked-session-dead error, batch sizes 5-6, source_type distribution 78/21/1/0.3) shaped test inputs without invention. The "OTP clicked but browser died" pattern in evidence file directly motivates D6 triage rule — without that mining the rule sounds abstract.
- **Cross-test redundancy emerged organically.** Mutation M-E + M-F both red test 09 alongside their primary targets; M-G reds tests 10 + 08; M-B reds 02 + 04. This is exactly the kind of test-suite property you want — overlapping coverage means a regression at any of these points has multiple chances to be caught. I noted it in mutation-results table as a positive signal.
- **Tier-1 ranking held.** §ADR-4a fits Postgres-only-floor cleanly (claim atomicity + sweep + lifecycle all in PL/pgSQL; Realtime is performance, not security; Mode 1 EF routing is §ADR-8's territory). No EF needed for the load-bearing claims.

## What didn't go to plan

- **`source_id` ambiguous between RETURNS TABLE column and `withdrawal_queue.source_id` column.** Initial `claim_withdrawal_items` had `SELECT id, source_id, ... FROM withdrawal_queue` inside FOR loop — PL/pgSQL couldn't disambiguate from the function's RETURNS TABLE columns. Fixed with table aliases (`q.source_id AS sid`). Cost: ~5 min. Lesson: when RETURNS TABLE column names match underlying table column names, always alias inside loops.
- **Forgot DO-block wrapping for `PERFORM` again.** This is the SAME mistake as §ADR-4b PoC. Tests 04, 05, 09, 10 all had `PERFORM poc4a.foo(...)` at top level → SQL syntax error → tests reported "no tests ran". Fixed by wrapping in `DO $$ BEGIN ... END $$;`. Cost: ~3 min.
  - **Process improvement to bake into the §ADR-4c PoC:** add a tests/_skel.sql template that already contains the DO-wrap pattern. Or write a lint check in run-tests.sh that greps tests for top-level PERFORM and bails early.
- **`psql` `set -e` + `pipefail` killed the runner loop on first FAIL.** When test 01 SQL-errored, `echo "$out" | grep -E ... | sed` returned non-zero (grep no-match) → pipefail propagated → `set -e` exited the loop. Fixed with trailing `|| true`. Cost: ~2 min. Bake into next runner template.
- **`unlike()` regex in test 09 used LIKE `%` syntax.** pgTAP `unlike(text, regex, desc)` takes a POSIX regex (not LIKE pattern). Initial `'%status\s*=\s*''pending''%'` was wrong; corrected to `'status[[:space:]]*=[[:space:]]*''pending'''`. Cost: ~3 min.
- **Test 04 first try used a convoluted query.** Original tried to join through claimed-row's source_id back to ts_payouts.request_id — got NULL because at that point the ts_payouts row hadn't been UPDATEd yet (the SELECT pre-dated the cascade). Rewrote to assert state directly via withdrawal_queue.status comparison between OLD-LOW and NEW-HIGH — much clearer, 3 lines instead of 10.

## AI Diary

### Approach evolution

I almost split this PoC into Pass-1 (claim RPC only) + Pass-2 (sweep + lifecycle). Decided to bundle because: the same `_seed_payout` helper drives all three subsystems; sweep + lifecycle are tiny RPCs (~40 + ~90 LoC); and the cross-test coverage in mutation testing was only achievable with all three present. Right call — total wall-clock 1.75h was less than 2× the time of just claim RPC.

### Sweep triage rule = the most production-grounded test in the suite

Test 07 + test 08 mirror the production `waiting_to_review` pattern almost 1:1. The mining surfaced that real `waiting_to_review` rows in mobiz current have:
- `bank_transaction_id` SET (bot already submitted)
- `error_message` mentioning OTP-clicked-session-dead
- `batch_id` matching other rows in same batch (multi-row OTP-flow failure)

Then the §ADR-4a D6 rule says exactly: this is the sweep-routes-to-waiting_to_review case. Reading production data and ADR text back-to-back, they confirm each other — the rule isn't theory, it's "encode what you already do, just structurally instead of via admin runbook". This is the cleanest "ADR-as-codification-of-existing-runbook" example I've seen so far in the corpus.

### The `cancle` typo

Mining hit 59 rows in production at `status='cancle'` (sic). My CHECK constraint in PoC schema uses `status IN ('pending','claimed','processing','success','failed','waiting_to_review','cancelled','overridden')` which rejects the typo. So next-system enforces the spelling at INSERT time — production data won't migrate as-is.

This is a migration concern, not an impl-architect concern. I noted it in the evidence summary so the architect's W2 retroactive sweep can pick it up. If I'd been a pg-tester, this would be a `#regression-candidate` learning. As impl-architect I just flag and move on.

### Mutation M-G crossing tests was the moment the suite "felt right"

I expected M-G to red test 10 (because test 10 directly asserts wallet balance after mark_failed). Surprise: it also red test 08, because test 08 calls sweep_stale_claims which calls mark_failed for no-tx-id rows, which calls the (now mutated) wallet-refund step. That cross-coverage means a regression in step (ii) has TWO independent test guards.

This is what good test suites feel like — if you mutate a load-bearing line, multiple unrelated-looking tests catch it. The signal is: my abstraction boundaries are right because the same primitive is reused, and my test surface is right because each test exercises the primitive in its own context.
